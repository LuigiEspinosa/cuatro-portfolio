# D5c: Traefik ForwardAuth, and the Auth.js status question

Accessed: 2026-08-15. All conclusions trace to sources retrieved this run. Budget: 6 distinct
publishers read (registry.npmjs.org, doc.traefik.io, api.github.com, github.com, authjs.dev,
better-auth.com), 11 tool calls.

## Q1 verdict: does ForwardAuth reduce integration work, or move it?

**It reduces the work of *gating*, and moves the work of *identity*.** Those are two different
jobs and ForwardAuth only does the first one for you.

For the 7-app / 6-framework case: ForwardAuth genuinely removes per-app OIDC client wiring for
any app that only needs "is this a logged-in human, and who are they?": the app reads an
injected header and does nothing else. That is a large saving over hand-wiring an OIDC client
into Next.js, Svelte, Vue, Angular, React/Vite and Phoenix LiveView separately (6 different
libraries, 6 different callback/PKCE/refresh implementations, 6 different failure modes).

But the moment an app needs its own user rows, roles, per-object authorization, or a session it
controls, ForwardAuth does not replace anything: the app still needs code that reads the
injected identity header and maps it onto a local session/user record. That code is smaller than
an OIDC client, but it is per-app, and it carries a security obligation (below) that the OIDC
client version does not.

Per the Traefik v3.7 docs, the middleware is a **per-request** delegation with **no documented
caching**, which is a real cost on a 2 vCPU box for asset-heavy SPA loads. See limitations.

Practical read for a solo dev: ForwardAuth is the cheapest thing that works *today* and is a
legitimate third architecture, not a toy. It is strongest as a **gate in front of apps that have
no user model at all** (dashboards, admin UIs, internal tools). It is weakest exactly where this
deployment is most interesting: the Phoenix LiveView app and anything with per-user data, where
the app needs a session regardless. A mixed posture (ForwardAuth for the no-user-model apps, real
OIDC for the apps with user models) is defensible and is what the evidence supports.

### How it works

From Traefik's own v3.7 reference documentation for the ForwardAuth HTTP middleware
(doc.traefik.io/traefik/v3.7/…/middlewares/forwardauth/, accessed 2026-08-15):

- Traefik forwards the incoming request to an external authentication service at `address`.
- **2XX response → access granted**, the original request proceeds to the upstream app.
- **Non-2XX response → the auth server's own response is returned to the client** (so the auth
  service controls the redirect-to-login, the 401 body, etc.).
- Traefik sends these headers describing the original request to the auth service:
  `X-Forwarded-Method`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Uri`,
  `X-Forwarded-For`.
- `authRequestHeaders`: "List of the headers to copy from the request to the authentication
  server." If empty/unset, **all** headers are passed through.
- `authResponseHeaders`: copies named headers from the **auth server's response** onto the
  request forwarded to the upstream app, **replacing** any conflicting header already present.
  This is the mechanism by which identity reaches the app.
- `authResponseHeadersRegex`: same, selected by regular expression; the docs note it "allows
  partial matching of the regular expression against the header key", so **full matching requires
  explicit `^` and `$` anchors**. This is a foot-gun: an unanchored regex copies more headers than
  intended.
- `headerField`: "Defines a header field to store the authenticated user."
- `addAuthCookiesToResponse`: copies named cookies from the auth server onto the response to the
  client (how the auth service sets its own session cookie).
- `preserveLocationHeader`, `preserveRequestMethod`, `authSigninURL` (redirect target on 401),
  `forwardBody`, `maxBodySize`, `maxResponseBodySize`.
- `trustForwardHeader` is **deprecated** and slated for removal in the next major version; the
  docs direct you to configure `forwardedHeaders.trustedIPs` at the EntryPoint instead.

### Documented limitations (incl. WebSockets)

- **Every request round-trips to the auth service.** The middleware delegates each incoming
  request; the v3.7 page documents no caching mechanism. Confidence: high for "no caching is
  documented"; the *latency* consequence is mechanism-derived, not a quoted benchmark.
- **`forwardBody` breaks streaming: verbatim:** "As body is read inside Traefik before
  forwarding, this breaks streaming." Leave `forwardBody` off unless the auth service genuinely
  needs the body.
- **Unbounded body sizes by default.** `maxBodySize` defaults to `-1` (unlimited) and
  `maxResponseBodySize` is unrestricted if unset; Traefik's docs warn this has "significant
  security and performance implications", citing DoS and memory exhaustion. On a 2 vCPU / 8 GB
  VPS this is worth setting explicitly.
- **WebSockets / Phoenix LiveView: NOT addressed in the Traefik v3.7 ForwardAuth documentation.**
  I looked and did not find it. The mechanism implies the auth check happens on the HTTP upgrade
  request only, with no re-check for the life of the socket, but that is my inference from how
  the middleware is described, **not a sourced claim**, and it should be tested before being
  relied on. The practical consequence, if the inference holds, is that a LiveView socket
  authorized at handshake stays open after the proxy session expires. Treat as an open question.

### Does it replace per-app OIDC, or only gate?

Both are possible; the docs support the "replace" pattern mechanically. `authResponseHeaders` /
`authResponseHeadersRegex` copy auth-service response headers onto the upstream request, and
`headerField` exists specifically to "store the authenticated user": that is Traefik documenting
identity propagation to the app, not merely a yes/no gate. So an app *can* trust the header and
skip OIDC entirely.

What that does **not** do:
- It does not give the app a session it controls (logout, refresh, step-up, remember-me).
- It does not give the app roles/claims beyond whatever the auth service is configured to emit as
  headers.
- It does not help an app that must work in local development without the proxy in front.

So: ForwardAuth replaces per-app OIDC **for identity delivery**, but the app still owns whatever
session and authorization semantics it needs. For Phoenix LiveView specifically, where the
established finding is that auth happens in a plain controller plug before `mount/3`: a
ForwardAuth header is readable in exactly that plug, so the integration point is the same one
you'd use for OIDC; only the source of the identity changes.

### Security caveats of proxy-injected headers

Documented by Traefik (v3.7):
- `trustForwardHeader` is deprecated precisely because blanket trust of `X-Forwarded-*` is
  dangerous; the replacement guidance is `forwardedHeaders.trustedIPs` at the EntryPoint, "to
  prevent untrusted clients from injecting malicious `X-Forwarded-*` headers."
- `authResponseHeaders` **replaces** conflicting headers, and unanchored `authResponseHeadersRegex`
  matches partially, both are ways to accidentally widen what the app sees.
- Unset body-size limits → documented DoS/memory-exhaustion risk.

**The "app reachable not through the proxy" caveat: I did NOT find this stated in the Traefik
pages I read.** Stating it plainly as reasoning rather than as a citation: if the app trusts an
identity header, then anyone who can reach the app's port directly: a container port published
to `0.0.0.0`, another container on the same Docker network, a misconfigured firewall rule, SSRF
from a neighbouring app, or the developer's own `localhost`: can set that header themselves and
become any user. There is no cryptographic binding in the ForwardAuth pattern: the header is
trusted because of network position alone. This is the single largest difference from OIDC, where
the app validates a signed token and network position is irrelevant. On a **single VPS running 7
apps side by side**, "another process on this box can reach the app directly" is the default
condition, not an edge case. Mitigation is binding every app to loopback or an internal Docker
network only, and never publishing app ports, which is operationally easy but is a standing
invariant you must not break later. Confidence: high on the mechanism, but flagged as unsourced
this run; it belongs in the two-source security class and I only have one side of it.

### Auth services designed to sit behind ForwardAuth

**oauth2-proxy**: latest stable **v7.15.3, published 2026-06-09** (GitHub releases API, accessed

## Q2 verdict: Auth.js / NextAuth actual status, **CONFIRMED (with a material correction)**

The circulating claim has two halves. One is confirmed at primary source; the other is the wrong
word.

**Confirmed:** users *are* being directed to Better Auth, by the maintainers, in the project's own
channels. The `nextauthjs/next-auth` GitHub README states verbatim: *"Auth js is now part of
Better Auth. We recommend new projects to start with Better Auth unless there are some very
specific feature gaps (most notably stateless session management without a database)."*
Independently, authjs.dev's own front page states: *"The Auth.js project is now part of **Better
Auth**"*, linking to an announcement post. Two primary sources, same message.

**Correction:** "maintenance mode" is not what happened and not the wording used. This is a
**project merger / change of stewardship**, announced by the maintainers, with an explicit
recommendation for *new* projects and an explicit named exception (stateless sessions without a
database). And the package is demonstrably still shipping: `next-auth@4.24.15` and
`next-auth@5.0.0-beta.32` were both published **2026-07-20** (under a month before access date)
as **security** releases (malformed Bearer tokens, OAuth cookie binding, email normalization, and
"auth checks failing open on provider configuration errors"). A project that shipped a
fail-open-auth fix four weeks ago is not abandoned. The content-farm framing was directionally
right about the destination and wrong about the mechanism.

**v5 is still beta**, confirmed at npm: `dist-tags.beta = 5.0.0-beta.32`, while
`dist-tags.latest = 4.24.15`. v5 has been in beta long enough that beta.32 is the current tag.
For this decision that matters: **the "modern" NextAuth is still not GA.**

**Cadence (12 months, from GitHub release dates):** 2026-04-14 (`next-auth@4.24.14` plus a wide
fan-out of `@auth/*` adapters), then 2026-07-20 (`@auth/core@0.41.3`, `next-auth@4.24.15`,
`next-auth@5.0.0-beta.32`, `@auth/sveltekit@1.11.3` and adapters). Sparse, batched, and
security-driven. I retrieved a 40-item release window that did not reach back a full 12 months, so
I can state "two release waves in the last four months, most recent 2026-07-20" and no more. Do
not infer a rate from this.

**Better Auth**: latest stable **v1.6.29, published 2026-08-14** (one day before access date),
with v1.7.0 in release-candidate (`v1.7.0-rc.6`, 2026-08-14). Cadence is aggressive and
continuous: v1.6.23 → v1.6.29 between 2026-06-29 and 2026-08-14, i.e. roughly weekly or better,
with a parallel RC track. This is a fast-moving project, which cuts both ways: active, but
`1.7.0` carries breaking changes (release notes flag `feat(oauth)!`, `feat(oauth-provider)!`,
`refactor(generic-oauth)!`: the `!` is a breaking-change marker).

**Better Auth's OIDC roles: it documents BOTH, but they are not equally mature:**
- **As an OIDC *client* (consuming a central provider): yes, and this is the relevant one.** The
  **SSO plugin** documents signing users in against external identity providers over **OIDC,
  OAuth2 and SAML 2.0**. Providers are registered server-side via `registerSSOProvider` with
  `providerId`, `issuer`, `domain` and `oidcConfig`; most endpoint fields are optional because
  "Better Auth automatically fetches and validates the provider's OpenID Connect Discovery
  Document" from `.well-known/openid-configuration`. Orchestration is server-side.
- **As an OIDC *provider* (being the central IdP): documented, but explicitly warned off.** The
  OIDC Provider plugin exposes `/oauth2/register` (RFC 7591), `/oauth2/authorize`, `/oauth2/token`,
  `/oauth2/consent`, `/oauth2/userinfo`, supports Authorization Code and PKCE (`clientSecret`
  "Optional for public clients using PKCE"). But the page carries a verbatim warning: **"This
  plugin is in active development and may not be suitable for production use."** It also carries a
  deprecation notice: it "will soon be deprecated in favor of the OAuth Provider Plugin."

**Relevance to this decision:** Better Auth is relevant as the **client** side (a Next.js app
federating to a central provider), not as the **central provider itself**: its provider plugin is
self-flagged as not production-ready *and* on a deprecation path to a successor plugin. Anyone
tempted to make Better Auth the single IdP for all 7 apps should read that warning first.
