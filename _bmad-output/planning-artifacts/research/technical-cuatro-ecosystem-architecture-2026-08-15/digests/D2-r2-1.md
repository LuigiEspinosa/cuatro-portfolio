# D2 round 2: Primer analogue, DSD support, web-component blockers in 2026

Accessed: 2026-08-15. Budget: 15 tool calls / 6 source reads, spent. Gaps are stated, not padded.

## Q1 verdict: what Primer actually shares between React and Rails

**The headline finding is that the analogue is being retired.** `primer/view_components`'
own README states: *"As part of GitHub's move to React-based interfaces, Primer ViewComponents
is in maintenance mode as of February 2026"*: security updates, dependency bumps and critical
bug fixes only, **no new features, components, or significant enhancements**: and *"We encourage
internal GitHub consumers to plan to migrate from Primer ViewComponents to Primer React."*
(github.com/primer/view_components README, accessed 2026-08-15).

So the closest public precedent for "a React cluster and a server-rendered cluster sharing one
design system" was maintained for roughly six years and then **collapsed to a single React
implementation**. That is the single most decision-relevant fact in this round.

**What is actually shared:** tokens, and essentially only tokens. `@primer/primitives` is the
shared layer; its repository names `@primer/react`, `@primer/view_components` and `@primer/css`
as its consumers (github.com/primer/primitives, accessed 2026-08-15). Tokens are authored as
**JSON in `src/tokens`**, compiled by **Style Dictionary** via `scripts/buildTokens.ts`, and
distributed from `dist/` as **CSS files exposing CSS custom properties**, in multiple theme
variants (light, dark, dark-dimmed, plus accessibility modes such as high contrast and
tritanopia) built through an **overrides mechanism** where a mode declares only its deltas from
a base mode. There is no shared component runtime, no shared behaviour layer visible in the
primitives repo: the React components and the Ruby ViewComponents are independent
reimplementations that consume the same CSS variables. This is exactly the round-1 pattern:
**tokens federate values; behaviour is reimplemented per stack.**

**`@primer/css` status:** not deprecated but explicitly **KTLO ("Keep The Lights On") /
maintenance mode**, with guidance to use `primer/react` or `primer/view_components` for complete
patterns that include markup, and `@primer/css` only for existing utility classes. This came
from a search-result summary of the primer/css repo and npm, **not** a direct read of the repo,
treat as medium confidence and re-verify. Note the guidance is now partly self-contradictory,
since view_components is itself in maintenance mode as of Feb 2026.

**Not retrieved (budget):** release cadence numbers and maintainer counts for either
implementation, and any explicit public statement from Primer acknowledging *visual drift*
between the React and Rails implementations. One search snippet referenced Primer React release
notes "addressing visual parity between components", but I did not read the release notes, so I
am **not** claiming Primer publicly acknowledges cross-implementation drift. Unresolved.

## Q3: React 19 + DSD, corroborated / refuted / unresolved

**CORROBORATED, from React's own issue tracker, with an important twist.**

facebook/react issue **#33698, "Bug: [React 19] React is not support Declarative Shadow DOM
(DSD)"**, opened **2025-07-04** against React **19.0.0 and 19.1.0**: React has no logic to convert
`<template shadowrootmode="open">` into a shadow root; on SSR the parser removes the template and
attaches the shadow root, but React's reconciler does not ignore it on the client, producing a
server/client mismatch and hydration errors. An earlier issue **#26071** reports the same
reconciler limitation against React 18.2.0, so the defect predates 19 and survived into it.

**The twist:** #33698 is **closed as not planned**, labelled *"Resolution: Stale"* (auto-closed
for inactivity) and *"Status: Unconfirmed"*. No maintainer comments were visible in the fetched
page. So this is corroborated as a *reported and unfixed* behaviour, **not** as something React
has confirmed or committed to fix. Round 1's single source is now backed by the primary tracker;
the class requirement is met (round-1 source + React issue tracker #33698/#26071).

**Workaround, from the same search cluster:** `@webcomponents/template-shadowroot` exposes
`hydrateShadowRoots()`, which walks `<template shadowrootmode>` elements and attaches them as
shadow roots on the client: the standard escape hatch for frameworks that do not handle DSD.
I did not read that package's docs directly; medium confidence on current version/status.

## Leads worth chasing

1. **Primer's replacement story mentions web components.** A search summary of the Primer org page says the design system "continues through guidance, tooling, and ready-to-use React **and web components**". If GitHub is keeping a web-component layer while retiring the Rails components, that is directly on-thesis for this project and is the single highest-value follow-up. Verify against primer.style and the Primer org repos.
2. **Read `primer/css` directly** to settle the KTLO-vs-deprecated question and get real version/date numbers.
3. **Primer release cadence + maintainer counts**: compare `primer/react` releases against `primer/view_components` releases over the last 12 months; the divergence in cadence is probably the quantitative proof of drift that Primer never states in prose.
4. **`@lit-labs/ssr` graduation**: search Lit's blog/RFCs for any stated plan to leave Labs. Five years in Labs is itself a finding about the maturity of server-rendered web components.
5. **Cascade layers across the shadow boundary**: unverified; matters if the token sheet needs `@layer` to lose specificity fights inside components.
6. **`@webcomponents/template-shadowroot`**: current maintenance status and whether it is still the recommended React workaround, or whether a React-specific integration has appeared.
