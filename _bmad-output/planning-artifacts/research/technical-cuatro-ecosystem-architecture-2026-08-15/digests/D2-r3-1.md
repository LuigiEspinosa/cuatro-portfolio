## Q1 verdict: Renovate vs Dependabot for one hub governing many repos

| Capability | Renovate (44.30.3, 2026-08-15) | Dependabot (GitHub Docs, accessed 2026-08-15) | Source |
|---|---|---|---|
| Shareable config hosted in ONE repo, referenced by many | **Yes.** `extends: ["github>owner/repo"]` — docs state the point is to keep config "in one location rather than having to copy/paste it to every repository individually" | **No.** The options reference documents no mechanism to extend or inherit a config from another repository | docs.renovatebot.com/config-presets/ ; docs.github.com dependabot-options-reference |
| Preset resolution syntax | `github>owner/repo` → `https://github.com/owner/repo`, loads `default.json` from default branch; `gitlab>owner/repo` same; `local>owner/repo` resolves against the current platform (self-hosted / GHE) | n/a | docs.renovatebot.com/config-presets/ |
| Preset versioning / pinning | Yes — git tag suffix: `github>abc/foo#1.2.3`. Untagged = default branch (floating) | n/a | docs.renovatebot.com/config-presets/ |
| Named presets in one repo | Yes — `<preset-name>.json` alongside `default.json`; `renovate.json` as a preset file is deprecated | n/a | docs.renovatebot.com/config-presets/ |
| Org-wide default preset auto-discovery | Yes — during onboarding Renovate looks for a `renovate-config` repo in the parent org with `default.json` and proposes it | Org-level config exists but ONLY for **private registry credentials** (GA 2025-07-22), not update policy/schedule/grouping | docs.renovatebot.com/config-presets/ ; github.blog changelog 2025-07-22 |
| Grouping updates into one PR | Yes — `packageRules` with `groupName`, matched by `matchDepTypes`, `matchUpdateTypes`, `matchPackageNames`, `matchCurrentVersion` | **Yes** — `groups` block with `patterns`, `exclude-patterns`, `dependency-type`, `update-types`, `group-by: dependency-name`. (Old "Dependabot can't group" folklore is OUT OF DATE) | both, as above |
| Native automerge | Yes — `automerge`, `automergeType` (`pr`\|`branch`), `automergeStrategy`, `platformAutomerge` (default on), `automergeSchedule`, `ignoreTests` | **No native option.** Users must rely on GitHub's own auto-merge feature or an external Actions workflow | both, as above |
| Release cadence | Extremely fast: 44.29.5 → 44.30.3 across 2026-08-14/15 (5 releases in ~2 days) | Continuously deployed service, no user-visible version | github.com/renovatebot/renovate/releases |

**Renovate automerge guardrails (documented, verbatim-ish):**
- Automerge is not instantaneous — Renovate needs roughly two hours to find a window where tests pass and the branch is current; "Renovate will only automerge one branch/PR, per target branch, per run."
- By default passing status checks are required. "We strongly recommend you have tests in any project where you are regularly updating dependencies."
- `ignoreTests` exists but is documented as not recommended.
- Guidance: "enable automerge for any dependency update where you would select 'merge' anyway"; works particularly well for `devDependencies` and `lockFileMaintenance`; keep it OFF where you'd want to read the changelog.
- Common blockers: branch protection preventing commits, mandatory PR reviews, committer allowlists that exclude Renovate, CODEOWNERS approval requirements. Workarounds: "Allow specified actors to bypass required pull requests", or the `renovate-approve` / `renovate-approve-2` helper apps.
- `automergeType: branch` pushes straight to a branch and only opens a PR if tests fail — reduces noise, but requires CI to run on `renovate/**` branches.

**Verdict for a solo dev with ~15 repos:** Renovate, decisively — and the deciding feature is the shareable preset, not grouping (Dependabot has grouping now). One `renovate-config` repo holding `default.json` means all 15 repos carry a single unchanging line, and every policy change (schedule, grouping, automerge rules, ignore rules) is a commit in the hub. Dependabot would require editing 15 copies of `.github/dependabot.yml`, and could not automerge without also copying an Actions workflow into all 15.

## Q2 verdict: how to publish the token artefact

| Mechanism | Cost | Consumer friction | Works for Elixir / Angular / Phoenix? | Source |
|---|---|---|---|---|
| **npmjs.com public scoped package** | Free (npm user account free; org needed only for org scope) | Zero — `npm i @scope/tokens`, no auth. Publish needs 2FA on the account or a granular access token with bypass-2FA | JS frameworks: yes, build-time. Elixir: only if the Phoenix app runs a Node build step (most do, via esbuild/assets pipeline) — otherwise you'd vendor the built CSS | docs.npmjs.com creating-and-publishing-scoped-public-packages |
| **GitHub Packages npm registry** | Public packages free & unlimited. Private: Free 500MB storage / 1GB transfer per month; Pro 2GB / 10GB; Team 2GB / 10GB; Enterprise Cloud 50GB / 100GB | **High.** GitHub Packages only supports scoped packages (`@NAMESPACE/NAME`). Every consumer needs `.npmrc` with `@NAMESPACE:registry=https://npm.pkg.github.com` AND `//npm.pkg.github.com/:_authToken=TOKEN`. Docs: "You need an access token to publish, install, and delete private, internal, and public packages" — i.e. **auth even for public packages**. In Actions, `GITHUB_TOKEN` works if the repo is granted read access to the package | Same as above, plus a token on every dev machine and in every CI job | docs.github.com working-with-the-npm-registry ; about-billing-for-github-packages |
| **CSS file from a CDN / hub domain, `<link>` or `@import`** | Free-ish | Zero install, zero auth, zero toolchain | Yes — works from Elixir/Phoenix, Angular, anything that renders HTML | see "could NOT find" below |

**Trade-off, stated plainly:** for a portfolio project whose tokens are not secret, there is **no reason to use GitHub Packages over public npmjs.com**. GitHub Packages adds an `.npmrc` + token on the developer machine *and* in CI, for every one of the 15 repos, and imposes that friction even on public packages — while npmjs.com public packages cost nothing and require no consumer auth at all. The only arguments for GitHub Packages are (a) the tokens genuinely must be private, or (b) you want everything in one billing/permission surface. Neither applies here. Note that even in the private case, GitHub Actions downloads using `GITHUB_TOKEN` do not count against the hosting repo's data-transfer allowance, so the 1GB Free-tier transfer cap is unlikely to bind — but the per-machine token friction remains the real cost.

**CDN/CSS-only distribution — what breaks vs what it buys (reasoned from the mechanics, NOT from a retrieved case study; see gaps):**
- Buys: zero install, no registry auth, works identically from Elixir/Phoenix and every JS framework, one URL to update.
- Breaks: no semver contract and no lockfile, so a hub change hits all 15 sites the moment the CDN cache expires — the opposite of controlled propagation; values are runtime-only, so no build-time access (no Tailwind config values, no compile-time theming, no tree-shaking of unused tokens); an extra render-blocking request; and cache-busting has to be hand-rolled via a versioned path (`/tokens/v3/tokens.css`), which is a package registry re-implemented badly.
- Sensible hybrid: publish the package publicly on npm for build-time consumers, and ALSO emit a versioned CSS file at a stable URL for the Phoenix app — the same Style Dictionary build produces both.

## Q3 verdict: what is genuinely central vs what must be duplicated per repo

**Genuinely central (one edit in the hub, all repos see it):**
1. **Reusable GitHub Actions workflows** — established prior round, not re-researched.
2. **Renovate shareable preset** — `default.json` in one `renovate-config` repo. All policy lives here.
3. **The token package version itself** — publish once, Renovate opens the 15 PRs.

**Must be duplicated per repo (but written once, then frozen):**
1. `renovate.json` containing a single line: `{"extends": ["github>owner/renovate-config"]}`. This is the bootstrap; it never changes again.
2. The reusable-workflow caller stub in `.github/workflows/`.
3. `package.json` dependency entry (Renovate then maintains it).

**Repository templates — bootstrapping only, confirmed:**
GitHub Docs state a new repo from a template gets "the same directory structure and files as your default branch", and that "Branches created from a template have unrelated histories, so you cannot create pull requests or merge between the branches." There is **no** documented mechanism for template changes to propagate to repos already created from it. Templates are a one-time scaffold. Useful for creating repo #16; useless for governing repos #1–15.

**Org rulesets — prior "Enterprise-gated" finding is WRONG, corrected:**
Per GitHub Docs, rulesets are available in **public repositories on GitHub Free** (including Free for organizations), and in **public and private repos on Pro, Team, and Enterprise Cloud**. So a solo dev on Free can use rulesets on public repos today; private repos need Pro (which a solo dev plausibly has). *However* — push rulesets specifically are documented as Team-plan-and-up for internal/private repos. More importantly for this decision: **rulesets govern branch/push protection, not file content.** They cannot push a config file into a repo. They are not a propagation mechanism.

**Dependabot org-level config:** exists but is scoped to private-registry credentials only (GA 2025-07-22), private-repo support gated behind GitHub Advanced Security / Code Security SKU. Not a general config-propagation mechanism. Also requires an organization, which a solo dev may not have.

**Net:** the only genuine config-propagation mechanisms are (a) reusable workflows, (b) Renovate presets, (c) a bot that opens PRs — where Renovate *is* that bot for dependency-shaped changes. For non-dependency file changes (e.g. an eslint config edit), nothing central exists; you either script `gh` across the repos or accept 15 manual edits.
