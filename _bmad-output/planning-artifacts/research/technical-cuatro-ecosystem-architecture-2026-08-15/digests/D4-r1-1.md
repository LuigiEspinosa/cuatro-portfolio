# D4 round 1: devcontainers and Windows repo relocation

Research run 2026-08-15. Web-only, research firewall observed. Budget spent: 6 sources fetched, 14 tool calls.

## Q1 verdict: is "monorepo or devcontainers" a false dichotomy?

**Yes: false dichotomy, and the evidence is structural rather than rhetorical.** No source retrieved this run couples the two decisions. They answer different questions:

- **Repository layout** answers: where does code live relative to other code, colocation, atomic cross-project commits, one shared dependency graph, one CI trigger surface.
- **Dev containers** answer: what toolchain does a given folder get when you open it, a `devcontainer.json` describes an image, features, and lifecycle commands for *a workspace folder*, not for *a repository*.

The decisive evidence is that the Dev Container Specification explicitly accommodates **many dev containers inside one repository**. The spec issue `devcontainers/spec#159` ("Use devcontainer.json in subdirectories in monorepo") and `microsoft/vscode-remote-release#7548` ("Support for folders with multiple devcontainer.json files") document the pattern `.devcontainer/{name}/devcontainer.json`, with the tool prompting which one to build. That is devcontainers *with* a monorepo, as a first-class supported layout. Equally, the one-repo-one-`.devcontainer` case is the default documented everywhere: devcontainers *with* a polyrepo. Both combinations are documented and in use; therefore the choice is a 2x2, not an either/or.

**Correction to offer the user:** the real axes are (1) source layout, one repo vs many, and (2) environment provisioning, host-native toolchain managers vs containerised toolchains. Pick each independently. The only genuine interaction found: monorepo + devcontainers has a **known rough edge**: support for multiple `devcontainer.json` files under `.devcontainer/` is implemented in **GitHub Codespaces but reported as not implemented in the VS Code Dev Containers extension** (search-surfaced from the issue threads, medium confidence, see Claims). And a monorepo pushes you toward *one* container definition covering N language runtimes, which is a fatter image; a polyrepo gives N small ones. That is a sizing consequence, not a coupling.

**Practical read for this user (15 projects, Windows 11, WSL, 100 GB VPS):** the single largest, most avoidable cost is not devcontainers, it is **repo placement**. Repos on `C:\` accessed from WSL or from a WSL2-backed container pay the cross-OS penalty on every file op. Microsoft's own guidance is unambiguous and current (page updated 2026-06-02). Moving repos into the WSL2 ext4 filesystem is a bigger win, and cheaper, than adopting containers. Note the corollary: if repos live in `\\wsl$`, VS Code should attach via **WSL remote**, and Windows-native editors/tools reaching in via `\\wsl$` pay the penalty in the other direction.

**Order of operations for relocating many repos:** no published, citable guidance was found this run (see below). What the evidence *does* support as a derived order, flagged as synthesis not citation:
1. Commit/stash and push everything; verify `git status` clean per repo.
2. Enumerate worktrees (`git worktree list`) **before** moving; either set `worktree.useRelativePaths=true`, or plan a `git worktree repair` pass after.
3. Prefer `git worktree move` over a filesystem move; note it refuses on the main worktree and on linked worktrees containing submodules.
4. `git submodule absorbgitdirs` before moving, so submodule gitdirs live in `$GIT_DIR/modules` under relative paths.
5. Move (copy first, delete after verification).
6. Post-move pass: `git worktree repair` in main and in each moved worktree; `git status` + `git submodule status` per repo; add `safe.directory` entries or fix ownership; enable `core.longpaths` before the first checkout on a deep tree.
7. Re-point external absolute paths last: IDE workspace files, compose bind mounts, scripts, scheduled tasks.

## Leads worth chasing

- `containers.dev/implementors/spec` and the spec repo's release/version history: needed to state the **spec's own** version and governance status, distinct from the CLI's 0.88.0.
- `jetbrains.com/help/idea/dev-container-limitations.html`: the page that actually enumerates what JetBrains does not support; the highest-value single unread page for the editor-agnosticism question.
- Current status of `devcontainers/spec#159` and `vscode-remote-release#7548`: whether multi-`devcontainer.json` has since shipped in the VS Code extension. This is the one genuine monorepo/devcontainer interaction and it hinges on issue state.
- `microsoft/WSL` issue #4197 and discussion #10738 read directly, for defensible `/mnt/c` numbers and whether **virtiofs** (now default or opt-in?) has changed them: the boxofcables.dev piece "WSL 2 is getting faster Windows file system access" suggests active change here, so 2021-era numbers may be stale.
- Git's own docs for `core.longpaths`, `core.filemode`, `core.symlinks`, and `safe.directory` (git-config man page): would upgrade four Q3 rows from vendor-KB to primary.

- Docker Desktop WSL2 backend docs on the `docker-desktop-data` VHDX growth / `wsl --manage --set-sparse`: directly relevant to the user's disk budget, entirely unaddressed this run.
