## Q1 verdict: shared cookie vs OIDC for a first-party suite

**Verdict: OIDC (Authorization Code + PKCE) for cross-app identity; a shared-domain cookie is
not viable as the primary SSO mechanism for this suite.** The decisive constraint is not
security preference, it is heterogeneity. The stated stacks are Next.js, Svelte, Vue, Angular,
React/Vite, Phoenix LiveView, with backends in Node/TS, Go, Python and Elixir. A shared session
cookie only works if every one of those runtimes can *read and verify the same session format*.
That means either a shared session store all six frameworks can query, or a self-contained
signed token in the cookie, and the latter is just a JWT, i.e. OIDC with extra steps and no
discovery, no rotation, no logout spec.

### The cookie mechanics, verified

MDN's Set-Cookie reference (accessed 2026-08-15) is explicit on the three points that matter:

- **Domain semantics.** "If omitted, the cookie is returned only to the host that sent them
  (i.e., it becomes a 'host-only cookie'). This is more restrictive than setting the host name,
  as the cookie is not made available to subdomains of the host." And: "Multiple host/domain
  values are *not* allowed, but if a domain *is* specified, then subdomains are always
  included." So `Domain=example.dev` reaches every `*.example.dev`: that is the mechanism
  that makes shared-cookie SSO work at all, and it is all-or-nothing. You cannot scope to a
  subset of subdomains.

- **`__Host-` forbids Domain: CONFIRMED.** MDN: "Cookies with names starting with `__Host-`
  must be set with the `Secure` attribute by a secure page (HTTPS). In addition, they **must not
  have a `Domain` attribute specified**, and the `Path` attribute must be set to `/`. This
  guarantees that such cookies are only sent to the host that set them, and not to any other
  host on the domain." **This is a hard fork in the design.** The `__Host-` prefix: the
  strongest cookie hardening the platform offers, and what most modern frameworks default to
  for session cookies: is *mutually exclusive* with domain-scoped SSO. You get one or the
  other. Choosing shared-cookie SSO means every app downgrades from `__Host-` to `__Secure-`
  (or an unprefixed cookie), permanently, across the whole suite.

- **The subdomain security consequence.** MDN states this only as the *rationale* for
  `__Host-` ("only sent to the host that set them, and not to any other host on the domain")
  rather than as an explicit attack warning. Read the inverse and it is the finding: any host
  under `.example.dev` can both read a domain-scoped cookie and, critically, **set** one that
  every sibling app will accept. In a suite behind Traefik on one apex domain, a single
  compromised or sloppily-deployed app, or any stray subdomain, including one pointed
  somewhere by a dangling Cloudflare DNS record: becomes an authentication-bypass surface for
  all seven. I did **not** retrieve a spec-grade source naming the "cookie tossing" /
  session-fixation attack this run; see "could NOT find".

- **SameSite.** MDN defines `Strict`/`Lax`/`None` in terms of "the same *site* that set the
  cookie", linking to the Glossary "Site" definition which I did not fetch. Practically: apps
  under one registrable domain are same-site, so `SameSite=Lax` does not obstruct
  subdomain-to-subdomain navigation. This is a point *in favour* of the cookie approach and
  against nothing, but note it also means SameSite provides no isolation between your own
  apps.

### The OIDC side, verified

**RFC 9700, "Best Current Practice for OAuth 2.0 Security", January 2025, BCP 240**, updates
RFC 6749 / 6750 / 6819 (fetched 2026-08-15). This is the current security baseline and it
settles the flow question:

- Implicit is out: §2.1.2, "Clients SHOULD NOT use the implicit grant (response type `token`)
  or other response types issuing access tokens in the authorization response, unless access
  token injection in the authorization response is prevented and the aforementioned token
  leakage vectors are mitigated."
- Password grant is out entirely: §2.4, "The resource owner password credentials grant ...
  MUST NOT be used."
- §2.1.1: "Public clients MUST use PKCE"; "For confidential clients, the use of PKCE ... is
  RECOMMENDED."
- §2.1.2: "Clients SHOULD instead use the response type `code`."

**So yes: Authorization Code + PKCE for both the SPAs and the server-rendered apps, in 2026.**
There is no longer a "SPA gets implicit, server gets code" split. The only real difference is
where the code exchange happens and where the token lands (BFF/server-side session vs
in-browser token handling).

### The honest trade-off

| | Shared cookie on `.example.dev` | OIDC with central provider |
|---|---|---|
| Cross-language | Every stack must parse the *same* session format. Node, Go, Python, Elixir do not share one. | JWT + JWKS is the lingua franca; every stack has a validator. |
| Cookie hardening | Forfeits `__Host-` suite-wide (MDN, confirmed). | Each app keeps `__Host-` on its *own* local session. |
| Blast radius | Any subdomain can set/read the shared cookie → one compromised app authenticates as anyone, everywhere. | Compromised app holds one app's tokens; central session survives. |
| Coupling | All apps couple to one session store and one framework's serialization. | Apps couple only to a protocol + discovery document. |
| Logout | Trivially easy: delete one cookie. This is its genuine advantage. | Needs a logout spec; see Q3. |
| Machinery | Low. | Higher: provider, client registrations, redirect URIs, key rotation. |

**Nuance worth keeping.** The two are not exclusive and the best-known shape for this
situation is the hybrid: OIDC as the *federation* protocol between the central provider and
each app, and each app maintaining its own ordinary, `__Host-`-prefixed, host-only session
cookie after login. You get language-neutral SSO without granting any subdomain the ability to
forge a sibling's session. This is also the only shape that works with Phoenix LiveView's
documented model (Q2) without contortion.

**I did not find a published, authoritative "guidance document" that answers the first-party
suite question directly**: see "could NOT find". The verdict above is reasoned from primary
spec mechanics, not quoted from a guide, and should be labelled as such downstream.

### Backend JWT validation: the correct procedure

Both Go and Python paths converge on the same shape, and it is worth writing down because
getting it wrong is the classic auth bug:

1. Fetch the provider's discovery document (`/.well-known/openid-configuration`) to obtain
   `jwks_uri`: do not hardcode keys.
2. Read the token header `kid`, fetch the matching key from JWKS, **cache it**, and refresh the
   key set when an unknown `kid` appears (PyJWKClient does this automatically; go-oidc's
   `RemoteKeySet` does this automatically). This is how key rotation works, never pin a key.
3. Verify the signature, then check `iss` matches your provider exactly, `aud` matches *this
   app's* client/audience identifier, and `exp`/`nbf` against clock skew.
4. **Pin the expected algorithm.** Not retrieved from a source this run, but implied by the
   libraries requiring an `algorithms=` argument.

The `aud` check is what makes per-app tokens meaningful in a suite: seven apps, seven
audiences, so a token minted for `app3` must be rejected by `app5`.

### Phoenix LiveView: the answer to the WebSocket/redirect problem

This is the sharpest finding of the run, and it is **fully resolved by primary docs**. Phoenix
LiveView **v1.2.9** security-model guide (fetched 2026-08-15):

- **"LiveView begins its life-cycle as a regular HTTP request. Afterwards, a stateful
  connection is established."**
- **"Since a LiveView starts as a regular HTTP request, they share the authentication logic
  with regular requests through plugs."**

So the OAuth redirect problem *dissolves*. You do exactly what the brief guessed: run the
authorization-code redirect and callback in a **plain Phoenix controller** (`oidcc_plug`
provides the Plug/Phoenix integration), write the authenticated identity into the normal
session cookie, and the LiveView receives it as the `session` argument to `mount/3` when it
later mounts. There is no need for the LiveView to participate in the redirect at all: the
WebSocket is established *after* authentication has already happened over ordinary HTTP.

Three documented mechanics complete the pattern:

- **`on_mount` hooks** encapsulate the authentication check so it runs on every mount, and can
  be declared once at the router: "Instead of declaring `on_mount` on every LiveView, you can
  declare it at the router level and it will enforce it on all LiveViews under it."
- **`live_session`** groups LiveViews and controls navigation: routes inside one `live_session`
  skip the regular HTTP request on navigation, while crossing between live_sessions triggers
  full router processing. The docs say it exists for "different *authentication* requirements
  or whenever you need to change root layouts." **Consequence: put authenticated and
  unauthenticated routes in different `live_session`s**, or a client-side navigation can move
  between them without re-running the plug pipeline.
- **`mount/3` runs twice**: "invoked both on the initial HTTP mount and when LiveView is
  connected", so the auth check in `on_mount` covers both the static render and the socket.
- **The long-lived-connection gotcha, named in the docs:** when a user is logged out, "this
  change won't reflect on the LiveView part unless the user reloads the page." The documented
  fix is `live_socket_id`: broadcast a disconnect to that topic, which forces reconnection and
  re-runs `mount/3`. **This is directly load-bearing for Q3**: LiveView needs an explicit push
  to notice a central logout, and `live_socket_id` is the mechanism.

## Q3: single logout in 2026

**Spec status: all four are Final.** The OpenID Foundation publishes final specifications for
Session Management 1.0, Front-Channel Logout 1.0, Back-Channel Logout 1.0 (incorporating errata
set 1), and RP-Initiated Logout 1.0. Verified via openid.net specification pages titled
"Final: …" and the Foundation's announcement post "The OpenID Connect Logout specifications are
now Final Specifications" (accessed 2026-08-15). So there is no draft-status excuse in any
direction.

**What breaks under third-party cookie blocking: front-channel logout, structurally.**

Front-Channel Logout works by the OP rendering hidden **iframes** pointing at each RP's logout
URI. The RP's logout endpoint needs its own session cookie to arrive with that iframe request in
order to know *which* session to kill, and needs to set a clearing cookie in the response. Under
third-party cookie blocking or partitioning, that iframe is a cross-site context: the RP's
cookie is not sent, and the clearing `Set-Cookie` write is refused. Mozilla tracks this
explicitly as **Bugzilla 1660574, "OIDC Frontchannel logout will not work under 3p cookie
partitioning"**, and Microsoft Learn documents the same failure for SPAs: applications respond
to the logout request by nulling cookies but the write is forbidden, leaving session cookies
intact. Practical symptom, per those sources: log out in app A's tab, app B's tab still shows
you logged in, and existing access tokens remain valid until expiry. Microsoft frames this as "a
known limitation of the OpenID Front-Channel Logout 1.0 specification."

*(These are search-snippet reads, not full fetches: MEDIUM-HIGH confidence, two independent
publishers, consistent.)*

**One caveat that is specifically relevant to this suite:** the same sources note the workaround
if the IdP is at `login.example.dev` and the apps at `app1.example.dev`, `app2.example.dev`,
the iframe requests are *same-site* (same registrable domain), so third-party cookie blocking
does not apply. **This solo-developer suite is exactly that topology.** So front-channel logout
is one of the few deployments where it might actually still work. That is a genuine finding, but
it is a bet on same-site classification surviving future browser changes, and it re-introduces
the coupling that Q1 argues against.

**Recommendation for 2026: RP-Initiated Logout as the user-facing entry point, Back-Channel
Logout as the propagation mechanism.** Back-channel is server-to-server: the OP POSTs a logout
token directly to each RP's `backchannel_logout_uri`: so it is immune to cookie policy
entirely. The spec's own stated downsides (per the openid.net back-channel spec text): the RP's
back-channel logout URI must be reachable from the OP ("the RP cannot be behind a firewall or
NAT when used with public OPs": a non-issue here, everything is behind one Traefik), and
"session state maintained between the OP and RP over the front-channel, such as cookies and
HTML5 local storage, are not available", so **all needed state must be explicitly communicated**
meaning each RP must maintain its own server-side map from OIDC `sid`/`sub` to its local
session in order to have something to destroy when the logout token arrives.

**For the Phoenix LiveView app specifically, back-channel logout must be wired to
`live_socket_id`**: receiving the logout token kills the server-side session, but per the
LiveView docs an already-connected LiveView will not notice until reload unless you broadcast
the disconnect.

## Q4: first-party consent skipping

**Consent can be skipped for first-party clients, and every major provider exposes a flag for
it.** Retrieved via search (accessed 2026-08-15), consistent across four independent vendors:

- **Ory Hydra**: set `require_consent: false` on the client to "skip the consent screen and
  automatically grant consent to the client"; Ory shipped a changelog entry specifically titled
  "Skip showing OAuth2 consent screen for 1P apps", introducing "a flag for trusted, 1st party
  OAuth2 clients to skip the consent screen."
- **Better Auth** (OIDC Provider plugin): trusted clients with `skipConsent: true` "bypass the
  consent screen entirely, providing a seamless experience for first-party applications."
- **Duende IdentityServer**: "With first-party applications that you control, you can disable
  the consent screen with `RequireConsent = false`."
- **Auth0**: documents a first-party vs third-party application distinction governing whether
  the consent dialog appears.

So the Google-Workspace-like feel (no consent prompt hopping between your own apps) is a
supported first-class configuration, not a hack.

**One caveat worth carrying forward, from the same search:** at least one source asserts that
not showing the consent screen "will break OpenID Connect Certification." Single-source,
unverified, and almost certainly irrelevant to a solo personal suite that will never seek
certification, but flagging it because it explains why some providers make the flag awkward to
find rather than the default.

   authjs.dev, github.com/nextauthjs/next-auth releases, and the npm `next-auth` registry

   Do not accept blog claims.

   Integrity" sections are the spec-grade statement of the subdomain cookie-tossing hazard I
   could not retrieve. Also `draft-ietf-httpbis-layered-cookies` appeared in search and may now
   be the live successor draft: worth checking which is current in 2026.
3. **Exact release dates** for oidc-client-ts, angular-auth-oidc-client, oidcc, assent: use
   `registry.npmjs.org/<pkg>` and `hex.pm/api/packages/<pkg>` JSON endpoints, which return
   precise timestamps and full release history (giving cadence, not just latest version).
4. **`oidcc_plug` docs specifically**: I confirmed it exists but did not read it. It likely
   contains the exact controller/callback wiring for Phoenix, which is the concrete deliverable
   for the LiveView app.
5. **Traefik ForwardAuth as an alternative shape**: not researched at all. A single
   forward-auth middleware in front of all seven apps could centralise session validation at the
   proxy, which is a third architecture distinct from both options in Q1 and is specifically
   enabled by the "everything behind one Traefik" constraint. Potentially the highest-leverage
   unexplored option for a solo operator.
6. **Whether same-site iframe front-channel logout survives** future browser partitioning,
   the workaround in Q3 depends on registrable-domain same-site classification. Check current
   CHIPS / partitioned-cookie direction.
7. **SPA token handling: BFF pattern vs in-browser tokens.** RFC 9700 settles the flow but not
   where tokens live. `draft-ietf-oauth-browser-based-apps` is the relevant document and was not
   consulted: it likely recommends a BFF, which would interact strongly with the Traefik
   forward-auth lead.
