## Q1 verdict: the correct Compose keys for CPU/memory caps today

| Key | Works outside Swarm? | Status | Source |
|---|---|---|---|
| `cpus` (service-level, top-level under the service) | Documented as a plain service attribute with no Swarm qualifier: "define the number of (potentially virtual) CPUs to allocate to service containers. This is a fractional number. `0.000` means no limit." | Current. Not marked deprecated or legacy anywhere on the page. Spec note: "When set, `cpus` must be consistent with the `cpus` attribute in the Deploy Specification." | docs.docker.com/reference/compose-file/services/ (accessed 2026-08-15) |
| `mem_limit` | Same: "configures a limit on the amount of memory a container can allocate, set as a string expressing a byte value." | Current. "When set, `mem_limit` must be consistent with the `limits.memory` attribute in the Deploy Specification." | ditto |
| `mem_reservation` | Documented; soft reservation. "must be consistent with the `reservations.memory` attribute in the Deploy Specification." | Current | ditto |
| `memswap_limit` | Documented: "defines the amount of memory the container is allowed to swap to disk. This is a modifier attribute that only has meaning if `memory` is also set." | Current | ditto |
| `mem_swappiness` | "a value between 0 and 100, for the host kernel to swap out anonymous memory pages used by a container." | Current | ditto |
| `cpu_shares` | "defines, as integer value, a service container's relative CPU weight versus other containers." Engine docs call the equivalent flag "a soft limit" that "doesn't guarantee or reserve any specific CPU access." | Current but a *weight*, not a cap: wrong tool for capping | docs.docker.com/reference/compose-file/services/ + docs.docker.com/engine/containers/resource_constraints/ |
| `cpu_period`, `cpu_quota`, `cpuset`, `cpu_count`, `cpu_percent`, `cpu_rt_runtime`, `cpu_rt_period` | Documented, low-level CFS knobs | Current | ditto |
| `pids_limit`, `oom_kill_disable`, `oom_score_adj` | Documented; `oom_score_adj` range -1000..1000 | Current | ditto |
| `deploy.resources.limits.{cpus,memory,pids}` | **Neither page states it is ignored outside Swarm, and neither states it is honoured.** Spec wording is platform-neutral: "limits: The platform must prevent the container to allocate more." | Current part of the spec; "Deploy is an optional part of the Compose Specification" | docs.docker.com/reference/compose-file/deploy/ and compose-spec/compose-spec `deploy.md` |
| `deploy.resources.reservations.{cpus,memory,pids,devices}` | Spec: "The platform must guarantee the container can allocate at least the configured amount." No statement about what a single Docker Engine does with a CPU reservation. | Current | ditto |

**Verdict.** The old "ignored by `docker compose up`" warning is *not present* in the current Compose Specification or in Docker's Deploy Specification page: that language belonged to the retired v3 compose-file reference and I could not reproduce it from any current official page. But absence of the warning is not a positive guarantee, and no current official page positively asserts that `deploy.resources.limits` is enforced by `docker compose up` on plain Engine either. The keys that ARE unambiguously documented as ordinary service attributes, with no Swarm qualifier and no deprecation marker, are the top-level ones. **Recommendation: cap with `cpus:` and `mem_limit:` at the service level.** If you also write `deploy.resources.limits`, the spec obliges the two to agree ("must be consistent with"), so mirroring them is legal and harmless, but the service-level keys are the ones the documentation lets you rely on without inference.

Also documented, and relevant to the 2 vCPU box: `--cpus="1.5"` means the container "is guaranteed at most one and a half of the CPUs" (Engine docs), and minimum allowed `--memory` is `6m`.

**Is `pg_dump` + offsite adequate here?** The documented reason to go further is recovery-point objective, not correctness: a dump is a consistent snapshot as of dump time, so worst-case data loss equals the dump interval. For portfolio and personal-use apps with no real end users, that is a defensible loss window; WAL archiving/PITR exists to shrink it and to allow recovery to an arbitrary point after an application-level mistake. I did not retrieve an official source this run that says a dump-only strategy is inadequate at this scale, that would be an invented finding, so I am not claiming it.

**Provider/VPS block snapshots: documented hazard.** PostgreSQL 18 docs, §26.2 (page dated 2026-08-13):
- "The database server *must* be shut down in order to get a usable backup. Half-way measures such as disallowing all connections will *not* work (in part because `tar` and similar tools do not take an atomic snapshot of the state of the file system, but also because of internal buffering within the server)."
- A frozen snapshot of a running server *is* usable, with a caveat: "A backup created in this way saves the database files in a state as if the database server was not properly shut down; therefore, when you start the database server on the backed-up data, it will think the previous server instance crashed and will replay the WAL log. This is not a problem."
- The killer for multi-volume setups: "If your database is spread across multiple file systems, there might not be any way to obtain exactly-simultaneous frozen snapshots of all the volumes… the snapshots *must* be simultaneous."
- Docs also call file-system-level backups "impractical, or at least inferior to the `pg_dump` method."
- Practical read for one VPS: a provider snapshot of a single volume holding the whole cluster restores as a crash-recovered server, which is legitimate; a snapshot taken with the data directory and a WAL directory on *different* volumes is not trustworthy. And a provider snapshot lives with the provider, it is not an offsite copy in the sense that matters when the account itself is the failure.

**Offsite target pricing (weak: see gaps).** Backblaze B2 listed at $6.95/TB/30 days with free egress up to 3x average monthly storage and $0.01/GB beyond (backblaze.com/cloud-storage/pricing, snippet grade, accessed 2026-08-15). Cloudflare R2 documents GB-month billing and zero egress fees but **I did not retrieve the per-GB storage figure**, so no R2 number is stated here. Pricing is a two-source class and neither figure has a second source: treat both as unverified.

## Q3: saturation thresholds

| Signal | Threshold | Source |
|---|---|---|
| `/proc/pressure/{cpu,memory,io}`: "some" line | "the share of time in which at least some tasks are stalled on a given resource" | docs.kernel.org/accounting/psi.html (documents kernel 7.2.0-rc7), accessed 2026-08-15 |
| Same: "full" line | "the share of time in which all non-idle tasks are stalled on a given resource simultaneously"; kernel doc calls this wasted CPU cycles and the workload "thrashing", with "severe impact on performance" when sustained | ditto |
| Fields | `avg10`, `avg60`, `avg300` as percentage ratios over 10/60/300s windows; `total` in **microseconds** of absolute stall time | ditto |
| Published "trouble" threshold | **None.** The kernel documentation gives no universal threshold. It gives a trigger mechanism instead: `<some\|full> <stall amount in us> <time window in us>`, with worked examples of 150 ms partial memory stall per 1 s window and 50 ms full IO stall per 1 s window | ditto |
| Per-container pressure | Under cgroup v2 the same data is exposed per-cgroup as `cpu.pressure`, `memory.pressure`, `io.pressure`, identical format: this is the cgroup-v2-specific capability an operator on Ubuntu 24.04 should use to attribute pressure to one app rather than the box | ditto |
| Load average per core | **Not sourced this run.** No primary threshold retrieved | n/a |
| OOM killer | Docker "attempts to mitigate these risks by adjusting the OOM priority on the Docker daemon so that it's less likely to be killed than other processes"; per-container `oom_score_adj` (-1000..1000) and `oom_kill_disable` are exposed as Compose keys | docs.docker.com/engine/containers/resource_constraints/ + compose services reference |
| Swap under a memory limit | `--memory-swap` set alongside `--memory` is **total memory + swap**, not swap alone: "if `--memory="300m"` and `--memory-swap="1g"`, the container can use 300m of memory and 700m swap." Setting both to the same value prevents swap entirely. `--memory-swappiness` 0 "turns off anonymous page swapping", 100 makes all anonymous pages swappable. Docs advise being "mindful when configuring swap on your Docker hosts. Swap is slower than memory but can provide a buffer," and note swap limits may require kernel support | docs.docker.com/engine/containers/resource_constraints/ |
