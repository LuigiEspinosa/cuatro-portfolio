## Q1: zero-downtime on Compose + self-hosted PaaS comparison

### 1a. Plain Docker Compose — PARTIALLY ANSWERED, primary confirmation NOT obtained

I fetched the Compose Specification `deploy` page (docs.docker.com/reference/compose-file/deploy/,
accessed 2026-08-15). It **documents** `update_config`, `rollback_config` and `order`
(`start-first` / `stop-first`), but the page carries **no statement about whether `docker compose`
honours them or whether they are Swarm-only**, and **no version stamp or date on the page itself**.
The only support caveat present is about job mode: *"Options like `max-concurrent` for controlling
concurrency are supported only via the CLI and are not available in Compose."*

That means the load-bearing question — *does `docker compose up` do a stop-then-start and drop
connections?* — is **NOT confirmed from primary Docker documentation this run**. Search-tier sources
(blogs, the `wowu/docker-rollout` README) uniformly assert that `docker compose up` stops the old
container before starting the new one, giving a 10–20 s gap, and that Compose has no native rolling
update outside Swarm. That is consistent across sources but it is secondary evidence and several of
the hits are of content-farm quality. **Do not ship a recommendation on this until it is confirmed
against the `docker compose up` CLI reference and the Compose changelog.**

Pattern that practitioners converge on (secondary, unverified against primary): `docker-rollout`
(github.com/wowu/docker-rollout) — a `docker compose` CLI plugin that scales a service to 2x, waits
for the new containers' healthchecks, then removes the old ones. This is the blue-green-via-scale
pattern and depends on (i) a real `healthcheck` in the Compose file and (ii) a reverse proxy that
discovers the new container and drains the old. Traefik's Docker provider + healthcheck-gated
routing is the mechanism that makes it work; I did not verify Traefik's draining semantics this run.

## Q2 verdict: does Caddy still need a custom build for Cloudflare DNS? Does Traefik not?

**Caddy: YES, the custom build is still required. Round 1's claim survives.** Caddy's own module
page for `dns.providers.cloudflare` (caddyserver.com/docs/modules/dns.providers.cloudflare, accessed
2026-08-15) states verbatim: *"This module does not come with Caddy. It can be added by using xcaddy
or our download page."* The page also flags non-standard modules as *"developed by the community and
are not officially endorsed or maintained by the Caddy project."* There is **no mention on that page
of an official Cloudflare-enabled Docker image, of `caddy add-package`, or of dynamic module
loading**. So the escape hatches the brief asked about do not appear in Caddy's own documentation
for this module. Caveat: the page carries no Caddy version stamp, and absence of `add-package` from
*this* page is not proof it does not exist elsewhere in Caddy's docs — but the module page is where
a supported no-rebuild path would be advertised, and it is not there.

**Traefik: the DNS providers are compiled in, no plugin install.** Traefik's own certificate-resolver
docs (doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/,
documentation for **v3.7**, accessed 2026-08-15) state: *"Traefik relies internally on Lego for ACME.
You can find the list of all the supported DNS providers in their documentation with instructions
about which environment variables need to be setup."* Lego is a Go library linked into the Traefik
binary; the docs describe configuration by **environment variables only** and describe **no build,
plugin-install or image-rebuild step** for DNS providers. Weaker than I wanted: the page does not
enumerate Cloudflare or its `CF_DNS_API_TOKEN` variables inline (it defers to Lego's docs), so this
is an inference from the absence of any install step plus the compiled-in nature of Lego, not a
literal quotation naming Cloudflare.

**Net:** the asymmetry round 1 identified is real and is confirmed on the Caddy side by Caddy's own
words. Traefik's side is strongly implied by Traefik's own words but would be nailed shut by one
more fetch of the Lego provider page or Traefik's Cloudflare example.

## Q3: Cloudflare SSL modes, Origin CA, ACME behind the proxy, WebSockets

**(a) Modes.** Cloudflare documents **five** modes, not four:
**Off (no encryption)**, **Flexible**, **Full**, **Full (strict)**, and **Strict (SSL-Only Origin
Pull)** (developers.cloudflare.com/ssl/origin-configuration/ssl-modes/, accessed 2026-08-15).

**Redirect loop.** From Cloudflare's troubleshooting page
(developers.cloudflare.com/ssl/troubleshooting/too-many-redirects/, accessed 2026-08-15), the loop is
**bidirectional, not unique to one mode**:
- **Flexible**: *"Cloudflare sends unencrypted requests to your origin server over HTTP. Redirect
  loops will occur if your origin server automatically redirects all HTTP requests to HTTPS."*
  This is the common case, and it is exactly what a Traefik/Caddy box doing automatic HTTP→HTTPS
  redirect will trigger.
- **Full / Full (strict)**: *"Cloudflare sends encrypted requests to your origin server over HTTPS.
  Redirect loops will occur if your origin server automatically redirects all HTTPS requests to
  HTTP."*
- **Always Use HTTPS** compounds it: Cloudflare rewrites HTTP→HTTPS at the edge, the origin bounces
  it back to HTTP, and the cycle repeats. Fix is to remove the origin-side redirect or disable
  Always Use HTTPS.

**(b) Origin CA.** From developers.cloudflare.com/ssl/origin-configuration/origin-ca/ (accessed
2026-08-15): Origin CA certificates are **not publicly trusted** — *"These certificates only encrypt
traffic between Cloudflare and your origin server, not traffic from client browsers to your origin."*
The documented workflow ends with *"select Full (strict)"*. Operationally important: *"Cloudflare
does not currently send expiration notifications for origin CA certificates"*, so renewal is entirely
the operator's problem.
**Validity period: NOT OBTAINED.** The page instructs the user to *"Choose a Certificate Validity
period"* without enumerating the options. I therefore give **no number** for Origin CA lifetime.
Consequently the treadmill question is only **half** answered: because Origin CA certs are issued by
Cloudflare's private CA and not by a public CA, they are **outside the CA/Browser Forum lifetime
reductions that drive Let's Encrypt to 64 days (Feb 2027) and 45 days (Feb 2028)** — that much
follows from them not being publicly trusted. But without the documented validity options I cannot
state how long they actually last, and it only works for hostnames that stay proxied (orange-cloud);
any hostname you grey-cloud needs a publicly trusted cert again.

**(c) HTTP-01 while orange-clouded: NOT ANSWERED.** Budget exhausted before I could reach
Cloudflare's ACME/validation documentation. Do not assume either way — this interacts directly with
whether Traefik's DNS-01 is a requirement or merely a convenience, and it deserves a round-3 slot.

**(d) WebSockets.** From developers.cloudflare.com/network/websockets/ (accessed 2026-08-15):
*"WebSockets are supported on all Cloudflare plans."* There **is** an idle timeout but Cloudflare
**publishes no number**: *"Cloudflare will close a WebSocket connection when no data is transmitted
in either direction for a period of time."* Enterprise customers can request custom timeouts.
Cloudflare's own remedy is a heartbeat: *"To keep long-lived connections alive during periods of
inactivity, implement a client-side heartbeat (ping/pong) mechanism."* Also documented:
**WebSockets are incompatible with Argo Smart Routing.** The widely repeated "100 seconds" figure
does **not** appear in Cloudflare's documentation and I give no number for it.

## Q4: LiveView default heartbeat interval

**30 000 ms (30 seconds).** From Phoenix's own source, `assets/js/phoenix/socket.js` on `main`
(raw.githubusercontent.com/phoenixframework/phoenix, accessed 2026-08-15):

```js
this.heartbeatIntervalMs = opts.heartbeatIntervalMs || 30000
```

Same file: `this.timeout = opts.timeout || DEFAULT_TIMEOUT` and reconnect backoff
`[10, 50, 100, 150, 200, 250, 500, 1000, 2000][tries - 1] || 5000`. The published JS docs at
phoenix.hexdocs.pm/js/index.html are for **Phoenix 1.8.11** and do **not** print the numeric default,
which is why the source is the citation. LiveView's client rides this same `Socket`, so unless
`heartbeatIntervalMs` is overridden the LiveView socket sends traffic every 30 s.

**Consequence:** any proxy or edge idle timeout longer than 30 s will never fire on an otherwise-idle
LiveView connection, because the heartbeat is itself traffic. Cloudflare's unpublished idle timeout
is the only unknown, and Cloudflare's own advice is precisely the heartbeat Phoenix already ships.
This de-risks the Phoenix app on the shared box considerably — **provided** nothing in the chain sets
a sub-30 s idle timeout.
