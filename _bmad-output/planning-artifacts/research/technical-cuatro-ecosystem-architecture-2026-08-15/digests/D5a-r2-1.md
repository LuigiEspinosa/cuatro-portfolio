## Q2: Pocket ID verified, is it a full OIDC provider, and is it passkey-only?

**Version: v2.13.0, released 2026-08-07.** Cadence over the last four months is tight and regular: v2.13.0 (08-07), v2.12.0 (07-29), v2.11.0 (07-13), v2.10.0 (07-10), v2.9.0 (06-16), v2.8.0 (05-31), v2.7.0 (05-11), v2.6.2/v2.6.1 (04-21), v2.6.0 (04-19). Roughly every 1–3 weeks. v2.12.0 was flagged security-critical with an immediate-update recommendation, so this is a project you must keep patched, not set and forget.

**Language: round 1's Go question, answered.** The installation docs list build-from-source prerequisites of **Go >= 1.26** and **Node.js >= 22**. Combined with the `.goreleaser.yaml` in the repo root, that reads as a Go backend with a Node-built (SvelteKit) frontend compiled into the binary. Confirmed enough to rely on; the Node requirement is build-time tooling for the frontend, not a runtime daemon.

**Database: SQLite is the default, Postgres is the option.** Docs: *"The database provider is automatically inferred from the connection string. By default, Pocket ID uses SQLite with a database file located at `data/pocket-id.db`."* Single variable, `DB_CONNECTION_STRING`. Both SQLite and PostgreSQL are supported. **Round 1's finding holds: no dedicated Postgres needed.** This is the single largest resource advantage over Logto/Keycloak/authentik/ZITADEL on a 2-vCPU box.

**Stated resource needs: none.** Neither the installation page nor the environment-variables reference states any CPU, RAM, disk, or network requirement. That is silence, not a claim of being light, though a Go binary plus a SQLite file is structurally cheaper than a JVM or a Node app plus a Postgres server.

**Is it a full OIDC provider? Yes, and it is certified.** The repository describes Pocket ID as an **"OpenID Connect Certified™ and OAuth 2.0 provider."** OIDC certification is a meaningful, verifiable claim: it is not marketing adjective. I could **not** individually confirm from primary docs this run: Authorization Code + PKCE specifically, refresh-token issuance, the standard-claims set, or any cap on the number of registered clients. The certification implies discovery, authorization code flow and standard claims, but I am flagging those as inferred rather than read. **Nothing suggested a client-count limit; nothing stated one either.**

**Is it passkey-only? Essentially yes: there is no password login, and that is the honest headline.** The repository states plainly: **"Only supports passkey authentication, which means you don't need a password."** The installation docs confirm it "uses the WebAuthn API."

But the picture is more usable than "passkey or nothing", and the nuance matters for the decision. The environment-variable reference exposes:
- `WEBAUTHN_USER_VERIFICATION`, `WEBAUTHN_ALLOW_SYNCED_PASSKEYS` (cloud-backed passkey sync: this is the recovery story), `WEBAUTHN_AUTHENTICATOR_ATTACHMENT`
- `EMAIL_ONE_TIME_ACCESS_AS_UNAUTHENTICATED_ENABLED`: **email one-time login codes as an alternative to passkeys**
- `LDAP_ENABLED`: LDAP authentication integration
- SCIM provisioning is referenced in the configuration section

So: **no username+password anywhere**, but a passkey-primary flow with an email one-time-code fallback and optional LDAP. There are **no OIDC-federation login variables**: Pocket ID does not appear to act as a broker in front of Google/GitHub. That is the real constraint to weigh: for a solo developer's portfolio estate, passkeys plus email codes is fine and arguably better than passwords. For anything that later needs "sign in with Google" or a password for a non-passkey-capable visitor, Pocket ID does not do it.

## Q4: Supabase password-hash export, does consolidation force a password reset?

**No. It does not force a reset. Supabase Auth uses bcrypt, and bcrypt hashes port.**

**Supabase's own position.** Supabase documentation and its official GitHub discussions establish that all auth data ("including emails and hashed passwords") lives in the `auth` schema in your own Postgres database, is queryable with `select * from auth.users`, and comes out in a `pg_dump` taken against the project connection string. Supabase publishes a troubleshooting guide, *"Migrating Auth Users Between Supabase Projects"*, which states you can migrate the whole `auth` schema including users and their hashed passwords, with the explicit consequence that **users do not need to reset or recreate their passwords after migration**. `encrypted_password` is a real, readable column and it is exportable.

**Two important caveats on that.** First, the Supabase-to-Supabase path documents contacting **Supabase Support** to get `auth.users` exported *with password hashes included*: i.e. the platform-blessed route involves a human, not a self-serve button. Second, and this is the honest gap: **Supabase documents migrating *in* (from Auth0, from Firebase Auth) and migrating *between its own projects*. I found no Supabase-authored guide for migrating *out* to a third-party provider.** The data is yours and it is accessible; the *path* is undocumented by the vendor. That is a legitimate finding and it is the shape of the answer to "does Supabase document a supported path out", **no, it does not.**

**Does the target side document a bcrypt import?** Yes, at least one does, in detail. **Better Auth ships an official `supabase-migration-guide`** in its documentation repo. It reads `encrypted_password` straight out of `auth.users` (alongside `email_confirmed_at`, `is_super_admin`, `raw_user_meta_data`, `raw_app_meta_data`, `phone`, and joined `auth.identities`), states plainly *"Since Supabase uses `bcrypt`, you'll need to configure Better Auth to use bcrypt for password verification"*, maps the column across with `password: user.encrypted_password || null`, and wires a verifier:

```js
verify: async ({ hash, password }) => {
  return await bcrypt.compare(password, hash);
}
```

That is a **direct hash-verification path with no password reset**: the migrated bcrypt hash is accepted as-is and checked on next login.

**What this means for the decision.** The hash algorithm is **bcrypt**, confirmed by a target vendor that had to build against it. Bcrypt is the most portable password hash there is: any target that lets you supply a custom verifier, or that supports bcrypt-format hash import, takes these users without a reset. The constraint is not the data, it is whether your chosen target accepts foreign hashes. **And here is the sting for the current front-runner: Pocket ID has no password login at all, so migrating the Supabase app's users into Pocket ID means every existing user enrolls a passkey regardless.** The bcrypt portability finding rescues a move to Better Auth, Clerk, Kinde, Stytch or ZITADEL. It does nothing for a passkey-only target.

Caveat I am flagging rather than hiding: with **no real end users yet**, this entire question is currently theoretical. It matters for the pattern, not for today's data.

## Leads worth chasing

- **Resolve the Logto date conflict.** Two primary reads disagreed by ~2 years on release dates while agreeing on the v1.4x series. A single fetch of blog.logto.io/changelogs or the container-registry tag list would settle it. Low cost, and it decides whether Logto's monthly cadence claim is current.
- **Ory Hydra was never researched**: budget ran out. Hydra (the OAuth2/OIDC server) is the piece that actually matters for this estate; Kratos is identity management. The Kratos cadence finding does not transfer to Hydra. This is the biggest remaining hole in Q1.
- **Casdoor's DB requirement and runtime** are unestablished. Casdoor ships as a Go binary and the release velocity is remarkable, but whether it needs MySQL/Postgres or can run on SQLite is exactly the question that decided Pocket ID's favour. One fetch of casdoor.org's deployment docs.
- **Confirm Pocket ID's PKCE and refresh-token support** from `pocket-id.org/docs` (OIDC client configuration page) before committing seven clients to it. OIDC certification makes this near-certain but it is currently inferred.
- **Ask Stytch directly** whether project/application count is capped. The pricing page's silence is the only honest reading, and it is the one gap that could disqualify them late.
- **Clerk's "MRU" is not "MAU."** Worth reading Clerk's definition: a 50,000 *per app* allowance is unusually generous and the definition is where the catch would live.
- **ZITADEL as the hedge**: from round 1 it needs Postgres and an h2c proxy but publishes no CPU/RAM minimum, and unlike Pocket ID it supports passwords, making it the natural target for the bcrypt import path if the Supabase app's users must keep their passwords.
