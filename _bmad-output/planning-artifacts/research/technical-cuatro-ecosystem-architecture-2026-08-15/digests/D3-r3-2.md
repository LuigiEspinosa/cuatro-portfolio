## Q1 verdict: what `docker compose up` actually does, and what `deploy.update_config` does outside Swarm

**Verdict in one line: plain `docker compose up` stops the old container before starting the new one, so it drops connections for the recreate window; and Docker does not document whether `deploy.update_config.order: start-first` has any effect outside Swarm — the vendor is silent, so it must not be relied on.**

Three findings, each traced to a Docker-published page:

**1. Default behaviour on a changed service is stop-then-recreate.** The `docker compose up` CLI reference states verbatim: *"If there are existing containers for a service, and the service's configuration or image was changed after the container's creation, `docker compose up` picks up the changes by stopping and recreating the containers (preserving mounted volumes)."* That is stop-first by construction. The same page contains **no mention** of zero-downtime, rolling update, or start-first anywhere in its option set. Practical consequence for the 12-app single-VPS setup: between the stop and the new container passing its healthcheck, Traefik has no healthy backend and returns 502/503.

**2. `update_config.order` is documented, but with no runtime scoping whatsoever.** Docker's Compose-file `deploy` reference documents `order` verbatim as: *"Order of operations during updates. One of `stop-first` (old task is stopped before starting new one), or `start-first` (new task is started first, and the running tasks briefly overlap) (default `stop-first`)."* It says `deploy` is *"an optional part of the Compose Specification"*. It does **not** say which runtimes implement `update_config`; it does not mention Swarm vs. `docker compose up` in that context at all. The upstream `compose-spec/compose-spec` `deploy.md` — the normative document Docker's page renders — is identically silent: it carries the same `update_config` text and only notes that *"Default and available values are platform specific"* for `endpoint_mode`. **This is the answer to the question as asked: the vendor does not document it.** The nearest thing to a vendor statement is the general escape hatch, that deploy support is an optional aspect of the spec and, if not implemented, the deploy section is ignored while the Compose file remains valid — which tells you it *may* be ignored, not that Compose specifically ignores it.

**3. `--wait` is a CLI-blocking guarantee, not a traffic guarantee.** Verbatim: `--wait` = *"Wait for services to be running|healthy. Implies detached mode."*; `--wait-timeout` = *"Maximum duration in seconds to wait for the project to be running|healthy"*. This makes the *command* block until healthchecks pass, which is genuinely useful in a deploy script (it turns "deployed" into "deployed and healthy" and gives a non-zero exit on failure). It does nothing about the gap, because the gap has already happened by then — the old container was stopped first.

Also relevant and sourced from docs.docker.com: `docker stack deploy` (the Swarm path where `update_config` unambiguously *is* honoured) uses the legacy Compose file **version 3** format used by Compose V1, and the current Compose Specification format is **not compatible** with `docker stack deploy`. So "just switch to Swarm to get `start-first`" is not a free move — it is a file-format migration for all 12 apps.

**Engineering conclusion for this decision:** treat `deploy:` as inert under `docker compose up`. Get zero-downtime from an external mechanism (Q2) or a PaaS layer (Q3), not from a Compose key.

## Q2: the scale-then-drain pattern

`wowu/docker-rollout` **exists, is real, and is maintained** — though at low release frequency.

- **Latest release v0.14, published 2026-07-12** (one month before access date). Repo shows MIT licence, ~3.3k stars, 102 forks, **4 open issues**, and **no archived / unmaintained notice**. v0.14's notes address *"rollout failing when existing containers are in exited state"* and add end-to-end testing.
- **Release history from the atom feed** (authoritative timestamps): v0.5 & v0.6 2023-10-13, v0.7 2023-12-09, v0.8 2024-03-04, v0.9 2024-04-03, v0.10 2025-03-28, v0.11 & v0.12 2025-05-29, v0.13 2025-07-25, v0.14 2026-07-12. **Trailing 12 months (Aug 2025 – Aug 2026): one release.** Read over time this is a small, slow, stable tool — not abandoned, but not actively evolving either. Do not expect fast turnaround on an issue.
- **Mechanism:** it is a Docker CLI plugin. It scales the service to double its instances, waits for the new containers to pass **Docker healthchecks**, then removes the old containers. An optional pre-stop hook drains connections before removal.
- **Requirements:** real Docker healthchecks (in the image or the compose file) **and** a reverse proxy doing service discovery — Traefik or nginx-proxy are the ones named.
- **Stated limitation, verbatim:** *"Your service cannot have `container_name` and `ports` defined in `docker-compose.yml`, as it's not possible to run multiple containers with the same name or port mapping. Use a proxy as described below."*

That limitation is the load-bearing fact for this decision. **It does not work with published host ports — only behind a proxy.** For the planned architecture (single Traefik front door, apps on an internal network with no host port publishing) that constraint is already satisfied and costs nothing. It also implies dropping `container_name` from every service you want to roll, and that every rollable app needs a genuine healthcheck endpoint — the healthcheck stops being cosmetic and becomes the correctness boundary.

**Alternatives with the same mechanism: not researched this run** (budget). See "Leads worth chasing".

## Which decision comes first — PaaS or proxy?

**The PaaS decision comes first, and it makes the proxy choice downstream — but only if you pick a PaaS that owns the proxy, which all four of these do.**

Every tool in the field ships and manages its own front door: Coolify drives Traefik, CapRover drives nginx on Swarm, Kamal drives kamal-proxy. Adopting any of them means you no longer author a Traefik config — the PaaS generates it from labels or its own config model, and hand-editing it fights the tool. So the round-1/round-2 work on Traefik v3.7 + Cloudflare DNS-01 via env vars is either preserved or discarded depending purely on which PaaS you pick. That is the definition of downstream.

Two consequences worth stating plainly:

1. **Coolify is the only option in this field that preserves the established proxy decision.** It drives Traefik, and v4.3.0 (2026-08-12) explicitly *"added Traefik 3.7 support"* — the exact version already settled on. Picking Coolify keeps the DNS-01 research alive. Picking CapRover discards it entirely (nginx + Swarm), and picking Kamal discards it too (kamal-proxy).
2. **CapRover carries a structural cost the others don't:** it runs on Docker Swarm, and Docker's own docs state `docker stack deploy` takes the legacy Compose **v3** format and is not compatible with the current Compose Specification. Twelve Compose apps would need format migration. Kubernetes was ruled out; Swarm is not Kubernetes, but it is the same class of "your compose files are no longer your compose files" tax.

**Does a solo operator on 2 vCPU / 8 GB gain or lose by adding this layer?** I will not answer with a resource number — see below, I have no verifiable one and will not invent one. What I *can* say from sourced structure:

- **The strongest argument against Coolify specifically is its release cadence, not its footprint.** Five releases in 3.5 weeks (v4.2.0 → v4.3.3) means an upgrade treadmill on a machine you are supposed to be ignoring. For a portfolio box where brief downtime is tolerable, that churn is a real recurring cost paid in attention.
- **Kamal is structurally the lightest fit for this shape of problem**, because it is a deploy tool run from your laptop rather than a server-resident control plane — the only thing resident on the VPS is kamal-proxy. Its quarterly cadence is a feature here, not a warning. Its cost is that it discards the Traefik work and is opinionated toward one-app-per-deploy-config.
- **The honest null option:** `docker-rollout` (Q2) + your own Traefik gets you the same zero-downtime property as any of these, on the stack already designed, with one 3.3k-star shell plugin as the entire new dependency. It requires you to have healthchecks and no published host ports — both of which the planned architecture already gives you. The PaaS layer's real value is not zero-downtime (you can have that without it); it's the web UI, git-push deploys, backups and secrets management. **Decide whether you want those, and only then does the proxy question re-open.**

## Leads worth chasing

- **Alternatives to docker-rollout with the same scale-then-drain mechanism** — not searched (budget). Worth one query before committing to a single 1-release-per-year dependency.
- **Dokku's default single-host router.** Only the k3s/Traefik path was evidenced. Verify the non-k3s default directly at dokku.com before using "bundled proxy" as a selection criterion.
- **Direct fetch of the three PaaS zero-downtime doc pages** (coolify.io rolling-updates, caprover.com/docs/zero-downtime.html, dokku.com zero-downtime-deploys). All three are official-domain and were read through search extraction rather than a direct fetch; the CapRover volume caveat in particular is decision-relevant enough to deserve a direct read.
- **`docker/compose` issue tracker or source** for a maintainer-level statement on whether `update_config` is parsed-and-ignored or silently dropped. The docs will not tell you; the code or an issue thread will. This would upgrade the Q1 finding from "undocumented" to "known".
- **Whether Traefik's healthcheck/service-discovery settle time compounds the recreate gap** under plain `up` — the gap is not just container start time, it is start + healthcheck + proxy rediscovery.
- **Coolify's upgrade mechanics and rollback story**, given 5 releases in 3.5 weeks. Cadence that high on an unattended box is the main risk of choosing it.

## Looked for and could NOT find

- **A Docker statement — anywhere on docs.docker.com or in compose-spec — saying whether `deploy.update_config` is or is not honoured by `docker compose up` on plain Docker Engine.** Both the rendered Docker page and the upstream normative `deploy.md` document the key with no runtime scoping at all. **The vendor does not document this.** This is a real finding, not a search failure: I read both authoritative documents directly. The only adjacent statement is the generic "deploy support is optional and may be ignored".
- **Any Compose Specification version number or last-updated date** on either the Docker-rendered `deploy` page or the upstream `deploy.md`. The spec is a living, unversioned document; claims above are stamped to access date 2026-08-15 rather than a spec version, because no spec version is published on the pages.
- **Any resource-overhead figure (RAM, CPU, disk) for Coolify, Dokku, CapRover or Kamal from a primary source.** Not reported. Consistent with the prior researcher's refusal, and I did not spend budget re-entering that search tier — the honest position is that these projects do not publish measured footprints, and everything that claims to is downstream of content farms. **The 2 vCPU / 8 GB sizing question remains open and should be settled by measuring on the actual box, not by research.**
- **Whether Coolify supports Caddy as an alternative proxy.** Only Traefik was evidenced this run.
