# D2 round 3 — token contract buildability: Tailwind v4, Phoenix, Angular

Accessed: 2026-08-15. Web research only, behind research firewall.

## Q1 verdict: external CSS custom properties and Tailwind v4 utilities — **CONFIRMED**

The previous researcher's inference **holds**, and it is now confirmed against Tailwind's own
current documentation rather than reasoned from the `@theme` / `:root` distinction.

Tailwind's theme docs state plainly: *"Theme variables aren't just CSS variables — they also
instruct Tailwind to create new utility classes that you can use in your HTML."* And the explicit
guidance: *"Use `@theme` when you want a design token to map directly to a utility class, and use
`:root` for defining regular CSS variables that shouldn't have corresponding utility classes."*

So: **a plain external CSS file that defines custom properties under `:root` supplies variables and
generates ZERO utility classes.** `bg-brand` will not exist. The values are usable only via
`var(--token-brand)` in hand-written CSS or via arbitrary-value syntax.

**But the inference's implied conclusion — "every value must be restated in `@theme`" — is too
pessimistic, and this is the important correction.** Two documented mechanisms make the token
contract cheap to wire:

**(a) `@theme` blocks can live in a separate, importable, publishable file.** This is documented
explicitly, with a monorepo/NPM example:

```css
/* ./packages/brand/theme.css */
@theme {
  --*: initial;
  --spacing: 4px;
  --color-lagoon: oklch(0.72 0.11 221.19);
}
```
```css
/* ./packages/admin/app.css */
@import "tailwindcss";
@import "../brand/theme.css";
```

The docs say: *"Since theme variables are defined in CSS, sharing them across projects is just a
matter of throwing them into their own CSS file that you can import in each project… You can put
shared theme variables like this in their own package in monorepo setups or even publish them to
NPM and import them just like any other third-party CSS files."*

**Ordering matters: `@import "tailwindcss"` comes first, then the theme file.** `--*: initial` in
the shared file wipes Tailwind's default theme namespace — include it only if you intend a
closed palette.

**(b) `@theme inline` lets `@theme` reference an existing custom property — this is the adapter
pattern, and `inline` is mandatory for runtime theming.** Documented form:

```css
@theme inline {
  --font-sans: var(--font-inter);
}
```

Docs: *"Using the `inline` option, the utility class will use the theme variable value instead of
referencing the actual theme variable"* — emitting `.font-sans { font-family: var(--font-inter); }`.
And the warning: *"Without using `inline`, your utility classes might resolve to unexpected values
because of how variables are resolved in CSS."* The documented failure is that a non-inline
`--font-sans: var(--font-inter)` resolves **where `--font-sans` is defined** (`:root`), so a
`--font-inter` redefined deeper in the tree — which is exactly how a `[data-theme="dark"]` or
per-section token override works — **is ignored**.

**Buildable contract this implies (reasoned from the above, not retrieved as a recommendation):**
publish two artifacts from Style Dictionary. (1) `tokens.css` — plain `:root` / `[data-theme=…]`
custom properties, universally consumable by Svelte, Vue, Angular, Phoenix, and any non-Tailwind
consumer. (2) `tailwind.css` — a thin generated adapter, `@import "./tokens.css"; @theme inline {
--color-brand: var(--token-color-brand); … }`, one line per token that should mint a utility. The
adapter is mechanical and generatable, so "restating every value" is a build-step cost, not an
authoring cost. `inline` is what preserves runtime dark-mode swapping through the utility.

**Not documented anywhere I could find:** any mechanism for `@theme` to auto-adopt variables
already defined in `:root`. There is no "scan `:root` and generate utilities" escape hatch. The
adapter file is required.

## Q2 verdict: the concrete Phoenix consumption path

**Vendoring a CSS file into `assets/` is the only path that works cleanly. There is no
`node_modules` and no `package.json` by default, so the npm-dependency option is off the table
without opting into Node.** URL `@import` is not viable for a compiled Tailwind pipeline.

Phoenix's own asset docs: *"From Phoenix v1.7, new applications use esbuild to prepare assets via
the Elixir esbuild wrapper, and tailwindcss via the Elixir tailwindcss wrapper. The direct
integration with esbuild and tailwind means that newly generated applications do not have
dependencies on Node.js or an external build system."* Both are Hex packages driving standalone
downloaded binaries. CSS lives under `assets/`, JS at `assets/js/app.js`, output to
`priv/static/assets/`.

npm is possible but opt-in and documented as a per-package escape: *"Call `npm install topbar
--prefix assets`, which will create `package.json` and `package-lock.json` inside your assets
directory."* That drags Node back into the build for every deploy and CI runner — a real cost for
a solo dev maintaining ~15 apps, and the reason vendoring wins here.

**Phoenix 1.8.0's own precedent is vendoring.** The installer template directory
`installer/templates/phx_assets/` at tag `v1.8.0` contains `app.css`, `app.js`, and vendored
**`daisyui.js` (251,614 bytes)** and **`daisyui-theme.js` (46,759 bytes)** — the daisyUI plugin
itself is committed into the app as plain JS, loaded via Tailwind v4's `@plugin` directive from a
relative path. Phoenix's `app.css` carries `curl` commands in comments for upgrading those vendored
files from daisyUI's GitHub releases. **A vendored `tokens.css` copied into `assets/css/` and
`@import`ed is the identical, framework-sanctioned pattern** — same mechanism, one more file.

`app.css` (Phoenix v1.8.0 template, 4,131 bytes) is CSS-first Tailwind v4: `@import "tailwindcss"`,
`@source` directives pointing at the app's `.ex`/`.heex`/`.js` files, `@plugin` for heroicons and
daisyUI (**daisyUI loaded with `themes: false`**), then **two `daisyUI theme` plugin blocks
declaring a light theme (default) and a dark theme (`prefers dark`) entirely in oklch values**,
plus LiveView `@custom-variant` rules for loading states and a dark-mode data-attribute variant.

**daisyUI theming is CSS-custom-property based**, which is what makes the token contract land.
Themes are declared via `@plugin "daisyui/theme" { name: "mytheme"; default: true;
--color-base-100: oklch(98% 0.02 240); … }`, with semantic variables `--color-primary`,
`--color-secondary`, `--color-accent`, `--color-info/success/warning/error`, plus
`--radius-selector`, `--radius-field`, `--radius-box`, `--border`, `--depth`, `--noise`. daisyUI's
docs show these set to literal oklch values; I found **no documentation confirming a `var()`
reference is accepted inside a `@plugin "daisyui/theme"` block** — see "could not find". The
safe, documented alternative is to skip the plugin block and declare the theme as
`[data-theme="mytheme"] { --color-primary: var(--token-brand); … }`, which daisyUI documents for
CDN usage and which is ordinary CSS cascade.

## Q3 verdict: the concrete Angular consumption path

**Trivial. Both routes work; global stylesheet via `angular.json` is the canonical one, and
component style encapsulation is a non-issue for custom properties.**

`angular.json`'s build target takes a `styles` array — *"An array of CSS files to add to the global
context of the project. Angular CLI supports CSS imports and all major CSS preprocessors."* Entries
are path strings or objects with `input` / `inject` / `bundleName`. Adding the token file to that
array, or `@import`ing it from the project's global stylesheet, are equivalent; the array is the
more explicit and the one the docs describe.

**Encapsulation does not block it.** Angular defaults to `ViewEncapsulation.Emulated`, implemented
by generating a unique HTML attribute per component and injecting it into the component's own CSS
selectors. The docs state directly: *"global styles defined outside of a component may still affect
elements inside a component with emulated encapsulation."* Emulated encapsulation stops a
component's styles leaking **out**; it does not shield the component from global CSS. CSS custom
properties on `:root` inherit down the DOM by the normal cascade and are readable inside components.
(The docs do not name custom properties specifically — that last step is CSS-spec inheritance,
labelled as reasoning, not retrieval.)

## Leads worth chasing

- **Verbatim Phoenix v1.8.0 `app.css`.** The fetch returned a summary, not the file. Read it byte-for-byte before authoring the Phoenix adapter — exact `@plugin` paths, whether the dark variant keys off `data-theme` or a `.dark` class, and the pinned daisyUI version in the upgrade comment all matter and all were paraphrased here.
- **Does `@plugin "daisyui/theme" { --color-primary: var(--token-brand); }` accept a `var()` reference?** Undocumented either way. If it does, Phoenix consumption is one adapter block. If it does not, use `[data-theme="x"] { --color-primary: var(--token-brand); }` plain CSS instead. Cheap to settle empirically in a scratch `mix phx.new` app — worth doing before committing the contract.
- **`--*: initial` semantics.** Tailwind's shared-theme example opens with it, wiping the default namespace. Decide deliberately whether the published token file is a closed palette or an overlay; it changes what ~15 apps inherit.
- **Angular 22 release date from a first-party changelog** (angular.dev/reference/releases or the angular/angular GitHub releases) to satisfy the two-source bar.
- **daisyUI 5.7.17 corroboration** from npm or GitHub releases — currently single-source.
- **Style Dictionary adapter generation.** The Tailwind `@theme inline` adapter file is mechanical. Worth checking whether Style Dictionary 5.5.1 has a Tailwind v4 `@theme` format built in or whether a ~20-line custom format is needed. Not investigated this round.

## Looked for and could NOT find

- **Any mechanism for Tailwind v4 `@theme` to auto-adopt variables already declared in `:root`.** The docs describe the two as deliberately separate and offer no bridge. This is the load-bearing negative finding: **the per-token adapter file is unavoidable** if you want utility classes. Absence of evidence here is strong — the theme docs are the exact place such a feature would be documented, and they instead spell out the opposite guidance.
- **Any mention of `@layer` / `layer()` on theme imports** in the Tailwind theme docs. The documented pattern is bare `@import`.
- **Confirmation that daisyUI theme variables accept `var()` references** inside a `@plugin "daisyui/theme"` block. Docs show only literal oklch values. Not refuted, just unaddressed.
- **The exact daisyUI version vendored in Phoenix v1.8.0.** The installer directory listing gives file sizes, not versions. An Elixir Forum thread shows a user's `app.css` upgrade comment pinning `v5.5.5`, but that is a forum post about someone's app, not authoritative for the 1.8.0 tag. Reading the version comment at the top of the vendored `daisyui.js` would settle it; I skipped it on budget (251KB file).
- **daisyUI mentioned anywhere in Phoenix's `asset_management.html` hexdocs page** — it is not, despite being vendored into every generated 1.8 app. The asset docs have not caught up with the installer templates.
- **Any explicit Angular documentation statement about CSS custom properties crossing the emulated-encapsulation boundary.** Inferred from the general global-styles statement plus CSS inheritance, not retrieved.
