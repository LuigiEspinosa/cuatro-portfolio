## Q1 verdict: moon v2 polyglot support

**Partially changed, and the 2024 complaint must NOT be repeated against v2 unqualified — but it is still
substantially true for this developer's stack.**

moon v2 replaced hard-coded "platforms" with WASM plugin toolchains. The official v2.0 announcement states:
"Toolchains are now powered by WASM plugins, instead of being hard-coded in core, allowing for more
flexibility, extensibility, and the ability for the community to create their own toolchains!"

The current `.moon/toolchains` config documentation (read 2026-08-15) enumerates the toolchains that
actually exist:

- **Stable / first-class:** `rust`, `go`, plus the JS cluster (`javascript`, `node`, `npm`, `pnpm`, `yarn`,
  `bun`, `deno`, `typescript`) and `unstable_nub`.
- **Explicitly unstable:** `unstable_python` (+ `unstable_pip`, `unstable_poetry`, `unstable_uv`),
  `unstable_ruby`.
- **Absent entirely:** **Elixir** and **Solidity** — no toolchain documented, stable or unstable.

So relative to the 2024-09 maintainer statement: **Go is now a documented first-class toolchain (real
change), Python exists but is shipped under an `unstable_` prefix (partial change), and Elixir and Solidity
remain wholly unsupported (no change).** For a stack containing Phoenix/Elixir and Solidity, moon v2 still
means "run whatever is on PATH" for those two — the exact failure mode round 1 identified for Nx and Pants.

The WASM plugin system does let a user point at their own `.wasm` toolchain plugin (config doc: you
"configure the location of the `.wasm` plugin file that moon will use to run this toolchain" via file,
HTTPS, or GitHub protocol). Whether anyone has actually authored an Elixir or Solidity toolchain plugin is
**unverified this run** (see "could not find"). Writing one is a Rust/WASM development project, not
configuration — that cost is real and should be priced as such.

**Version number is UNRESOLVED and fails the two-source rule** — see Claims.

## Q2 verdict: can a hub repo centrally own satellite CI in 2026?

**Yes for CI job definitions — the 2021 "manually copy the workflow into every satellite" complaint is
obsolete for the workflow BODY. It is not obsolete for the workflow STUB.**

GitHub Actions reusable workflows are called cross-repository with
`{owner}/{repo}/.github/workflows/{filename}@{ref}`, documented as working for public and private
repositories. Pinning is by SHA, release tag, or branch, with SHA documented as "the safest option for
stability and security" — so a hub can version its CI and satellites can pin.

What remains irreducibly per-repo: each satellite still needs its own caller workflow file containing the
trigger (`on:`) and the `uses:` line. Central definition is solved; central *installation* is not — the
stub, and any change to it, is still N-times work. Round 1's complaint was about copying whole workflows;
the residue in 2026 is copying a ~10-line stub.

Documented current limitations (GitHub Docs, accessed 2026-08-15):
- Max **ten levels** of nested workflows (top-level caller + up to nine reusable levels).
- **Loops in the workflow tree are not permitted.**
- Matrix + outputs: with a matrix strategy, the output is whichever matrix leg last completed successfully
  and actually set a value — a real footgun.
- **Environment secrets cannot be passed** via `workflow_call`, because `workflow_call` does not support the
  `environment` keyword.
- Permissions "can only be maintained or reduced—not elevated—throughout the chain."

For a solo developer with personal repos, none of these limits bind: nesting one level deep, no matrix
outputs, no environment secrets.

Org-level **rulesets can require a workflow to pass across many repositories at once** (GitHub Enterprise
plan / Enterprise Cloud), pinned to a branch, tag, or SHA — this is the piece that would remove the stub. It
is **plan-gated to Enterprise**, so it is not available to a personal-account developer. This claim rests on
aggregated search snippets, not a page read (budget spent) — treat as MEDIUM confidence and re-verify before
relying on it.

Renovate / Dependabot / repo templates: **not verified this run.** Do not assert.

## Q3 verdict: does modern git change monorepo economics at small scale?

**Modern git makes large monorepos survivable, but it is irrelevant at 15 modest personal projects. This is
a non-factor in the decision — do not let it argue either way.**

`scalar` (documented in git 2.53.0) "is a repository management tool that optimizes Git for use in **large
repositories**," and by default configures partial clone ("only commit and tree objects are cloned"),
sparse-checkout ("the only files present are those in the top-level directory"), commit-graph with
changed-path Bloom filters (`commitGraph.changedPaths=true`), multi-pack-index, and background maintenance.
The git documentation states an intent ("large repositories") but **publishes no size threshold** — no file
count, no repo size in GB, no commit count.

GitHub's own guidance (Derrick Stolee, GitHub Blog, 2020-12-21, updated 2021-04-28) is the closest thing to
a threshold and it points the other way: full clones are recommended when "your repository is
reasonably-sized"; blobless clones are for "large repositories with extensive file histories"; treeless
clones are for CI only — "we strongly recommend that developers do not use treeless clones"; and "we do not
recommend shallow clones except for builds that delete the repository immediately." That post contains no
concrete size or timing numbers; it defers them to a companion post it does not link.

Combined with round 1's finding that git scale pain tracks commit and ref count rather than project count, a
repository of ~15 modest personal projects is squarely inside "reasonably-sized." **A specific answer: no —
such a repository would not need partial clone, sparse checkout, scalar, or manual commit-graph maintenance,
and would not be expected to during this developer's lifetime of solo commits to it.** These features are
neither a reason to choose a monorepo nor a cost of one at this scale.

Freshness caveat: the GitHub partial-clone post is 2020/2021, outside the 12-month landscape window. It is
cited because it is GitHub's primary engineering guidance and no newer official replacement was located
within budget; its recommendations are consistent with the current git 2.53.0 scalar documentation.
