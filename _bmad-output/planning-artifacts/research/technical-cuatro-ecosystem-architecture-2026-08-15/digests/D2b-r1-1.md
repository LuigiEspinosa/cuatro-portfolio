**DATE CAVEAT — read this before quoting any Style Dictionary date.** The GitHub releases page fetch returned the
release *sequence* correctly (5.5.1, 5.5.0, 5.4.4 … 5.3.1) but stamped them 2024. That is impossible and internally
contradictory: the same page states v5.4.0 added support for the **DTCG v2025.10** dimension token type, and 2025.10
did not exist until October 2025. The npm listing (surfaced in search) independently says 5.5.0 was published
"a month ago", i.e. ~July 2026. Resolution by internal consistency: **the version numbers are high confidence, the
years are a fetch artifact, and the true dates are 2026.** Exact release dates are UNVERIFIED and must be re-checked
against the GitHub API before anyone depends on them. npm.com returned HTTP 403 to direct fetch this run.

- **Claim:** Tailwind v4 replaced the JS `tailwind.config.js` theme with a **CSS-first `@theme` directive**; every
  theme variable is emitted as a native CSS custom property AND generates utilities (`--color-mint-500` → `bg-mint-500`,
  `text-mint-500`, `fill-mint-500`).
  - source: https://tailwindcss.com/docs/theme
  - publisher: Tailwind Labs (primary docs)
  - pub_date: docs channel v4.3, undated page
  - accessed: 2026-08-15
  - confidence: high
  - class: version
  - corroboration: https://tailwindcss.com/blog/tailwindcss-v4 (v4.0 announcement, surfaced in search)

- **Claim:** Tailwind's docs draw an explicit line that matters for token federation: **use `@theme` when a token
  should map to a utility class, and `:root` for CSS variables that should NOT generate utilities.** A plain
  CSS-custom-properties file imported into a Tailwind app therefore yields variables but **no utility classes** unless
  its values are also declared in `@theme`.
  - source: https://tailwindcss.com/docs/theme
  - publisher: Tailwind Labs
  - pub_date: undated (v4.3 docs)
  - accessed: 2026-08-15
  - confidence: high (the quoted distinction), medium (the "no utilities from a plain CSS file" consequence is my inference from that distinction, not a sentence in the docs)
  - class: cost
  - corroboration: single-source — **this is the load-bearing inference for the whole Tailwind question and deserves a round-2 verification.**

- **Claim:** `@theme inline` exists specifically because **without it, a theme variable that references another
  variable resolves where it is *defined*, not where it is *used*** — producing wrong values/fallbacks when the
  referenced variable is redefined in a nested scope. This is the mechanism for `@theme inline { --font-sans:
  var(--font-inter); }`.
  - source: https://tailwindcss.com/docs/theme
  - publisher: Tailwind Labs
  - pub_date: undated (v4.3 docs)
  - accessed: 2026-08-15
  - confidence: high
  - class: pattern
  - corroboration: single-source (primary docs)
  - **why this matters:** it is the documented bridge for "define tokens in a shared CSS file, then alias them into
    `@theme` so Tailwind generates utilities." It is also the documented failure mode if you *don't* use `inline`.

- **Claim:** The Tailwind theme docs **do not mention** runtime-theming limitations, nor any requirement that theme
  values be static at build time.
  - source: https://tailwindcss.com/docs/theme
  - publisher: Tailwind Labs
  - pub_date: undated
  - accessed: 2026-08-15
  - confidence: medium (absence of evidence on one page)
  - class: cost
  - corroboration: single-source. Secondary sources surfaced in search claim v4 supports runtime theme swapping via
    `.dark` / `[data-theme="brand"]` "with no rebuilds" — **not read, and those are marketing-register blog posts.**

- **Claim:** A design-token change is treated as **breaking (major bump) when it changes the contract, not when it
  changes the pixels**: renaming a token, removing one, changing its structure or type. Even a one-character rename
  (`colour` → `color`) is breaking. By contrast **adding new colors, or retuning an interactive blue for
  accessibility, is a minor bump** — a value change is not inherently breaking.
  - source: https://designtokens.substack.com/p/how-to-manage-breaking-changes-in and https://medium.com/eightshapes-llc/versioning-design-systems-48cceb5ace4d
  - publisher: Design Tokens newsletter; Nathan Curtis / EightShapes
  - pub_date: not established this run (EightShapes versioning essay is a long-standing reference piece)
  - accessed: 2026-08-15
  - confidence: medium (read via search summary, neither article fetched)
  - class: pattern
  - corroboration: two independent publishers agree, plus NL Design System publishes a formal semver convention for tokens (https://nldesignsystem.nl/handboek/developer/semver-conventie/)
  - **direct answer to "is a color change breaking?": per these sources, NO — a value change is minor; a NAME change is major.** Curtis separately argues for a "visual breaking change" concept, i.e. changes that break *appearance* without breaking the API — a category plain semver does not express.

- **Claim:** The recommended handling of a token breaking change is a **three-phase deprecation → migration → removal**
  window, not a hard cutover.
  - source: https://designtokens.substack.com/p/how-to-manage-breaking-changes-in
  - publisher: Design Tokens newsletter
  - pub_date: not established
  - accessed: 2026-08-15
  - confidence: medium
  - class: pattern
  - corroboration: single-source
  - **relevance:** with no atomic cross-repo commit, a deprecation window is not a nicety — it is the only mechanism
    that lets 15 repos migrate at different speeds. Old and new token names must coexist for a release or two.

- **Claim:** The dominant published release automation for token packages is **semantic-release (Conventional Commits)

  - source: https://medium.com/@jdposada/design-tokens-architecture-7544c9a8f33a and https://stevekinney.com/courses/enterprise-ui/dependency-management
  - publisher: Juan David Posada; Steve Kinney (Enterprise UI course)

  - class: pattern
  - corroboration: two publishers, but both generic-advice rather than a case study

## Distribution mechanisms compared

Honest framing: **I did not find a single case study naming a specific design system and its cross-repo distribution
mechanism.** The Oppermann article (the most promising practitioner account, "The ultimate Design Tokens setup or how
to manage design tokens across your org") is **Medium member-only and returned only its intro** — trade-offs, versioning
and CI detail were behind the paywall. The table below is therefore mostly *mechanism space* with weak sourcing, not
verified practice. Treat it as a round-2 agenda, not a finding.

| Mechanism | Who uses it (verified?) | Trade-off | Source |
|---|---|---|---|
| npm package + semantic-release/Changesets | **Not verified to a named system.** Described as standard practice | Version pinning per repo; each repo upgrades on its own clock; needs a registry decision (public/private/GH Packages) | [Posada](https://medium.com/@jdposada/design-tokens-architecture-7544c9a8f33a), [Kinney](https://stevekinney.com/courses/enterprise-ui/dependency-management) |
| Publish JSON → Style Dictionary transform per consumer | Described as the canonical pipeline shape (export JSON from design tool → transform → distribute) | Each consumer needs the transform toolchain — bad for the Phoenix app | [Posada](https://medium.com/@jdposada/design-tokens-architecture-7544c9a8f33a) |
| Prebuilt CSS custom properties file | **Not verified this run** | Lowest common denominator; per Tailwind docs, yields variables but no utilities without `@theme` re-declaration | inference from [tailwindcss.com/docs/theme](https://tailwindcss.com/docs/theme) |
| Monorepo (avoid the problem) | Advised only where packages change together; "packages that release independently don't need to be forced into a monorepo" | **Not available** — the brief fixes separate repos | [Kinney](https://stevekinney.com/courses/enterprise-ui/dependency-management), [freeCodeCamp](https://www.freecodecamp.org/news/how-to-build-a-scalable-design-system-in-a-monorepo/) |
