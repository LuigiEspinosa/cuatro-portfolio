# D1b round 1 — monorepo vs polyrepo evidence, solo-maintainer discount

Sources actually read this run (6 of 6 budget): Proton engineering blog; Grab engineering blog; CSS-Tricks (Losoviz); Streamdal/Medium (Selans); kenmuse.com; Indie Hackers thread. Everything below traces to one of those. Search-engine result summaries were NOT treated as sources.

## Claims

- **Claim:** Proton's front-end org moved ~15 polyrepo repositories into one monorepo, with ~15 front-end developers plus cross-team contributors, and the stated driver was that a single feature forced them to "mirror Git operations — branching, committing, opening merge requests, reviewing, rebasing" across many repositories.
  - source: https://proton.me/blog/engineering-polyrepo-monorepo
  - publisher: Proton (engineering blog)
  - pub_date: 2022-08-18
  - accessed: 2026-08-15
  - confidence: medium (primary account, but no post-migration metrics; HISTORY — 4 years old, admissible as pattern evidence only)
  - class: team-dependent
  - corroboration: single-source for the specifics; direction corroborated by Streamdal (below)

- **Claim:** Every named Proton benefit (atomic multi-repo changes, cross-project code visibility encouraging contribution to projects "they don't directly own", unified Git workflow and administration guidelines across teams, one-click onboarding setup) is framed around coordination between people, not around a single author's throughput.
  - source: https://proton.me/blog/engineering-polyrepo-monorepo
  - publisher: Proton
  - pub_date: 2022-08-18
  - accessed: 2026-08-15
  - confidence: medium
  - class: team-dependent
  - corroboration: single-source (this is my reading of their stated benefit list, not their claim)

- **Claim:** Grab's monorepo reached 214 GB of Git data, ~13 million commits, 23.6 million trees, 176 GB of blobs, 12.2 million refs and 444,000 checked-out files, at which point clone took 7.9 minutes and Gitaly replication lag ran ~240 seconds.
  - source: https://engineering.grab.com/taming-monorepo-beast
  - publisher: Grab Engineering (Gangwar, Vajpayee, Low, Hameed, Misra)
  - pub_date: 2025-09-16
  - accessed: 2026-08-15
  - confidence: high (first-party numbers, recent)
  - class: performance
  - corroboration: single-source for these exact figures — TWO-SOURCE RULE NOT MET, treat as one company's scale, not a general threshold

- **Claim:** Grab's fix was history truncation (keep 2,000+ tags plus one month of history, simplify merge commits), not partial clone or sparse checkout, and it cut storage 214→87 GB (59%), commits ~13M→~15,800 (99.9%), refs 12.2M→9,860 (99.9%), clone 7.9→5.1 min (36%), replication delay 240s→~1.5s (99.4%).
  - source: https://engineering.grab.com/taming-monorepo-beast
  - publisher: Grab Engineering
  - pub_date: 2025-09-16
  - accessed: 2026-08-15
  - confidence: high
  - class: cost
  - corroboration: single-source
  - note: the load-bearing detail for D1b is the SHAPE of the cost — the pain is driven by commit/ref/history COUNT, which is a function of contributor-years, not of number of projects. 15 personal projects cannot generate 13M commits.

- **Claim:** Monorepo git pain in Grab's account is caused by history depth and ref count (99.9% of the win came from deleting commits and refs; deleting 59% of bytes bought only a 36% clone improvement), i.e. checkout size is the weaker driver.
  - source: https://engineering.grab.com/taming-monorepo-beast
  - publisher: Grab Engineering
  - pub_date: 2025-09-16
  - accessed: 2026-08-15
  - confidence: medium (inference from their own before/after table)
  - class: performance
  - corroboration: single-source

- **Claim:** A single maintainer (Leonardo Losoviz, PoP project, ~200 interdependent PHP packages) traversed all four layouts — single repo → multi-repo → monorepo → "multi-monorepo" — and the multi-repo stage failed for him specifically on dependency versioning: "Every package must be versioned, and every version of a package depends on some version of another package."
  - source: https://css-tricks.com/from-a-single-repo-to-multi-repos-to-monorepo-to-multi-monorepo/
  - publisher: CSS-Tricks / Leonardo Losoviz
  - pub_date: 2021-08-17

  - confidence: medium (HISTORY, 5 years old; single-author self-report, no metrics)
  - class: pattern
  - corroboration: single-source — this is the ONLY genuinely N=1 multi-year layout retrospective I found

- **Claim:** Losoviz's trigger for leaving the plain monorepo was not scale or performance but a visibility constraint — "the code in the repo is either public or private, so I'm unable to host my private code in the public leoloso/PoP repo" — plus mixed licensing and a chaotic shared issue board.
  - source: https://css-tricks.com/from-a-single-repo-to-multi-repos-to-monorepo-to-multi-monorepo/
  - publisher: CSS-Tricks / Losoviz
  - pub_date: 2021-08-17
  - accessed: 2026-08-15
  - confidence: medium
  - class: failure (partial — a constraint, not a collapse)
  - corroboration: single-source

- **Claim:** The "hub and satellites" idea has a documented practitioner instance under the name **multi-monorepo / federated monorepo**: an upstream public monorepo embedded as a Git submodule inside a downstream private monorepo, sharing workflows and config downward.
  - source: https://css-tricks.com/from-a-single-repo-to-multi-repos-to-monorepo-to-multi-monorepo/
  - publisher: CSS-Tricks / Losoviz
  - pub_date: 2021-08-17
  - accessed: 2026-08-15

- **Claim:** The reported failure mode of that federated pattern is abstraction leakage: the downstream repo must pass `--recurse-submodules`, upstream CI must be written with escape hatches (`CHECKOUT_SUBMODULES: ""`) so downstream can override it, and GitHub Actions only loads workflows from `.github/workflows` so shared workflows must be MANUALLY COPIED downstream despite upstream being the declared source of truth.
  - source: https://css-tricks.com/from-a-single-repo-to-multi-repos-to-monorepo-to-multi-monorepo/
  - publisher: CSS-Tricks / Losoviz
  - pub_date: 2021-08-17
  - accessed: 2026-08-15
  - confidence: medium (era caveat: GitHub Actions reusable workflows have evolved since 2021 — VERIFY current behaviour before relying on this)
  - class: cost
  - corroboration: single-source
  - note: this is the most directly decision-relevant finding for the hub-and-satellites option — the shared-tooling benefit is the part that leaked, and it leaked in exactly the "one repo owns the deploy layer" direction being considered.

- **Claim:** Streamdal (open-source startup, ~10 interdependent repos: server, console, Go/Node/Python SDKs, protobuf schemas, WASM artifacts, docs) consolidated into a monorepo in ~1 week of hands-on work, and the driver was PROJECT PERCEPTION and user navigation — the flagship repo showed "Last updated: 6 months ago", GitHub's language bar showed only shell and markdown, and users could not tell which of 10+ repos to file a bug against.
  - source: https://medium.com/streamdal/mostly-terrible-the-monorepo-5db704f76bdb
  - publisher: Streamdal / Daniel Selans (Principal Architect)
  - pub_date: 2024-01-03
  - accessed: 2026-08-15
  - confidence: medium (single-author retrospective, no CI/size metrics)
  - class: pattern
  - corroboration: direction (polyrepo→monorepo at ~10-15 repos) corroborated by Proton — TWO INDEPENDENT SOURCES for the direction, not for any number
  - note: highly transferable to a portfolio of 15 personal projects, where the audience-facing signal (does this look alive?) is arguably the point.

- **Claim:** The same author who made that migration still concludes monorepos are "mostly terrible" in general, with the open-source/user-facing case as the rare exception — i.e. the migration was justified by discoverability, not by engineering economics.
  - source: https://medium.com/streamdal/mostly-terrible-the-monorepo-5db704f76bdb
  - publisher: Streamdal / Selans

- **Claim:** Ken Muse's anti-monorepo argument rests on organizational friction (longer merge queues delaying releases, minor changes forcing larger slower deployments, notification overload) and on the observation that Google-scale monorepos need "custom file system drivers and other OS-level tooling" plus "dedicated teams and a budget for ongoing maintenance" — he gives NO numeric git thresholds and does not discuss shallow clone, sparse checkout or Scalar.
  - source: https://www.kenmuse.com/blog/why-you-should-not-prefer-monorepos-for-git/
  - publisher: Ken Muse (independent, ex-GitHub-ecosystem author)
  - pub_date: 2023-06-23

  - class: team-dependent
  - corroboration: single-source
  - note: every cost he names — merge queues, deployment batching, notification volume, access control — is a MULTI-CONTRIBUTOR cost. At N=1 there is no merge queue, no contractor access boundary, no notification fan-out. This piece is close to a proof by construction that the mainstream anti-monorepo case does not bind a solo developer.

- **Claim:** In a solo-developer thread started by someone who consolidated 8 repositories (website, API, jobs, lambdas, bot) into a monorepo, the practitioner consensus was "For smaller teams, 100% do monorepos. When you start to have autonomy between teams repo splits become important."

- **Claim:** The same thread surfaced two decision heuristics worth carrying: path-filtered CI ("you can trigger builds only when anything under a specific folder is changed") makes monorepo CI fan-out tractable, and the split line should follow AUTONOMY — keep tightly-integrated full-stack components together, separate genuinely independent apps with distinct versioning needs.
  - source: https://www.indiehackers.com/post/multi-vs-mono-repo-pros-cons-380cb63ae6

## Team-dependence audit

Which claimed monorepo benefits survive at N=1, on the evidence retrieved:

**Require N>1 — do NOT survive at N=1:**
- *Coordinated multi-repo git ceremony* — Proton's headline pain was mirroring branch/commit/MR/review/rebase across repos. Review and MR ceremony is a team artifact. (proton.me, 2022-08-18)
- *Cross-project discoverability for contributors* — Proton: visibility "encourages developers to contribute across projects they don't directly own." Meaningless with one owner. (proton.me, 2022-08-18)
- *Unified workflow/administration guidelines across teams* — Proton frames standardization as governance over multiple front-end teams. (proton.me, 2022-08-18)
- *Onboarding* — Proton's "one-click setup" benefit is a per-new-person cost that at N=1 is paid roughly once, or once per machine.
- Symmetrically, the main POLYREPO benefits also require N>1: access control / contractor isolation, and team autonomy. (kenmuse.com 2023-06-23; indiehackers.com 2020-02-18)
- And the main polyrepo-avoids-this COSTS require N>1: merge queues, deployment batching across teams, notification volume. (kenmuse.com, 2023-06-23)

**Survive at N=1:**
- *Atomic cross-project change and rollback* — Proton: "no single operation could perform a rollback on separate Git histories simultaneously." A solo dev changing a shared token and 4 consumers hits this identically. (proton.me, 2022-08-18)
- *Dependency version coordination* — Losoviz, working alone across ~200 packages, was defeated by version-of-a-version chains, not by people. (css-tricks.com, 2021-08-17)
- *Single-place dependency/library upgrades* — same mechanism.
- *Project liveness and user navigation signal* — Streamdal's "Last updated: 6 months ago" and wrong language bar are properties of the REPO and its AUDIENCE, entirely independent of contributor count. For a 15-project personal portfolio this is the strongest surviving benefit. (medium.com/streamdal, 2024-01-03)
- *Shared tooling/config inheritance* — real, but demonstrably leaky when federated rather than merged. (css-tricks.com, 2021-08-17)

**Cost side, discounted for N=1:**
- Git scale pain is driven by commit count, ref count and history depth (Grab: 13M commits, 12.2M refs), all of which accumulate per contributor-year. 15 personal projects merged do not approach any of it. (engineering.grab.com, 2025-09-16)
- Nothing I retrieved gives a repo-size threshold applicable below the tens-of-GB range. Treat "monorepo git performance" as a non-issue at personal-portfolio scale until evidence says otherwise.

## Leads worth chasing

- **git-meta (Two Sigma)** — https://github.com/twosigma/git-meta, described in search listings as "build your own monorepo using Git submodules". Named, tooled instance of the hub-and-satellites pattern. NOT READ — verify it is still maintained (its era looks ~2017-2019, which if true makes it HISTORY and possibly a dead pattern; a dead tool is itself a finding).
- **`metarepo` (PyPI)** and **OpenSlides' "meta repository" wiki** — two more named instances of the pattern, unread. Worth one round to see whether practitioners report the same workflow-leak failure Losoviz did.
- **The "Planning Repo Pattern"** (jbpoley, Medium) — claims to manage 20+ repos while explicitly avoiding submodule version coupling. Directly on-point for hub-and-satellites; unread.
- **Contradiction to resolve:** Streamdal migrated INTO a monorepo while calling monorepos "mostly terrible", and Ken Muse's costs are all team costs. Both point the same way — that the anti-monorepo literature is arguing about org dynamics, not repo mechanics. One more critical source with actual solo/small numbers would settle it.
- **Era check owed:** Losoviz's GitHub Actions workflow-copying complaint is from 2021, before reusable workflows matured. If reusable workflows now work across repos, the central cost of hub-and-satellites may have been fixed. This is the single highest-value verification for the decision.
- **Unverified but frequently repeated:** "Kubernetes moved away from a monorepo into ~48,000 repositories" (appeared in the Ken Muse summary). Needs a primary Kubernetes/CNCF source before use.
- **Turborepo/Nx era question:** all six sources read pre-date or barely touch modern JS monorepo tooling. Whether Turborepo remote caching changes the 4-Next.js-app partial-merge economics is untested here.

## Looked for and could NOT find

- **Any published study, survey, or dataset on solo developers / N=1 maintainers and repository layout.** Nothing. The public evidence base is community threads and single-author blog posts. The Losoviz CSS-Tricks piece is the closest thing to a rigorous N=1 account and it has zero metrics and is 5 years old. **This is a genuine gap, not a search failure: the monorepo literature is written by and for teams, and the solo case is unstudied.**
- **Any retrospective with numbers for the monorepo → polyrepo direction.** I found the direction asserted repeatedly in listings but read no primary account of it. The TWO-SOURCE bar for "monorepo failed for someone" is **NOT MET** — I therefore do not state that monorepo failed for anyone. Note the irony that the top-ranked "why we moved away from our monorepo" result (Streamdal) is actually a migration INTO one.
- **Numeric thresholds** — no source read gives "at X GB / Y files / Z commits, git operations degrade". Grab gives one company's operating point (214 GB, 13M commits), not a breakpoint. Nobody publishes the low end.
- **Before/after CI-minute numbers** for any migration in either direction. Grab reports "3x more concurrent jobs" and a prior "5-8 minute" CI overhead but does not tie it to a layout decision.
- **Any evaluation of whether modern git mitigations (partial clone, sparse checkout, Scalar) change the calculus below enterprise scale.** Grab explicitly did NOT use them; Ken Muse does not mention them. The "monorepos are slow" complaints I read are therefore untested against the current toolchain.
- **Clone-size or IDE/language-server performance data** at any scale. Not addressed by any source read.
- **Any documented re-evaluation trigger stated as a metric.** The triggers I did find are all qualitative: cross-repo change ceremony (Proton), version-chain unmanageability (Losoviz), public/private split (Losoviz), stale-looking flagship repo and confused bug reporters (Streamdal). Notably, NONE of the four triggers is performance.
