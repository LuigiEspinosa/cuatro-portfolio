## Q1 verdict: custom elements inside LiveView

**Documented, supported, and bounded, but the docs never say "web component" or "custom element".**

LiveView v1.2.9 documents exactly three escape hatches for client-owned DOM, and none of
them are custom-element-specific:

- `phx-update="ignore"`: "ignores updates to the DOM regardless of new content changes …
  useful for client-side interop with existing libraries that do their own DOM operations."
  The carve-out that matters: updates are ignored "except for data attributes. Changes,
  additions, and removals from the server to data attributes are merged with the ignored
  element which can be used to pass data to the JS handler." So a server→client data channel
  survives the ignore; a server→client *attribute* channel does not.
- `phx-hook`: lifecycle callbacks `mounted`, `beforeUpdate`, `updated`, `destroyed`,
  `disconnected`, `reconnected`. "when using `phx-hook`, a unique DOM ID must always be set."
- The `LiveSocket` `dom` option with `onBeforeElUpdated(fromEl, toEl)`: the docs' explicit
  recommendation "for integration with client-side libraries which require a broader access
  to full DOM management", firing "just before the DOM patch operations occurs in LiveView"
  so libraries can "re-initialize DOM elements or copy attributes as necessary."

The official recommendation is therefore: **`phx-update="ignore"` for a self-contained
client-owned island, `onBeforeElUpdated` when the client library needs to survive patching
globally, `phx-hook` to bridge events.** `phx-update="stream"` is for large server-driven
collections, not for client components: irrelevant here.

The v1.2.9 pages I read contain **no mention of shadow DOM, custom elements, morphdom, or
the DOM patching library by name**. That is a real gap, not an oversight on my part: LiveView
documents "client-side libraries" generically and leaves custom elements to be inferred as
one such case.

**On failure reports: I could NOT corroborate any to the two-source standard within budget.**
Search surfaced multiple Elixir Forum threads whose titles describe exactly the predicted
failure modes ("LiveView re-render is causing DOM elements to reset", "Why LiveView resets
all the document created element (DOM)", "Running LiveView inside a web component with shadow
DOM", "Embed LiveView inside ShadowDOM"), but I did not read the threads and have no version
stamps for them. Titles are not evidence of a failure mode; several are dated pre-1.0 by URL
ID. Treat as leads, not findings.

## Q2 verdict: precedent for server-rendered + JS-framework sharing one system

**No published Phoenix/LiveView + JS-framework shared design system was found this run.**
Zero results, not a weak result: searches on Phoenix design systems and Phoenix design tokens
returned component libraries and generic token explainers, never a documented cross-stack system.

**The adjacent Rails precedent has just been abandoned, and that is the load-bearing finding.**
GitHub Primer: the canonical example of one design system serving both a server-rendered
template stack (Rails ViewComponent) and a client-framework stack (React): retired the server
side. From the primer/view_components README: "As part of GitHub's move to React-based
interfaces, Primer ViewComponents is in maintenance mode as of February 2026", "not accepting
new features, components, or significant enhancements", with only "Security updates, Dependency
bumps, Critical/P0 bug fixes" continuing, and "We encourage internal GitHub consumers to plan
to migrate from Primer ViewComponents to Primer React."

So the best-resourced organisation attempting exactly this problem concluded, in the last six
months, that maintaining component parity across a server-rendered stack and a React stack was
not worth it, and resolved it by deleting the server-rendered stack, not by unifying it.

What Primer shared across the boundary, per search-snippet only (LOW confidence, not read):
design tokens from JSON in `@primer/primitives`, consumed by Figma, CSS and code. I did not
verify this against the primitives repo. Components were **not** shared: they were parallel
implementations, which is precisely why one of them is now in maintenance mode.

Django: searched implicitly via the design-token query; nothing surfaced. Not established.

## Q3 verdict: what Phoenix apps actually use for UI

**Tailwind classes and CSS custom properties, shipped as HEEx function components. Not web
components.** This is well supported for the generator; less well supported for the ecosystem
libraries, where my extraction was thin.

Phoenix 1.8.0 (released 2025-08-05) is explicit: the release "extends our built-in tailwindcss
support with daisyUI, adding a flexible component and theming system", ships "the latest and
greatest from the recent tailwind v4 release", and "All phx.new apps now ship with light and
dark themes out of the box, with a toggle built into the layout." That is the change to what
`mix phx.new` generates, and the date it landed: **Tailwind v4 + daisyUI, August 2025.** The
blog post does not name a daisyUI version number.

`core_components.ex` got *smaller* in 1.8, not larger: "The `mix phx.gen.live` generator now
follows its sibling, `mix phx.gen.html`, to provide a straight-forward CRUD interface you can
build on top of … In turn, this allows us to trim down the core components to only the main
building blocks." Phoenix deliberately reduced its built-in component surface and pushed the
visual system down into daisyUI's Tailwind/CSS-variable theming.

Ecosystem libraries (2026-01-31 survey, plus README-level snippets: MEDIUM/LOW confidence,
no versions or release cadence established): SaladUI (shadcn-inspired, copy-into-your-project
HEEx components), Petal Components (HEEx + Tailwind, "similar to Bootstrap or MUI, but written
in HEEx using Tailwind CSS classes"), PrimerLive, Fluxon UI, Mishka Chelekom ("zero-dependency,
Tailwind CSS-based UI kit with over 90 components"). **Every library named is HEEx +
Tailwind-class based. Not one is a web-component library.** I did not establish current
versions or release cadence for any of them: see "could NOT find".

The honest framing you asked me to test holds up for the framework itself: **Phoenix consumes a
design system as Tailwind classes and CSS custom properties, and re-implements components in
HEEx.**

## Q4 verdict: token consumption path into a Phoenix app

**Mechanically plausible and architecturally obvious; published precedent NOT found.**

Nothing I read this run documents a Phoenix app consuming a token artefact produced by a JS
token pipeline. The search returned generic design-token-vs-CSS-variable explainers from
non-Phoenix publishers. One Medium post ("Integrating Tailwind, React Islands, and Elixir
Phoenix LiveView") appeared in results but I did not read it and it is a low-quality publisher.

What I *can* anchor: Phoenix 1.8 ships Tailwind v4 and daisyUI, and daisyUI's theming is
CSS-custom-property based, and 1.8 apps ship a light/dark theme toggle in the layout
(phoenixframework.org, 2025-08-05). A CSS-custom-properties file is therefore landing in
exactly the layer Phoenix 1.8 already uses for theming. But I did not verify the `assets/`
directory layout, the esbuild/tailwind Mix task wiring, or any npm-consumption path against a
primary source this run: that was budgeted away. **Do not treat the token path as verified.**
