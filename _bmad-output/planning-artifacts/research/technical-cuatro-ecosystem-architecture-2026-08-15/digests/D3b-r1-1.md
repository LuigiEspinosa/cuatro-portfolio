## Verdict on the binding constraint

**CPU, and the evidence points at it — but the mechanism is not the one the brief assumed.**

The RAM arithmetic does not look frightening. The only hard footprint number I could evidence (640 MB RSS for a Next.js SSR server, and that under crawler assault) implies four Next.js apps ≈ 2.5 GB worst case, likely well under that at idle. Add Postgres (128 MB shared_buffers default plus backends), a BEAM release, Fastify, Python, Go, and a proxy, and 8 GB has visible headroom. **I could not evidence footprints for BEAM, Fastify, Traefik/Caddy at all**, so this is an inference from one measured number plus defaults — hold it loosely.

CPU is where the evidence actually bites: a **single** Next.js process was measured at 103.3% CPU — more than half of a 2-vCPU box consumed by one of twelve containers — and the trigger was **bot traffic, not users**. That is decisive for this case, because the brief says there are no real end users: the load on a portfolio box is crawlers, which do not care that the site is a portfolio, and four public Next.js apps are four crawl targets. Add that these are *shared* vCPUs (steal time, no burst guarantee) and the first wall is CPU.

**Symptoms, in the order to expect them:** (1) rising 15-minute load average past 2.0 on 2 cores while free RAM still looks fine — the classic tell that this is CPU, not memory; (2) Node event-loop delay and event-loop utilisation climbing, with aborted responses (the exact signature in the Next.js thread: "sharp increase in Event Loop Delay", frequent `ResponseAborted`); (3) p99 latency degrading across *unrelated* apps simultaneously, because they share the cores; (4) only much later, memory symptoms. Notably, **`next build` is itself CPU- and RAM-hungry, and building on the box while serving from it is the most likely way to actually fall over** — I could not source a figure for this and flag it as the top gap.

**Shared-vs-per-app Postgres call:** the evidence supports **one Postgres container, one database + one role per app**. Each extra Postgres container pre-commits its own shared_buffers (128 MB default each — five containers ≈ 640 MB before serving a query), its own autovacuum workers and background processes, its own backup and upgrade lifecycle. Schema-per-app is the tighter variant but couples the apps' migrations, which is bad with Prisma. Database-per-app in one cluster gets nearly all the isolation (separate roles, separate `pg_dump`, no cross-app table visibility) at one process's fixed cost. The Prisma risk is real but is arithmetic, not fate: set an explicit `connection_limit` per app in the DATABASE_URL, keep the sum under `max_connections`, and skip PgBouncer entirely at this scale — PgBouncer exists for serverless burst, which does not apply to long-lived containers.

**Supabase:** the three-way collapses fast. Self-hosting needs 10+ containers and a recommended 8 GB *by itself* — it would eat the box. Managed Free ($0) pauses after 7 days of inactivity, which is precisely the access pattern of a portfolio app, and caps at 2 active projects. Managed Pro is $25/mo — a quarter of the ceiling for one app's database. Plain Postgres on the VPS is the only option that is both free and unpaused; keeping Supabase managed on Free with a keep-alive ping is the zero-migration fallback.

## Leads worth chasing

1. **Verify Compose limit syntax against the current spec** — `docs.docker.com/reference/compose-file/deploy/` and the `services` top-level keys. My `deploy.resources` finding is issue-tracker hearsay and undated. This is the single most load-bearing unverified item.
2. **`next build` CPU/RAM cost on 2 vCPU.** Strongly suspect this, not steady-state serving, is the real wall. Search "next build out of memory 2GB CI" and Next.js build-time docs.
3. **BEAM/Phoenix idle footprint.** Zero public numbers found. Try the Fly.io and Erlang Solutions engineering blogs, or `erlang-questions` — BEAM's idle memory is genuinely small (~30–60 MB is the folk figure) but I could not evidence it and refuse to assert it.
4. **Backup tooling release cadence — entirely unexamined.** pgBackRest, wal-g, Barman, restic, borg: check GitHub releases *over time* for 2025–2026. Restic in particular had a long quiet stretch historically; do not assume. Also compare against provider snapshots, which for a solo operator are the only backup that actually gets sustained.
5. **Restore testing guidance.** The brief asked; I found nothing. Look for pgBackRest docs' verification chapter and any published "we never tested restore" post-mortems.
6. **PSI (pressure stall information) thresholds** on cgroup v2 / Ubuntu 24.04 — `/proc/pressure/{cpu,memory,io}` and per-cgroup equivalents. This is the *right* metric for this box (better than load average) and I found nothing citable. Try kernel.org Documentation/accounting/psi.rst and Facebook's original PSI writeups.
7. **Swap policy** — only partially answered. I have Docker's per-container swap semantics but **no current guidance on whether a 2 vCPU/8 GB container host should have swap at all**. Search "zram swap container host" and Ubuntu server guidance.
8. **Railway sleep/idle policy** — the pricing page is silent; check `docs.railway.com` app-sleeping / serverless settings, since scale-to-zero would change the hybrid cost calculus enormously for idle portfolio apps.
9. **Cloudflare in front of everything** — the Next.js thread's own resolution (90%+ load reduction) suggests the cheapest CPU fix on this box is not tuning, it is a free CDN/bot filter. Worth its own round.
