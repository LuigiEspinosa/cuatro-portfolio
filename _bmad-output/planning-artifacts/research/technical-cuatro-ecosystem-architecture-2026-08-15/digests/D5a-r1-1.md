## Q4: Supabase user export

**Not answered from Supabase's own documentation.** The page I read
(supabase.com/docs/guides/auth/managing-user-data) documents that the `auth` schema **"is not
exposed in the auto-generated API"**, that `auth.users` is viewable in the Table Editor, and that
you **"can query the `auth.users` and `auth.identities` table via the SQL Editor tab to extract all
users"** and export the results as CSV. It says **nothing** about the `encrypted_password` column,
password-hash format, pg_dump, or migrating hashes to another provider.

The claim that Supabase stores bcrypt in `auth.users.encrypted_password` and that hashes come out
with a `pg_dump` of the `auth` schema appeared only in GitHub Discussions
(supabase/supabase #3897, supabase #36664) and third-party migration vendors (Better Auth, Neon,
lovablemigration.com) surfaced via search: **I did not read any of those pages this run.** The
direction of travel is plausible and the mechanism (direct SQL/pg_dump against your own Postgres,
since Supabase gives you the database) is consistent with what the official page does say about
SQL-Editor access. But **the hash format and the importability into a specific target IdP are
unconfirmed.** Do not plan a no-password-reset migration on this round's evidence.

## Leads worth chasing

1. **Keycloak version + cadence**: read github.com/keycloak/keycloak/releases directly. The "Nightly 26.7.1" label on the docs site is not a release version and must not be reported as one.
2. **Keycloak native/Quarkus image sizing**: the HA sizing page is silent. Check keycloak.org/server/containers and the `--optimized` / native-build docs for any separate memory guidance; this is the single biggest swing factor on whether Keycloak is survivable here.
3. **Pocket ID docs**: pocket-id.org docs for the language/runtime (Go claim), stated resource footprint, and whether SQLite is the default. If Go + SQLite + single binary holds, it is the leading candidate and deserves a dedicated read.
4. **ZITADEL resource footprint**: the requirements page is silent; try zitadel.com/docs/self-hosting/manage/production and github.com/zitadel/zitadel/discussions/2079 (a maintainer answer there would be semi-primary). A search summary attributed "~512MB RAM, <1 CPU core" to help.zitadel.com, **unverified, do not cite until read at source.**
5. **authentik GitHub issue #21413, "Hardware Requirements are way too low"**: an open issue on the project's own tracker arguing the documented 2 GB minimum is understated. If maintainers responded, that is a primary-ish correction to the vendor minimum and is directly decision-relevant.
6. **Logto, Casdoor, Ory**: entirely unexamined. Each needs GitHub releases + a requirements/docs page.
7. **Unverified pricing to confirm at vendor source only**: Kinde free-tier MAU, Stytch free-tier MAU and first paid tier, Supabase Auth managed MAU allowance and overage rate, Clerk free tier and first paid tier. Also confirm at source whether Auth0 Free caps the number of applications, the pricing page does not say, so check the Auth0 docs quotas/limits page.
8. **Supabase hash export**: check supabase.com/docs/guides/auth/passwords and the GoTrue/auth admin API docs for whether `createUser` accepts a pre-hashed password, and whether the hash algorithm is documented. Also worth checking whether the *target* provider (Pocket ID is passkey-first; authentik/ZITADEL are password-capable) can import bcrypt at all, a passkey-only IdP makes the hash question moot.
