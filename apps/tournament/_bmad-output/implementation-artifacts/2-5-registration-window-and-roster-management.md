# Story 2.5: Registration window and roster management

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want to open and close registration and manage the roster,
so that I control who is enrolled before the bracket is generated.

## Acceptance Criteria

**Primary ACs (verbatim from [epics.md#Story 2.5](../planning-artifacts/epics.md), lines 400–420) — these are the contract:**

1. **(AC1 — registration window, FR-3)** _Given_ the registration window (FR-3), _When_ the admin opens or closes registration, _Then_ `tournament.state` reflects `registration_open` / `registration_closed` **and players can enroll only while open**.

2. **(AC2 — the `roster_entry` migration slice, this story)** _Given_ the `roster_entry` migration slice (this story), _When_ a player enrolls, _Then_ a `roster_entry` is created `UNIQUE(tournament_id, steamid64)` under RLS `FORCE`.

3. **(AC3 — roster management + lock, FR-3)** _Given_ roster management (FR-3), _When_ the admin removes a player **before bracket generation**, _Then_ the removal succeeds and is **reflected to all surfaces**; **after bracket generation, roster membership is locked**.

**Derived ACs (implementation-level; required for a working, testable slice — do not skip). These are story-authoring elaboration grounded in [SOLUTION-DESIGN.md §3](../planning-artifacts/architecture/architecture-cs-tournament-2026-06-30/SOLUTION-DESIGN.md) (the `roster_entry` DDL), the [ARCHITECTURE-SPINE.md](../planning-artifacts/architecture/architecture-cs-tournament-2026-06-30/ARCHITECTURE-SPINE.md) Lifecycle convention (line 235), AD-7 (two-policy RLS), AD-8 (server-gated mutations), and the PRD FR-3 consequences (prd.md:149–151) — NOT verbatim epic text:**

4. **(AC4 — migration 0004: `roster_entry` + FORCE RLS + AD-7 two-policy + explicit grants)** A **net-new** `supabase/migrations/0004_roster.sql` creates the `roster_entry` table exactly per the canonical DDL (SOLUTION-DESIGN.md:83–91): surrogate `id bigint generated always as identity` PK; `tournament_id bigint not null references tournament(id) on delete cascade`; `steamid64 text not null references player(steamid64) on delete restrict`; `bracket_seed int` (nullable **shell**, populated at bracket generation in Epic 4 — mirrors 0001's `final_match_id`/`fair_seed` nullable-placeholder precedent); `status text not null default 'active' check (status in ('active','removed'))`; `registered_at timestamptz not null default now()`; `unique (tournament_id, steamid64)`. Then `ENABLE` + **`FORCE`** RLS, the **AD-7 two-policy read** (`roster_entry_viewer_read` `for select to anon, authenticated using (status = 'active')` **+** `roster_entry_admin_read` `for select to authenticated using ((select public.is_admin()))`), and **explicit grants** (always-revoked default — `config.toml` `auto_expose_new_tables` unset): `grant select on roster_entry to anon, authenticated;` and `grant select, insert, update on roster_entry to service_role;` (**NOT** `delete` — soft-delete model, AC3/Decision 2). **No** forward FK to `match` (Epic 4 owns `match → roster_entry`). This is the FIRST table to **realize** the two-policy convention [migration 0002 forecast in its `status`-column comment](../../supabase/migrations/0002_rls.sql) (lines 87–98).

5. **(AC5 — player self-enroll route, authenticated-gated + state-gated)** A **net-new** `app/api/roster/enroll/route.ts` lets an **authenticated player enroll _themselves_** (FR-3, prd.md:149). It calls the **net-new `requireUser` gate** (the caller's identity from the **verified** session → their canonical SteamID64; fail-closed 401 on no/invalid session — the non-admin sibling of 2.4's `requireAdmin`), resolves the tournament that is currently `registration_open`, and inserts/reactivates a `roster_entry` for **the caller's own SteamID64 only** (never another id) via the service role. Enrollment is **rejected unless `tournament.state = 'registration_open'`** (AC1 "enroll only while open"). Node runtime, `dynamic = 'force-dynamic'`.

6. **(AC6 — admin registration + roster routes, `requireAdmin`-gated + state-gated + soft-delete)** Two **net-new** routes under the AD-8 `app/api/admin/` tree, both `requireAdmin`-gated (reuse 2.4's `lib/auth/admin-guard.ts` verbatim), Node runtime, dynamic: **(a)** `app/api/admin/registration/route.ts` opens/closes registration by `UPDATE`ing `tournament.state` between `registration_open` ↔ `registration_closed`, guarded so it **cannot re-open once the bracket is live** (write `WHERE state in ('registration_open','registration_closed')`); **(b)** `app/api/admin/roster/route.ts` lets the admin **add** a player (allowed while `state in ('registration_open','registration_closed')` — admin may add even after close, prd.md:150) and **remove** a player (soft-delete `status='removed'`, allowed only **before bracket generation** i.e. `state in ('registration_open','registration_closed')`, refused once `bracket_live`+ — AC3 lock). All writes via the service role; the acting admin's SteamID64 is recorded in the audit row (AC7).

7. **(AC7 — lock enforced, admin actions audited, scope held, suite accounting)** The **roster lock** (AC3) is enforced both by the route's state check **and** by the write's `WHERE`-clause state guard (a 0-row result → typed refusal, never a silent no-op), so once `tournament.state = 'bracket_live'` (or `ceremony`/`closed`) no enroll/add/remove succeeds. Each **admin** state-mutation (open/close registration, admin add, remove) writes an append-only **`audit_log`** row (`actor_steamid64` = acting admin, `tournament_id`, `action`, `detail` before/after) — **no migration** (`audit_log` + its `service_role` INSERT grant exist since 0003; `action` is uncapped `text`, so the new action strings need no schema change; roster/registration actions are **tournament-scoped**, so the 2.4 `grant_role` deferral-to-4.9 blocker does **not** apply here). **Scope held:** NO bracket generation or `bracket_seed` population (Epic 4), NO admin/viewer **UI** (deferred — see UX note), NO unreconciled-list (Story 2.6), NO per-season role/roster scoping (AD-18 deferred), NO `tournament`/`season` row _creation_ route (seeded prerequisite — see Dev Notes). `npm test` (Vitest) stays green with new specs; the new pgTAP suite carries an explicit `plan(N)` (retro action item #5); `supabase test db` stays green (existing 0001/0002/0003 suites unaffected + the new 0004 suite).

### ⭐ Central design decisions — surfaced to Cuatro (confirm before/at dev-story kickoff)

2.5 has **five** genuine judgment calls (more than prior stories because it is the first migration since Epic 1 **and** the first multi-actor slice). **All five were RESOLVED by Cuatro at the end of story creation (2026-07-05) — each took the RECOMMENDED option below** (like 2.2's "write BOTH" and 2.4's "Option A"). Tasks/ACs are built for these resolutions; the recommendations are retained below with the rejected alternative for dev/review context.

- **⭐ Decision 1 — Enrollment model (✅ RESOLVED, Cuatro 2026-07-05 → hybrid self-enroll + admin-manage).** The PRD **resolves** this (prd.md:149–151): players self-enroll while `registration_open` (prd.md:149); the admin can add even while closed (prd.md:150) and remove pre-bracket (prd.md:151). All writes go through **server routes using the service role** — there is **no** `authenticated` write policy on any event table (SPINE:295, AD-2 single-writer), so "self-enroll" is a **server route that writes the caller's own verified SteamID64**, never a client-side insert. **1b (sub-decision):** the self-enroll route needs a net-new `requireUser` gate (any authenticated caller → their verified id). RECOMMEND a **standalone** `requireUser` in `lib/auth/user-guard.ts` (regression-safe — leaves the live-QA'd `requireAdmin` untouched); optional DRY refactor only if `admin-guard.test.ts` stays green. _Alternative:_ admin-only roster (drop self-enroll) — contradicts prd.md:149's testable consequence, so not recommended.
- **⭐ Decision 2 — Removal = soft-delete vs hard-delete (✅ RESOLVED, Cuatro 2026-07-05 → soft-delete via `status='removed'`).** The canonical DDL includes `status ('active','removed')` (SOLUTION-DESIGN.md:88) — soft-delete is the designed model, and it makes AC3's "reflected to all surfaces" clean (the viewer `status='active'` policy hides removed rows) while keeping the admin/history record on this ~8–16-row table. Migration grants service_role `insert, update` but **not** `delete`, so a hard delete fails closed. _Alternative (PRD-safe):_ hard `DELETE` (prd.md notes no stats exist pre-bracket) — would need a `delete` grant, drops the `status` column's purpose, and forgoes the two-policy read; not recommended.
- **⭐ Decision 3 — Removal-lock boundary (✅ RESOLVED, Cuatro 2026-07-05 → per-action state gates).** SPINE:235 gates roster mutations to `registration_open`; AC3 allows admin removal "before bracket generation" (which includes `registration_closed`); prd.md:150 lets the admin add while closed. - **⭐ Decision 4 — Audit `audit_log` in this story vs defer to 4.9 (✅ RESOLVED, Cuatro 2026-07-05 → audit in 2.5).** FR-33 (prd.md:437) mandates every event-mutating **admin** action be logged with actor + timestamp; open/close registration and admin add/remove qualify. Unlike 2.4's `grant_role` (event-global vs `audit_log.tournament_id NOT NULL` → deferred to 4.9), roster/registration actions **are tournament-scoped**, so there is **no blocker** — and `audit_log` + its `service_role` INSERT grant already exist (0003), `action` is uncapped `text` (new strings need no migration). RECOMMEND writing the rows now (2.5 establishes; 4.9 generalizes the audited-route helper). Self-enroll (a player action) is **not** audited. _Alternative:_ defer all roster/registration audit to 4.9 for consistency with 2.4 — acceptable, but leaves FR-33 partially unmet in the interim; not recommended.
- **⭐ Decision 5 — UI scope (✅ RESOLVED, Cuatro 2026-07-05 → backend-first, defer the Admin Roster console + viewer state).** Unlike 2.4 (which had **no** IA entry), the UX docs **do** specify an "Admin console — Roster / registration" screen ([EXPERIENCE.md:43](../planning-artifacts/ux-designs/ux-cs-tournament-2026-06-30/EXPERIENCE.md)) and a viewer pre-event state ("**El evento aún no empieza. RECOMMEND shipping the migration + state machine + gated routes + tests + live-QA now and **explicitly deferring** the Roster console UI and the "Inscripciones abiertas" viewer copy to a later UI slice (Epic 5 / a follow-up) — framed as an **acknowledged deferral** (the surface is designed, just not built here), not "the docs are silent". _Alternative:_ build a minimal admin roster UI now — premature (no app shell), and larger than the epic implies; not recommended.

### Security / correctness requirements (non-negotiable)

- **Fail-closed everywhere.** Every ambiguous branch in `requireUser`, the `lib/roster.ts` functions, and the routes denies/rejects — never writes by default. No session → 401; non-admin on an admin route → 403; wrong tournament state → 409 `locked`/`registration_not_open`; a 0-row write → a typed refusal, never a silent "ok". Mirrors `is_admin()`'s `coalesce(...,false)` posture.
- **A player can only enroll THEMSELVES.** The self-enroll route reads the SteamID64 from the **verified session** (`requireUser`), never from the request body — no path lets player A enroll player B. The admin route is the only path that writes an arbitrary target id, and it is `requireAdmin`-gated + audited.
- **All writes via the service role, behind a gate.** Never add an `anon`/`authenticated` insert/update/delete policy on `roster_entry` — that would break the fail-closed posture the 0004 pgTAP proves (and the SPINE:295 invariant).
- **`steamid64` stays `text` end-to-end** — `STEAMID64_RE = /^[0-9]{17}$/` guards every id before a DB write; never parse to a JS `Number` (>2^53 precision loss).
- **Soft-delete, not hard-delete** (Decision 2) — removal is a `status` UPDATE; the migration grants no `delete`, so even the service role cannot hard-delete a roster row (the grant is the teeth, as 0003's append-only tables proved).
- **The lock is a real DB-write guard, not just a UI/route check** — the `WHERE state in (...)` clause means even a mis-ordered call after `bracket_live` writes nothing.
- **Secrets server-only (AD-25).** New `lib/` modules carry `import 'server-only'`; no service-role key or admin id reaches a client bundle.
