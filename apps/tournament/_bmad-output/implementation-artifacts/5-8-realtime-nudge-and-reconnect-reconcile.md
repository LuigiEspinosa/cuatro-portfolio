# Story 5.8: Realtime nudge and reconnect reconcile

Status: done

## Story

As a viewer,
I want live updates within ~2 s and a clean reconnect,
so that the event feels live but never shows invented or stale state.

## ⚠ Read this first — the five things that will bite you

1. **The emit side is ALREADY BUILT AND SHIPPED — do NOT add a second emitter.** Every semantic-change commit point posts its post-commit Broadcast today, from *inside* the DB transaction via `realtime.send(...)` on the public channel `tournament:<id>` (`private => false`): `match.approved` (`0017_aprobar_publish.sql:428-442`), `bracket.advanced` (`0013_advance.sql:839`, replaced in `0014_grand_final_reset.sql:633`), `match.rolled_back` (`0018_rollback_match.sql:377`), `match.manual_resolved` (`0019_manual_score.sql:377`). The walkover/forfeit path (`0015`) deliberately reuses the advance emitter — **no second emitter** (`0015_walkover_grace.sql:272`). AD-11 is explicit and repeated in-code: "Broadcast (server-emitted, post-commit) only *nudges* clients to re-render" and a fold calls `advance_match(..., p_emit => false)` so **exactly one** Broadcast carries the whole atomic change. **This story writes NO `realtime.send`, no `pg_notify`, no publication, no trigger.** Your entire job is the **consumer** — the first `.channel()`/`.subscribe()` in the repo.

2. **The Broadcast is a NUDGE, not the source of truth — re-fetch, never trust the payload, never replay.** AD-11: "every viewer surface is fully reconstructable from a published-state read alone… On reconnect a client **re-fetches the published snapshot** and never replays missed events." On any nudge you re-run the existing Approved-only reader for the current surface; you do **not** apply `match_id`/`score_a`/… off the wire, and you do **not** accumulate/replay a stream of missed events. The payload exists only so the emit can carry the semantic change atomically — the consumer's contract is "something changed → re-read published truth."

3. **The four snapshot readers are `import 'server-only'` — you CANNOT import them into a browser island.** `fetchFeedSnapshot` (`lib/feed/read.ts`), `fetchBracketSnapshot` (`lib/bracket/read.ts`), `fetchLeaderboard` (`lib/leaderboard/read.ts`), `fetchPlayerDetail` (`lib/player/read.ts`) all run in `force-dynamic` Server Components against the anon RLS client. The re-fetch seam from a client island is **Next.js `router.refresh()`** — it re-executes the current route's Server Components (re-invoking those readers verbatim) and reconciles the RSC tree in place, preserving scroll + client state. That IS "re-fetch the published snapshot, never replay." Do **not** reach for a client-side Supabase read of `timeline_feed`/`match` (that would re-implement the reader, bypass the model shaping, and risk the exact optimistic/replay bugs AD-11 forbids). The readers, the `TimelineFeed` list (`id`-keyed, `aria-live`), and the bracket `aria-live` region were all built in 5.6/5.7 **specifically annotated** "Story 5.8 re-invokes / refreshes this on a nudge."

4. **`Reconectando…` is muted, quiet, and NEVER wipes the screen.** `EXPERIENCE.md:120` (the "Offline / realtime-lag" State Pattern — this is the rule the epic calls UX-DR56; the literal token "UX-DR56" appears in no doc): *"If the realtime channel drops, hold the last known truth and show a quiet 'Reconectando…' — never wipe the feed or invent state. Reads stay available; no optimistic mutation on a viewer surface (they have none). On reconnect, reconcile silently to the Approved truth."* Muted chrome (`--ink-muted`/`.pillSoft` tone, `DESIGN.md:263`) — **not** alarm-red. The banned pattern (`EXPERIENCE.md:134`) is *"auto-refresh that wipes feed scroll position"* — the reconcile must not reset scroll (another reason `router.refresh()`, not a remount).

5. **Everything already exists to render this — reuse, don't invent.** The Spanish strings are **already in the module**: `es.live.reconnecting = 'Reconectando…'` and `es.live.loading = 'Cargando el evento…'` (`lib/i18n/es.ts:29-30`). The pill CSS variants `.pillLive` (blue, `@keyframes pulse`), `.pillDone` (gold static), `.pillSoft` (muted static) already exist (`app/(viewer)/viewer.module.css:39-86`) — the reconnect indicator is a **new state on the existing pill**, not a new component. The pill state machine `livePillState(state)` (`lib/feed/read.ts`) and the layout's `PILL_COPY` map (`app/(viewer)/layout.tsx:18-22`, currently only `on|off|final`) are the seams you extend. Realtime is already enabled server-side (`supabase/config.toml:87-88`).

## Dev Notes

### The one-paragraph mental model

The server already shouts "something semantic committed" on `tournament:<id>` after every Aprobar/advance/rollback/manual-resolve (via `realtime.send` inside the same transaction, so the shout can't outrun its commit). Nobody is listening yet. Your job: **listen in the browser, and when you hear anything, ask the server to re-render the page you're on** (`router.refresh()` → the `force-dynamic` Server Components re-read Approved-only truth). The Broadcast is a doorbell, not the mail — you never read the mail off the doorbell. When the doorbell wire is cut, you quietly say `Reconectando…` and keep showing the last page you rendered; when the wire is back, you ring your own doorbell once (`router.refresh()`) to catch up, and you never try to replay the rings you missed.

### The read model — nothing new to read; you re-invoke what exists

All four readers are **self-contained, `server-only`, Approved-only**, and were written for exactly this re-invocation (their header comments say so):

| Surface | Reader | Signature | Re-fetch trigger |
|---|---|---|---|
| Feed (`/`) | `fetchFeedSnapshot` | `(client, tournamentId)` | `router.refresh()` re-runs `app/(viewer)/page.tsx` |
| Bracket (`/bracket`) | `fetchBracketSnapshot` | `(client, tournamentId)` | `router.refresh()` re-runs `app/(viewer)/bracket/page.tsx` |
| Leaderboards (`/leaderboards`) | `fetchLeaderboard` | `(client)` | `router.refresh()` re-runs `app/(viewer)/leaderboards/page.tsx` |
| Player (`/jugador/[id]`) | `fetchPlayerDetail` | `(client, steamid64)` | `router.refresh()` re-runs the route |

`router.refresh()` refreshes the **active route + shared layout together**, so one island in `layout.tsx` makes every surface live *and* updates the pill (the layout re-resolves `currentTournament()` → `livePillState`). You do not enumerate surfaces or reader functions in the island — you refresh whatever route is mounted. **Do not** add a client-side `timeline_feed`/`match` read: it would duplicate the reader, skip the model shaping (`toCardModel`, bracket grouping, board building), and re-open the optimistic/replay hazards AD-11 forbids.

### Reconnect / cold-load semantics — the exact rules (cite these)

1. **Re-fetch published snapshot on reconnect; never replay** (AD-11 SPINE:133; SOLN:382).
2. **Hold last-known truth while disconnected; never wipe or invent** (`EXPERIENCE.md:120`). The DOM stays; `router.refresh()` reconciles rather than remounts (no blank, no scroll reset — `EXPERIENCE.md:134` bans scroll-wiping refresh).
3. **Quiet `Reconectando…`** (muted, `DESIGN.md:263`); **cold first load** may show `Cargando el evento…` — "never a blank screen" (`EXPERIENCE.md:108`). (5.6 already renders real content server-side, so cold-load is largely covered; `loading` is for the pre-subscribe instant.)
4. **Silent reconcile to Approved truth on reconnect** (`EXPERIENCE.md:120`); **no optimistic mutation** — viewers show confirmed Approved truth only, "no Viewer ever sees a result that later un-happens" (`EXPERIENCE.md:160`).
5. **Budget ~2 s** propagation to connected viewers (PRD:498,530; `EXPERIENCE.md:109,156`).

### Security boundary (AD-7 / AD-25 / AD-12)

- Re-fetch runs under the anon/authenticated **`FORCE` RLS** (approved-only, two fail-closed policies — AD-7 SPINE:110-113). The channel carries a nudge, **not** data, so it needs no privilege.
- **No service-role, no mirrored secret in the client bundle** (AD-25 SPINE:203; the first-build client-bundle leak scan is homed at Story 7.5 — keep this clean for it). Only `NEXT_PUBLIC_URL`/`_ANON_KEY` cross to the browser.

### Decisions this story makes (defaults chosen — flagged ones repeated at the end)

<a id="decision-refresh"></a>**Re-render mechanism = `router.refresh()`.** Default: on nudge/reconnect, call `router.refresh()` and let the `force-dynamic` Server Components re-read published truth. *Why:* it is the only path that honours "reconstructable from a published read alone / never replay" while preserving scroll + client state, and it reuses the four readers verbatim. *Rejected:* a client-side re-fetch (server action or route that re-runs a reader, then client-prepends) — heavier, re-implements shaping, and invites optimistic/replay bugs; a client Supabase `.from()` read — violates AD-11 and the `server-only` boundary. *Structure:* one `RealtimeNudge` island in the layout that owns the channel + status and either renders the pill directly or publishes status to a tiny context the client pill reads. *Flagged — recommend `router.refresh()`.*

<a id="decision-client-lib"></a>**Browser client = `@supabase/ssr` `createBrowserClient`.** Default: reuse the already-installed `@supabase/ssr` (`createBrowserClient`) so realtime auth rides the Supabase Auth cookie/session (AD-12) for free and no new dependency is added. *Alternative:* `@supabase/supabase-js` `createClient({ realtime })` — also fine, but a second client style. *Flagged — recommend `createBrowserClient`.*

<a id="decision-channel"></a>**Channel stays public (`private:false`), no migration.** Default: subscribe to `tournament:<id>` public, matching the shipped emitters' `private => false`; a public Broadcast needs no `realtime.messages` RLS to receive, so **no migration**. *Contingency:* if the installed Realtime build refuses a public receive without authorization, add `0023_realtime_read.sql` (+ pgTAP) with the minimal receive policy — nothing more. *Flagged — recommend public/no-migration; verify at dev (Task 6).*

<a id="decision-debounce"></a>**Coalesce nudges (~250–500 ms).** Default: debounce/coalesce a burst of nudges into one `router.refresh()` within the ~2 s budget (a single Aprobar already emits one Broadcast via the fold rule, but rapid successive admin actions could stack). *Flagged minor — recommend a small coalesce; the exact window is a knob.*

<a id="decision-final-reconnect"></a>**`Reconectando…` shows even in `final` state.** Default: a channel drop shows `Reconectando…` regardless of `on`/`final`, because freshness still matters mid-ceremony/post-final. *Alternative:* suppress reconnect chrome once `final` (nothing more will change). *Flagged minor — recommend show; cheap and honest.*
