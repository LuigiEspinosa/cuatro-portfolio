## Story

As a platform,
I want the match score derived from the demo whenever a demo exists, and the demo bound to the match it decided,
so that scores are never hand-typed and the admin has a `Pending` match to approve.

## Acceptance Criteria

**AC1 — demo-derived score (AD-5, FR-16; = Story 3.7's AC1).**
**Given** the score-source rule, **When** a demo is parsed for a match, **Then** the worker computes the demo-derived score and the match's `score_source` is `demo_derived`.
⚠ **Split across 4.6a/4.6b, deliberately.** 4.6a computes and persists the *derivation* (per-player round wins on `stat_row`); **4.6b writes `match.score_a`/`score_b`/`score_source`** inside the Aprobar transaction, because `SOLUTION-DESIGN.md:373` puts the score write there and `score_source_guard` (`0010:124-128`) forbids it before the demo is bound. 4.6a's proof obligation is that the derived tally **equals the demo's final round tally** (FR-16 `prd.md:272`).

**AC2 — single-writer precedence (AD-23; = Story 3.7's AC2).**
**Given** single-writer precedence, **When** a demo arrives for a match already committed `Forfeit` or `Bye`, **Then** the demo is archived for evidence but produces no `stat_row` and does not flip the match.
⚠ **Two of three halves already ship.** "Archived for evidence" is delivered by demo retention (AD-1, Stories 3.1/3.2). "Does not flip the match" is delivered by 4.5's `match_terminal_state_guard` (`0015:108-126`, `IC901`). **4.6a owns the remaining half**: `bind_match_demo` must REFUSE to bind a demo to a terminal match — proving the round-trip 4.5 could only install the guard for (`0015:55-56`).

**AC3 — `Pending` is reachable (FR-13, the Match lifecycle).**
**Given** the lifecycle `Live → Pending: demo parsed` (`ARCHITECTURE-SPINE.md:309`), **When** an admin binds a parsed demo to its bracket match, **Then** `match.demo_id`, `demo.match_id` and `stat_row.match_id` are populated and the match enters `pending` — the state 4.6b's Aprobar and 4.7's rollback both require.

## THE ONE-PARAGRAPH HEADLINE

**Nothing in this codebase can put a match into `pending`, and nothing can tell a demo which match it belongs to.** Those two gaps are the same gap, and this story closes it. The `match` table has carried a nullable `demo_id` and the `demo`/`stat_row` tables a nullable `match_id` since 0010, every one of them NULL on every row, each with a comment naming **this story** as their writer (`0010:28-29,153-155,170-171,180-181`). The score has no home either: `grep -i score supabase/migrations` was zero hits when 3.7 was deferred, and it still is — `stat_row` is 22 nullable Epic-5 stat shells with **nothing score-bearing**. ⭐ **And the retro action item that carried 3.7 forward specifies the wrong shape**: it says *"widen `ParseResult` with `score_a`/`score_b`"*, but `a`/`b` name the **match's competitor seats**, and the worker is match-agnostic **by AD-2 design** — it is the single writer of `demo`+`stat_row` only, it holds no `match_id` (only the external `matchzy_match_id`), and a grep of `worker/` for `match` DML returns zero. **It cannot know which player is `competitor_a`.** So the worker emits the only fact it is entitled to know — a per-SteamID64 round tally — and the seat mapping happens in 4.6b, inside the transaction where the bracket knowledge lives. That is also the only shape that satisfies the UX: the admin *"eyeballs the derived score"* in the queue **before** approving (`EXPERIENCE.md:44,209`), which a score computed only inside Aprobar could never be.
