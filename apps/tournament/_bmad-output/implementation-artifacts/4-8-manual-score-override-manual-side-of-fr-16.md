# Story 4.8: Manual score override (manual side of FR-16)

Status: done

> **⚠ THIS STORY IS THE THIRD SIBLING OF [`approve_match`](4-6b-aprobar-atomic-publish-publish-side-of-fr-13.md) AND [`rollback_match`](4-7-rollback-an-approved-match-rollback-side-of-fr-14.md).** All three are one-transaction, whole-bracket-locked, `advance`-calling, one-emit RPCs that publish a match result. `approve_match` writes a *demo-derived* result (`score_source='demo_derived'`, `state='resolved'`); **`manual_resolve_match` writes an *admin-entered* result (`score_source='admin_manual'`, `state='manual_resolved'`)** — the fallback for a match that has **no demo**, or the **audited override** of a demo whose score is wrong. Read `approve_match` end-to-end (`supabase/migrations/0017_aprobar_publish.sql:235-464`) before you write a line: your RPC mirrors its lock, its guard-before-write discipline, its `{ok:false}` typed refusals, its `advance_match(..., false)` fold, its single post-commit emit, and its audit shape — with **one score derived from two hand-entered numbers instead of a demo**, and **one genuinely new mechanism: the AD-5 audited-override gate**, which is `match_format_audited` (0012) rebuilt for the score.

## Story

As an admin,
I want to enter a manual score only where no demo exists or with an audited override,
so that demo-less matches can resolve without ever quietly overriding demo truth.

## Acceptance Criteria

Verbatim from [epics.md#Story 4.8 (lines 785-801)]. Traces: **FR-16 (manual) · AD-5, AD-23**.

**AC1 — the one-score-source rule (AD-5, FR-16).**
**Given** the one-score-source rule, **When** an admin enters a manual score, **Then** `score_source='admin_manual'` is permitted **only** when `demo_id IS NULL`, **or** when `manual_override=true` with a matching `audit_log` row, and the match becomes `ManualResolved`.

**AC2 — single-writer precedence (AD-23).**
**Given** single-writer precedence, **When** a manual score is entered, **Then** the `match` row remains the single arbiter and a `Resolved` (demo) result and a `Forfeit` cannot coexist.

### AC1's LOAD-BEARING SECOND CLAUSE — "a matching audit_log row" is a MECHANISM, not a convention

AD-5 (`ARCHITECTURE-SPINE.md:103`) is verbatim: *"an `admin_manual` score is permitted only when `(demo_id IS NULL)` **or** when `(manual_override = true AND a matching audit_log row exists)`."* AD-5's *Prevents* (`:102`) names the hazard: *"a demo-derived score and a hand-entered score silently disagreeing; the bracket advancing on the wrong one."* The live `score_source_guard` (`0010:124-128`, tightened `0017:155-169`) **already enforces the `manual_override=true` half** — but it says **nothing about the audit row**. Landing the override with a raw `service_role` UPDATE (`score_source='admin_manual', manual_override=true`, **no audit row**) passes `score_source_guard` today. That is the exact silent-override hole AD-5 + FR-16 (*"any manual override … is logged and flagged"*, `prd.md:273`, `prd.md:216`) exist to close, and it is the **same hole `match_format_audited` (0012) was built to close for FR-10**. **Treat "a matching audit_log row exists" as structural teeth, not RPC discipline** — see **DECISION C**.

### FR-16 / FR-10's "logged and flagged" clauses

- FR-16 (`prd.md:273`): *"A Demo-derived score cannot be silently overridden; any manual override (FR-10) is logged and flagged."*
- FR-10 (`prd.md:215-216`): *"when absent, the Admin enters the result and the entry is **logged as manual** … any manual override is **visible on the Match record**."* The "visible on the record" flag for the SCORE is `match.manual_override` (`0010:69`, `0012:67-76` — distinct from FR-10's `format_overridden_at`). `score_source='admin_manual'` is itself the record-level "this was hand-entered" badge.

## THE ONE-PARAGRAPH HEADLINE

**`manual_resolve_match` is `approve_match` with the score typed in by an admin instead of read off a demo, and it lands `manual_resolved` instead of `resolved`.** It serves **two** shapes (DECISION A), and the state↔`demo_id` correlation makes them clean: a **no-demo** match (`demo_id IS NULL`, sitting in `declared`/`live` — `Live → ManualResolved` is the lifecycle edge, and `declared → live` is unowned so a demo-less match sits in `declared` with its format locked) → a **plain** manual score (`manual_override=false`); a **demo-bound** match (`demo_id IS NOT NULL`, sitting in `pending` — the state `bind_match_demo` always produces, incl. after a 4.7 rollback) → an **audited override** (`p_override=true`, `manual_override=true`) that discards the demo's score. The admin submits `(score_a, score_b)`. In one whole-bracket-locked transaction the RPC guards everything before the first write (the AD-5 rule, the format lock, a tie, an undetermined seat), writes the audit row **first** (it is the *precondition* for the override gate, exactly as `declare_match_format` writes its row before the format UPDATE), then writes `score_a`/`score_b`/`score_source='admin_manual'`/`winner_entry`/`state='manual_resolved'` (plus `manual_override=true` **iff** overriding a bound demo), folds in `advance_match(..., false)` honouring its `{ok:false}` by raising (a distinct **IC906**) so a scored-but-unadvanced match never commits, posts one `match_result` `timeline_feed` entry (DECISION D — unlike 4.7's rollback, `match_result` fits a manual result perfectly), and emits **one** Broadcast post-commit. **The one genuinely new mechanism is DECISION C's `match_manual_override_audited` constraint trigger** — `match_format_audited` (0012) reborn for the score: when a match gains an `admin_manual` override, a matching `manual_score` audit row written by THIS transaction must already exist, or the write is refused for *every* writer, `service_role` and `postgres` included. **A manual match publishes NO stat rows (DECISION E) — the no-demo match has none, and an override deliberately discards the demo's rows; the `match` row itself is the published result.**

### The mechanism, precisely — every difference from `approve_match` is called out

1. **The whole-bracket lock, UP FRONT** — byte-identical to `approve_match` (`0017:265-271`), because you call `advance_match`, which locks the whole bracket in `id` order. Take it before the first write or reproduce the 4.3 `40P01` deadlock.
2. **Read the source under the lock:** `state`, `demo_id`, `competitor_a`, `competitor_b`, `score_source`, `format_locked`, `bracket_position`, `tournament_id`.
3. **Guards — ALL before any write, typed refusals RETURNED** (the 0012/0017 convention):
   - `bad_match` — no such match.
   - `not_manual_resolvable` — `state not in ('declared','live','pending')` (DECISION A). `declared`/`live` are the no-demo shape; `pending` is the demo-bound override shape. This is the guard that makes **AC2** true (you cannot manual-resolve a committed `resolved`/`forfeit`/`bye`/`manual_resolved`/`rolled_back` row).
   - `undetermined` — `competitor_a is null OR competitor_b is null` (an unseated bracket node has no winner to derive; `match_winner_is_competitor` `0010:94-98` would reject it anyway).
   - `format_not_declared` — `not format_locked` (the `manual_resolved`-needs-a-lock 23514 map, `0012:123-126`). Never fires on a `pending` match — `pending` already required a lock.
   - `bad_score` — `score_a`/`score_b` null or negative (the route validates too; the RPC is the authority).
   - `tied` — `score_a = score_b` (mirror `approve_match`'s DECISION K, `0017:337-342`): a draw has no winner and cannot advance a double-elim bracket.
   - ⭐ **the AD-5 rule (DECISION C), branching on `demo_id`** (the state↔`demo_id` correlation holds: `declared`/`live` ⟺ `demo_id IS NULL`; `pending` ⟺ `demo_id IS NOT NULL`, incl. a rolled-back match whose demo stays bound): if `demo_id IS NOT NULL` and **not** `p_override` → `override_required` (a demo is bound; discarding its score demands the explicit audited-override flag — this is the FR-16 dispute-correction: the admin looked at the demo-derived `pending` score and is overriding it). If `demo_id IS NULL` and `p_override` → `nothing_to_override` (surgical, like format's `override_needs_ids` — a mis-set override flag on a no-demo match surfaces an admin mistake). The two clean cases: `demo_id IS NULL, not override` → plain manual (`manual_override=false`); `demo_id IS NOT NULL, override` → audited override (`manual_override=true`).
4. **Derive the winner** — `v_winner := case when p_score_a > p_score_b then competitor_a else competitor_b end`; `v_loser` = the other. Capture `before` (`state`, `score_source`, `score_a`, `score_b`, `winner_entry`).
5. **Write the audit row FIRST (DECISION C — the precondition, not the receipt).** `action='manual_score'`, `target_match_id=p_match_id`, `detail` carrying a REAL `before`/`after` where `after = {state:'manual_resolved', score_source:'admin_manual', score_a, score_b, winner_entry, manual_override:<bool>}` + `override:<bool>`. The `match_manual_override_audited` trigger (DECISION C) matches its UPDATE against exactly this `after`.
6. **Write the match** — `score_a`, `score_b`, `score_source='admin_manual'`, `manual_override=(override case)`, `winner_entry`, `state='manual_resolved'`, in ONE UPDATE (score_source_guard needs all three score columns + the flag together). `demo_id` is UNTOUCHED (a demo, if present, stays bound as evidence — AD-1).
7. **Fold in the advance** — `advance_match(p_match_id, p_actor_steamid64, false)`; honour `{ok:false}` by raising **IC906** so the whole manual resolution rolls back (mirror `approve_match`'s IC903, `0017:381-386`). Do NOT change `advance_match`.
8. **NO `stat_row` write (DECISION E).** A no-demo match has zero stat rows; an override of a demo deliberately does NOT publish that demo's stats (the manual score is the score of record, contradicting them). The `match` row is the published result; the leaderboard (Story 5.5, over `status='approved'` rows) simply sees no stats for this match, which is correct.
9. **One `match_result` `timeline_feed` entry (DECISION D)** + **one emit** (`match.manual_resolved`, DECISION F) post-commit by construction. Mirror `approve_match:388-442`.
10. Return `{ok:true, state:'manual_resolved', score_a, score_b, winner_entry, override, advanced, champion}`.

## DECISIONS (made in-story; overrule at review — the 4.1–4.7 pattern)

**DECISION A — ⭐ the manual writer accepts `declared`, `live`, OR `pending`; nothing else — the two AD-5 shapes, keyed by the state↔`demo_id` correlation.** RECOMMENDED. AD-5 (`SPINE:103`) has TWO permitted `admin_manual` shapes, and each maps to a source state:
  - **No-demo (`demo_id IS NULL`)** → source `declared`/`live`. The lifecycle edge is `Live → ManualResolved` (`SPINE:310`), but `declared → live` is unowned (Epic-5 console — `0012:54-56`, `0016:38`), so a demo-less match sits in `declared` with its format locked. Plain manual entry, `manual_override=false`.
  - **Audited override (`demo_id IS NOT NULL`)** → source `pending`. `bind_match_demo` is the ONLY producer of `demo_id`, and it ALWAYS lands `pending` (`0016:243-246`); a 4.7 rollback also lands `pending` with the demo still bound. So the override case — the FR-16 dispute-correction where the admin looks at a demo-derived `pending` score and overrides it — necessarily operates on a `pending` match. **Refusing `pending` (an earlier draft's error) would make the entire override half of AD-5 unreachable**, since no `declared`/`live` match can ever carry a `demo_id`. `manual_override=true`, gated by DECISION C's audit trigger.

  The state↔`demo_id` correlation is exact (declared/live ⟺ demo_id null; pending ⟺ demo_id not null), so the RPC branches on `demo_id` and the accepted-state set is `{declared, live, pending}`. It REFUSES `resolved`/`manual_resolved`/`bye`/`forfeit`/`void`/`awaiting_grace`/`rolled_back` — which is what makes **AC2** true (a manual score can never coexist with a committed demo/forfeit/bye result; correcting an already-`resolved` match is 4.7 rollback → `pending` → override). ⚠ Overrule path: if Cuatro wants the override to require a rollback-to-`declared` first (never touching a `pending` demo-bound match), the override becomes unreachable without first widening 4.7's rollback to strip the demo — more moving parts for the same outcome.

**DECISION B — `manual_resolve_match` is a reusable `security invoker` RPC (not route-local logic), the manual sibling of `approve_match`.** RECOMMENDED — a hard constraint, same as 4.6b's DECISION J and 4.7's DECISION B. It takes the whole-bracket lock and calls `advance_match`, so it must be composable inside a larger transaction and callable in canonical lock order.

**DECISION C — ⭐ THE HEADLINE. The AD-5 "matching audit_log row" clause is enforced STRUCTURALLY by a new `match_manual_override_audited` constraint trigger — `match_format_audited` (0012) rebuilt for the score.** RECOMMENDED, and the direct analogue the codebase already blessed for FR-10. `score_source_guard` enforces `manual_override=true` for a demo-bound `admin_manual` score, but NOTHING enforces AD-5's *"AND a matching audit_log row exists"* — a raw `service_role` UPDATE can silently override a demo-derived score with `manual_override=true` and no trail. That is the exact silent-override hole AD-5 (`SPINE:100-103`) + FR-16/FR-10 (*"logged and flagged"*, `prd.md:273,216`) exist to close, and it is the SAME hole `match_format_audited` closes for the format. The trigger fires only on the `manual_override=true` branch (the demo-present override), requires the `manual_score` audit row written by THIS transaction describing the exact result, and RAISEs **IC907** if absent — for every writer, `postgres` included. ⚠ Overrule path: for a private friends event Cuatro may deem "the RPC writes the row" sufficient and drop the trigger (relying on `score_source_guard`'s flag). That leaves the audit-row clause a convention a raw UPDATE can bypass — inconsistent with FR-10's shipped teeth, so the trigger is recommended. Cost is ~40 lines + one pgTAP section, small next to the hole it closes.

**DECISION D — a manual resolution WRITES one `match_result` `timeline_feed` entry** (contrast 4.7 DECISION D, which DEFERRED because no `entry_type` fit a rollback). RECOMMENDED. A manual resolution IS a match result; `entry_type='match_result'` fits exactly, and 4.6b already provisioned it and set the precedent of writing it on publish. Writing it keeps the two "publish a match result" paths (demo-approve + manual) symmetric in the feed. No reader exists yet (5.6), same as 4.6b — provisioning, not premature. ⚠ Overrule path: defer it like 4.7 if Cuatro prefers the feed carry only demo-approved results until 5.6 exists; the audit row already logs the manual resolution regardless.

**DECISION E — a manual resolution writes NO `stat_row` and flips none to `approved`.** RECOMMENDED. A no-demo match has zero stat rows (AD-9's spirit — no demo, no stats). An *override* of a demo deliberately discards that demo's score, so publishing its stat rows (which contradict the manual score) would be wrong — they stay as they are. The `match` row is the published result; the leaderboard (Story 5.5, over `status='approved'`) correctly sees no stats for a manual match. So there is nothing to flip and nothing to build — the "removes/adds a leaderboard contribution" question is a NO-OP here, as it was for 4.6b/4.7.

**DECISION F — emit ONE `match.manual_resolved` Broadcast** on `tournament:<id>` post-commit (AD-11). RECOMMENDED. `SPINE:230` lists `match.approved`/`bracket.advanced`/… and specifies no manual event, so mint `match.manual_resolved` and note it as a new name (the same posture 4.7 took for `match.rolled_back`). The payload carries the new state + score + advance so a viewer re-fetches corrected truth (AD-11: a nudge). ⚠ Overrule path: reuse `match.approved` if the viewer only needs "a match got a published result — re-fetch"; minting a distinct name is recommended for audit legibility.

**DECISION G — the route is `POST /api/admin/manual-score`, symmetric with `approve`/`rollback`.** RECOMMENDED. The epic AC1/AC2 are about the WRITE (entering the manual score), not its rollback. `rollback_match` (4.7) refuses `manual_resolved` with `not_resolved` (4.7 DECISION C), so a mis-entered manual score currently has **no undo path** — a real gap, but a distinct concern the epic did not spec. **Intended home:** widen `rollback_match` to accept `manual_resolved` (reverting to `declared`/`live` + clearing the score, and un-seating dependent advances via its existing two-pass/AD-8 machinery), or a sibling RPC — most naturally Story 4.9 or a small Epic-4 follow-up. **Log a `deferred-work.md` entry.** ⚠ Overrule path: if Cuatro wants a mis-entry undoable now, the cheapest correct form is widening `rollback_match`'s state guard + its target-state mapping — a meaningful addition to 4.7's RPC, worth its own slice.

The path stays UNREACHABLE (a `manual_resolved` match is never `declared`/`live`, so no bind ever touches a `score_source`-set row), so this is robustness, not a live-bug fix — record that in Completion Notes. ⚠ Overrule path: if the change is deemed churn on an unreachable path, annotate the deferred item "unreachable, confirmed" and leave `bind.ts` untouched.
