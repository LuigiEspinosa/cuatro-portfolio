# Story 2.4: Roles, admin gating, and revoke-invalidates-session

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an operator,
I want admin and viewer roles enforced and a revoked admin's session invalidated immediately,
so that only admins can mutate the event and a stale JWT cannot retain admin after revoke.

## Acceptance Criteria

**Primary ACs (verbatim from [epics.md#Story 2.4](../planning-artifacts/epics.md), lines 381–398) — these are the contract:**

1. **(AC1 — server-enforced admin gating, FR-4)** _Given_ the role model (FR-4), _When_ any event-mutating action is attempted, _Then_ it is permitted only for an admin and is **server-enforced** (not merely hidden in the UI).

2. **(AC2 — revoke-invalidates-session, AD-12)** _Given_ an admin role is revoked (AD-12), _When_ the revoke is applied, _Then_ `app_role` is updated **and** the player's session is invalidated/forced to refresh, _And_ a previously issued JWT can no longer pass `is_admin()` after the refresh.

**Derived ACs (implementation-level; required for a working, testable slice — do not skip). These are story-authoring elaboration grounded in AD-8 / AD-12 / AD-17 / Story 4.9's enumerated "grant role" route — NOT verbatim epic AC text (the epic states only AC1/AC2 above):**

3. **(AC3 — the reusable `requireAdmin` gate — the primitive Epic 4 reuses)** A server-only guard resolves the caller's identity from the **verified** Supabase session (never trusting an unvalidated cookie) and authorizes an admin-only action. It is **fail-closed**: no session, a `getUser` error, a `viewer` claim, an unknown/absent role, or a thrown error → **denied** (HTTP 403), never allowed-by-default. On success it yields the acting admin's canonical SteamID64. This is the single primitive every Epic-4 command route (advance/approve/rollback/…) will reuse (AD-8), so it lives in `lib/` (injectable, unit-tested), not inline in one route.

4. **(AC4 — admin-only, server-gated grant/revoke route)** A **net-new** server route under the AD-8 `app/api/admin/` tree (`app/api/admin/roles/route.ts`) sets a target player's role. It calls `requireAdmin` first (non-admin → **403**, no write), validates the body (`{ steamid64, role }`, 17-digit target, `role ∈ {admin, viewer}` → **400** on malformed), and writes `app_role` **only** via the service-role client (no client write policy on `app_role`, AD-12). Runs on the Node runtime (`runtime = 'nodejs'`, `dynamic = 'force-dynamic'`), like the callback route.

5. **(AC5 — `granted_by` admin-only / no-self-grant invariant, enforced IN THE ROUTE)** On a role write the route stamps `app_role.granted_by` = the **acting admin's** SteamID64 (an admin by construction of AC3) and `granted_at = now()`; it **rejects a self-target** (acting admin's id === target id → **409/400**, no write) and refuses a target with no `player` row yet (never logged in → **400/404**). Enforced in the route, **not** a DB CHECK/trigger — [migration 0003's own header forbids adding one](../../supabase/migrations/0003_audit_snapshot.sql) ("_The granted_by admin-only / no-self-grant invariant → Story 2.4 server route (RLS can't enforce it; service-role writes bypass RLS). Do NOT add a CHECK/trigger here._"). No migration.

6. **(AC6 — revoke is durable AND heals the JWT mirror)** A revoke (or any role change) (a) **UPDATEs** `app_role` (durable authority — `resolveRole` reads `app_role` first, so a re-login **never** re-promotes a revoked admin even if they are still in `ADMIN_STEAMIDS`; update, never delete), and (b) re-mints the target's `app_metadata.role` via `admin.auth.admin.updateUserById(uid, { app_metadata: { steamid64, role } })` — **both keys** (the Admin API REPLACES `app_metadata`, no deep-merge; omitting `steamid64` clobbers it — established in `session.ts`). Consequently the target's **post-refresh** JWT carries the new role and `is_admin()` flips (satisfies AC2's "after the refresh"). **⭐ + the central decision below (AC3 re-reads `app_role` for instant enforcement) closes the residual stale-access-token window.**

7. **(AC7 — scope held; no migration; audit deferred; suite accounting)** **No** schema migration and **no** new table — `app_role` + `is_admin()`/`jwt_steamid64()` + grants + `audit_log` all already exist (0001/0002/0003). The `audit_log` row for `action='grant_role'` is **DEFERRED to Story 4.9** (its `tournament_id` is `NOT NULL` but a role change is event-global per AD-18; 4.9 formally owns the audited-command-route slice) — the `app_role.granted_by`/`granted_at` columns are 2.4's durable role-change record. Do **not** build the Epic-4 command routes that consume `requireAdmin`, any admin **UI** (no UX surface — backend-only), per-season role scoping (AD-18 deferred), `roster_entry`/registration (2.5). `npm test` (Vitest) stays green with the new specs; if any pgTAP is added it carries an explicit `plan(N)` (retro action item) — but note the DB-level `app_role` write-deny + `is_admin()` fail-closed matrix is **already fully proven** in `0002_rls_test.sql`, so new pgTAP is optional, not required.

### ⭐ Central design decision — where does `requireAdmin` read role from? (Option A vs B) — ✅ RESOLVED → **Option A** (Cuatro, 2026-07-05)

**DECISION: Option A — `requireAdmin` re-reads the authoritative `app_role` per request (instant revoke).** Build exactly as the tasks/ACs below specify (they were written for A): keep the `admin` param on `requireAdmin`, re-read `app_role`, and still heal the JWT mirror via `updateUserById`. Option B (trust the JWT claim, accept the ≤access-token-TTL window) was considered and **declined** — it leaves a real ~1h admin window post-revoke, the exact thing this story exists to close.

This is 2.4's **one genuine judgment call** (like 2.2's "write BOTH `app_role` + mirror" and 2.3's "AC6 in scope"). The role lives in **two** places: the `app_role` **table** (authoritative) and the **JWT** `app_metadata.role` mirror that `is_admin()` reads. Supabase access tokens are **stateless JWTs** — the gateway accepts any signed, unexpired token without consulting a revocation list, and there is **no admin "sign out by user id"** in `@supabase/auth-js` 2.110.0 (`signOut(jwt, scope)` needs the user's *live* access token, which an admin-initiated revoke does not have — verified against `node_modules/@supabase/auth-js/dist/main/GoTrueAdminApi.d.ts`). So a revoked admin's **already-issued** access token keeps `role:admin` until it expires (Supabase access-token TTL, default ~1h). That residual window is exactly what this story exists to eliminate.

- **⭐ Option A (RECOMMENDED — authoritative re-read = instant revoke):** `requireAdmin` reads the caller's `steamid64` from the verified JWT, then **re-reads `app_role`** (service role) to confirm `role='admin'` at request time. A revoke (`UPDATE app_role → viewer`) is effective on the **very next admin action** — the headline promise ("a stale JWT cannot retain admin after revoke") becomes literally true for mutating actions immediately, with no dependency on token-refresh timing. Cost: one indexed single-row `SELECT` (PK lookup) per admin action — negligible. Fully unit-testable server-side (no live token needed). Still **also** heals the JWT mirror via `updateUserById` (AC6) so `is_admin()` on the JWT converges for any RLS-read path on the next refresh.
- **Option B (leaner — trust the JWT claim, accept the ≤TTL window):** `requireAdmin` gates on `data.user.app_metadata.role === 'admin'` (literal `is_admin()` semantics, AD-8). Revoke = `updateUserById(app_metadata→viewer)` only; a previously-issued token keeps admin until it refreshes (matches AC2's literal "after the refresh"). Simpler, drops the `admin` param from `requireAdmin`, but leaves the real up-to-TTL admin window post-revoke.

**Recommendation: Option A.** It is the only design that makes the story's headline true without waiting on a refresh, it is cheap, and it aligns with `app_role` being the authoritative store (the same principle `resolveRole` already embodies). Both options keep the `updateUserById` mirror-heal (AC6) — Option A merely **adds** the app_role re-read in the gate. The tasks/ACs above are written for **Option A**; if Cuatro prefers B, gate on the claim and drop the `admin` param. (Optional independent hardening under either: lower the Supabase access-token TTL in the dashboard — an ops lever, not code.) **This is the decision to confirm before/at dev-story kickoff** (surfaced to Cuatro at the end of story creation).

### Security / correctness requirements (non-negotiable)

- **Fail-closed everywhere.** Every ambiguous branch in `requireAdmin`, `setRole`, and the route denies/rejects — never allows or writes by default. No session, an error, a viewer, an unknown role, a DB read error → denied. This mirrors `is_admin()`'s `coalesce(..., false)` posture and AD-7's "malformed policy fails closed."
- **Server-enforced, not hidden (AC1 / UX-DR4).** The gate is a real server rejection (403), not a UI affordance toggle. A viewer who hand-crafts a `POST /api/admin/roles` gets 403 + no write.
- **No client write path to `app_role`.** All writes via the service role, behind `requireAdmin`. Never add an anon/authenticated write policy/grant on `app_role` (would break the 0002 fail-closed proof).
- **`granted_by` is always a different admin.** No-self-grant makes `granted_by` a genuine accountability pointer and prevents an admin self-demoting into a lockout or self-promotion loop.
- **`steamid64` stays `text` end-to-end** — never parse to a JS `Number` (>2^53 precision loss). `STEAMID64_RE = /^[0-9]{17}$/` guards every id before a DB write (reuse the `roles.ts` const).
- **Revoke updates, never deletes** the `app_role` row — a persistent `viewer` row is what makes the revoke durable against re-login + allowlist re-promotion (`resolveRole` reads `app_role` first).
- **Secrets server-only (AD-25).** `admin-guard.ts` gets `import 'server-only'`; the service-role key never reaches a client bundle; no `NEXT_PUBLIC_` mirror (the `env.ts` `FORBIDDEN_PUBLIC_MIRRORS` guard already covers the relevant keys).
