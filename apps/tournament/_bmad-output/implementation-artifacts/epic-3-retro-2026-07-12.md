## What Went Well (keep doing this)

1. **"One state-machine node per story" was the star decomposition.** Each story mapped to exactly one node and stayed a thin, provable slice — scope was self-evident and reviews were fast.
2. **Pre-provisioning shells/grants ahead of need paid off, repeatedly.** 0005's nullable `demo` shells were filled by 3.2/3.3/3.4; `parse_generation` + the `stat_row` DELETE grant were provisioned early so **3.6 needed no migration**; the full `stat_row` column set means **Epic 5 enriches stats with no migration**.
3. **The DB-only ↔ worker-only mirror discipline.** 3.5 was pure DB (empty `worker/` diff); 3.6 and 3.8 were pure worker (empty `supabase/ app/ lib/` diff). A green `git diff` boundary became a *proof* that scope didn't leak.
4. **The injectable-seam/fake pattern ported cleanly from Epic 2.** `DemoStore`, `DemoRecorder`, `StatRecorder`, `RosterReader`, `DemoReader`, `Parser`, `Alerter` — all injectable; full orchestration coverage with no real R2/DB/`.dem` in unit tests (the Go analogue of Epic 2's `HttpPost` seam).
5. **One named decision per story, resolved with the Project Lead before dev** — carried straight from Epic 2's keep-doing list, and it held every story (3.7's entire disposition was resolved at create-story before a line was written).
6. **Every architectural invariant became running code.** AD-1 immutability is now *actively proven* — 3.6 re-hashes the retained object byte-for-byte and fails closed on mismatch. AD-2 single-writer, AD-3 idempotency, AD-7 two-policy RLS, AD-26 bounded async job — realized, not just asserted.

## Key Insights / Breakthroughs

- **Pre-provisioning only works when the architecture models a home for the column.** 3.5 rode the pre-provisioned `stat_row.status` shell; 3.6 rode `parse_generation` + the DELETE grant. 3.7 broke the streak precisely because **score lives on the not-yet-existent `match` table** — no shell existed anywhere the single-writer worker could persist. That is the difference between a clean shell-fill and a forced deferral, and it's a reusable planning heuristic.
- **The orthogonal-axes model.** `demo.validation_state` (anomaly-hold axis, admin-only) vs `stat_row.status` (publish axis, viewer-read). Kept distinct across 3.4/3.5/3.6, it prevented the classic "re-validating on re-parse looks like a Pending flicker" confusion (it isn't — different axis, invisible to viewers).
- **The live-QA gate stayed irreducible.** The real pgx `text[]` array binding for delete-missing, SHA-256 over a real 31 MB object, the off-request 200 timing and the `3s → 6s` backoff in 3.8 — none provable headlessly. Fakes cover orchestration; live-QA covers the real SQL/parse/timing. Same posture that made Epic 2 feel a notch harder than pure-SQL Epic 1.
- **AD-26 dual-ownership split cleanly** (3.8 mechanism / 7.4 hardening). The `Alerter` seam and the concurrency/attempts/backoff defaults were built as the exact injection/tuning points 7.4 will use — a rework-free hand-off.

## What Was Hard (systems-level, no blame)

- **The worker can't reach hosted Supabase from an IPv4-only host** (3.1 live-QA finding). `db.<ref>.supabase.co` is IPv6-only now; IPv4 needs the Supavisor pooler. Every Epic 3 live-QA ran against the *local* Supabase stack (R2 was real). **Resolved this retro** (see Action Items #2): a full-DSN `DATABASE_URL` override in `buildDatabaseURL`.
- **A second story deferred for the exact structural reason as 2.6.** 3.7's score has no home until `match` exists (Epic 4) — a mirror of 2.6 having no home until `stat_row` existed. Two epics, two "data source is a later epic's migration" deferrals: a sequencing signal worth naming (both caught cheaply at create-story, never mid-dev — the process working as intended).
- **The recurring "widest ripple" refactor.** Almost every worker story carried a predictable signature-change blast radius (3.2 `DemoRecorder`→`RecordOutcome`; 3.3 the `demo_id` provenance thread; 3.4 the `ValidationOutcome` param). Handled cleanly each time, but a standing tax.
- **The pgTAP-against-fully-migrated-schema gotcha.** 3.5's headline risk was that migration 0009 *invalidates* three assertions in 3.3's `0007` test, because every pgTAP file runs against the final schema. Caught and handled — but a real trap for every future migration that changes a prior table's posture.
- **The `Σkills==Σdeaths` conservation-gate tension** (3.4). Strict `==` false-positives on unattributed deaths. Kept the spec `==`, deferred the empirical call to live-QA — real demos balanced (16==16), so it held. Relax to `Σk > Σd` is now an approved Epic-5 change (Action Item #5).
- **The standing live-QA fixture was never operationalized.** Each live-QA improvised its own season/tournament/roster (3.4 ad-hoc, 3.5 direct-SQL, 3.6 ran with an *empty* roster, 3.8 seeded ad-hoc). A recurring papercut, finally being closed (Action Item #1).
