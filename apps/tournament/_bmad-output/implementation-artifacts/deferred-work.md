## Deferred from: code review of 2-1-steam-openid-2-0-server-side-login (2026-07-02)

- [ ] **Nonce double-submit uses an identical value in the cookie and the URL, and carries no embedded expiry.** The signed CSRF nonce is set both as the `steam_openid_nonce` httpOnly cookie AND carried in `openid.return_to` (`[app/auth/steam/login/route.ts:22-34]`); Steam echoes the full URL back, so any leak of the callback URL (browser history, `Referer` to third-party resources on `/`, proxy/access logs) discloses the same value that is the cookie's "secret" half — weakening the double-submit guarantee the code comment claims. The token itself (`[lib/steam/nonce.ts]`) embeds no timestamp; only the 10-min cookie `maxAge` bounds freshness, and the value isn't tracked server-side as consumed (the cookie IS deleted after use, giving practical single-use). **Intended home:** auth hardening pass (Epic 7) or Story 2.4. **Reason deferred:** for a casual private group the httpOnly cookie + HMAC signature + Steam signing the full `return_to` + cookie-deletion-after-use make this a defense-in-depth gap, not an exploitable hole. Revisit by using a distinct cookie-half value or an embedded expiry if auth surface widens.
- [ ] **`ensureAuthUser` doesn't re-assert `app_metadata.steamid64` on the "already exists" path.** `[lib/auth/session.ts:46-56]` sets the identity claim only at `createUser`; on the exists branch it no-ops. A Supabase auth user that pre-exists WITHOUT the claim (created manually, by an earlier code version, or a partial prior run) would mint a session whose JWT has no `steamid64`, so `jwt_steamid64()` (migration 0002) returns null and RLS fails closed silently for that user. **Intended home:** fold into Story 2.2 (which already touches `app_metadata` for role) via an `updateUserById` claim-upsert on the exists path. **Reason deferred:** low probability in a fresh single-environment project where every user is created by this exact code path; becomes worth fixing when role binding (2.2) makes a claimless session actively confusing.
- [ ] **Over-broad "already exists" classification in `isAlreadyExists`.** `[lib/auth/session.ts:30-39]` treats any `error.status === 422` as duplicate-user, but Supabase returns 422 for a range of validation failures (disallowed email domain, weak input, etc.). A genuine non-duplicate `createUser` failure would be swallowed, then surface less precisely at the downstream `generateLink` call. **Intended home:** same live-QA pass that resolves the AC5 `verifyOtp` decision. **Reason deferred:** the correct narrowing (prefer `code === 'email_exists'`, drop the bare `status === 422`) depends on the live Supabase error shapes — resolve empirically alongside the AC5 session-mint QA rather than guessing statically.
- [ ] **`display_name` from the Steam persona is written unbounded and un-length/charset-checked.** `[lib/players.ts:42,68]` passes `personaname` (only end-trimmed) into `player.display_name`, a `text` column with no length CHECK (`0001_core_schema.sql`). Very long, RTL, control-char, or 4-byte-unicode persona names land verbatim. **Intended home:** viewer-surface hardening (Epic 5) or a schema touch. **Reason deferred:** cosmetic for a casual group; React escapes on render, so no XSS today; a length cap is reasonable when leaderboards render names.
- [ ] **`check_authentication` response could also assert the OpenID namespace.** `[lib/steam/openid.ts:90]` requires `parsed['is_valid'] === 'true'` but not `parsed['ns'] === OPENID_NS`. **Intended home:** auth hardening pass. **Reason deferred:** the endpoint is a hardcoded HTTPS constant (no SSRF/attacker-controlled URL), so the added assertion is belt-and-suspenders, not a fix for a reachable hole.
- [ ] **Home page depends on a remote Steam button image.** `[app/page.tsx:39-44]` loads Valve's "Sign in through Steam" asset from `community.fastly.steamstatic.com` at render. **Intended home:** self-host the asset (small static file) in a UI polish pass. **Reason deferred:** cosmetic — the `<a href="/auth/steam/login">` link still works if the image 404s, so login is never blocked.

## Deferred from: code review of 2-2-bind-identity-and-role-into-app-metadata (2026-07-02)

- [ ] **`app_role` role value is cast `as Role` with no runtime validation.** `resolveRole` returns `existing.role as Role` / `raced.role as Role` (`[lib/auth/roles.ts:47-57]`) — a blind TypeScript cast, not a runtime guard. **Intended home:** revisit when the role set expands (e.g. a Story 2.4/beyond `superadmin`) or if `app_role` ever gains a non-Data-API writer. **Reason deferred:** fully guarded TODAY by migration 0001's `CHECK (role in ('admin','viewer'))` plus the strict `is_admin()` (`= 'admin'` → any unexpected value fails closed to non-admin), so there is no reachable defect. The only obligation is to keep the `Role` union in lockstep with the DB CHECK; a runtime guard now has ambiguous forward-compat semantics (would it downgrade a future legit role?), so it's not worth adding until the role set actually changes.
- [ ] **`23505` race re-read swallows its own error + depends on the exact PostgREST `code` string.** In `resolveRole` the concurrent-first-login recovery path (`[lib/auth/roles.ts:64-74]`) destructures only `{ data: raced }` (drops `error`) and branches on `insertError.code === '23505'`; a fault during the re-read is reported as "insert failed / duplicate key", and if PostgREST ever surfaces the unique violation under a different `code`, a legit concurrent first-login throws. **Intended home:** auth hardening pass. **Reason deferred:** the race requires two concurrent first-logins of the SAME SteamID64 — effectively impossible for a private friends roster (one person per Steam account). It fails closed (user retries). Minor diagnostic/robustness nit, not a defect.
- [ ] **A fully-malformed non-empty `ADMIN_STEAMIDS` silently yields an empty allowlist (everyone `viewer`) with no operator signal.** `parseAdminAllowlist` (`[lib/auth/roles.ts:26-34]`) drops every non-17-digit entry; if the whole var is mis-formatted, no admin is ever bootstrapped and nothing warns. **Intended home:** a small `console.warn` when `ADMIN_STEAMIDS` is set but parses empty (ops nicety). **Reason deferred:** conformant with AC7 (fail-closed to `viewer` by design); the live-QA gate (Cuatro's login must show `admin`) is the backstop, and for a casual single-admin v1 the silence is low-risk.

## Deferred from: code review of 2-3-canonical-steamid64-capture-and-display-name-tolerance (2026-07-03)

- [ ] **`defaultGet`'s real transport (fetch + timeout + `!res.ok` throw + `res.json()`) is never exercised by any test.** Every `fetchSteamProfile` test injects a mock `get`, so the default transport (`[lib/players.ts:29-38]`) — including the `AbortSignal.timeout(10s)`, the non-200 throw, and the JSON parse — ships unverified; a regression there (e.g. someone drops the `!res.ok` throw) would pass green. **Intended home:** a thin transport test (mock global `fetch`) or an auth hardening pass. **Reason deferred:** thin-glue coverage; mirrors 2.1's equally-untested `HttpPost` default seam — consistent precedent, low value for a casual event.
- [ ] **An unhydrated FIRST login writes a permanent 17-digit placeholder as `display_name`.** A brand-new player who logs in during a Steam outage (or before `STEAM_API_KEY` is configured — `env.steamApiKey()` returns `''`) gets a placeholder row `{display_name: steamid64, avatar_url: null}` (`[lib/players.ts:108-111]`; `display_name` is NOT NULL so *some* value is forced). It self-heals only if that same human logs in again while Steam is healthy — otherwise the id-as-name persists and is user-facing. **Intended home:** **Story 2.6** (unreconciled-SteamID64 list / roster-side reconciliation surface). **Reason deferred:** an accepted AC6 design consequence (login must produce a row; the null-path DO-NOTHING is what protects *existing* good values); heals on the next healthy login, and a backfill/reconciliation path is squarely 2.6's job, not 2.3's.
- [ ] **`ignoreDuplicates:true` makes a DO-NOTHING no-op indistinguishable from a real insert.** On the unhydrated path (`[lib/players.ts:108-111]`), `ON CONFLICT DO NOTHING` returns `error: null` whether it inserted a new placeholder row or silently skipped an existing one, and `upsertPlayer` returns `void` either way — so a genuinely-skipped write is reported as success. **Intended home:** revisit if/when a second UNIQUE constraint is added to `player`. **Reason deferred:** benign today — `player` has exactly one key (`steamid64` PK), so the only conflict target is the intended one; becomes a latent silent-skip footgun only the moment a second unique constraint on `player` lands.
- [ ] **AC6 avatar-only partial-200 clobber (sub-case of the resolved decision).** A Steam **200** with a *present* persona but a *missing* `avatarfull` (`[lib/players.ts:70]`) yields a truthy profile with `avatarUrl: null`, so the normal UPDATE path overwrites a stored good `avatar_url` with `null`. The code-review decision (Cuatro, 2026-07-03) chose **Option A** — fix the visibly-bad *name* clobber now (blank persona → `null`), and defer this rarer avatar-only case. **Intended home:** Epic 5 (viewer-surface hardening, alongside the `display_name` length/charset cap). **Reason deferred:** a nulled avatar is far less bad than a name becoming a 17-digit number, and a present-persona/missing-avatar 200 is essentially a malformed response; per-field preserve (Option B) needs a read-modify-write / DB-side COALESCE that this casual-event slice does not warrant. Revisit when avatars render on leaderboards.

## Deferred from: code review of 2-4-roles-admin-gating-and-revoke-invalidates-session (2026-07-05)

- [ ] **`findAuthUserIdByEmail` silently no-ops the mirror-heal past the 10,000-user pagination cap.** The lookup pages `listUsers` at `LIST_USERS_PER_PAGE=200` up to `LIST_USERS_MAX_PAGES=50` (`[lib/auth/roles.ts:184-197]`); a target sitting on page 51+ falls through to `return null`, and `healRoleMirror` treats `null` identically to "no auth user yet — deliberate no-op success" (`[lib/auth/roles.ts:168-169]`). So a real, logged-in user whose JWT mirror needs re-minting is indistinguishable from one who never logged in — the refresh-convergence half of a grant/revoke silently never happens, with no error and no log. **Intended home:** revisit if the auth-user count ever approaches 5-figures (or when a `getUserByEmail`/indexed lookup becomes available in `@supabase/auth-js`). **Reason deferred:** 10,000 users is orders of magnitude beyond this private friends event and the cap is a documented backstop; enforcement is unaffected (Option-A `requireAdmin` re-reads `app_role` regardless of the mirror), so the only residual is delayed `is_admin()` convergence on RLS-read paths for an out-of-scale user. Optional cheap hardening when touched: `console.warn` when the loop exhausts `MAX_PAGES` without a match, so a silent miss becomes visible.
