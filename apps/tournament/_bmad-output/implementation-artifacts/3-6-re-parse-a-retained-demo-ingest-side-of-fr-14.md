# Story 3.6: Re-parse a retained demo (ingest side of FR-14)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an **admin**,
I want to **deliberately re-parse a demo that is already retained** — re-deriving its `stat_row`s from the immutable raw `.dem` — with the whole **revert → reparse → republish** running as **one DB transaction** so existing published rows never flicker back to Pending,
so that **a fixed parser or a corrected derivation updates a match's stats in place**, replacing (never duplicating) rows and dropping any player the old parse produced in error, while the raw demo and its SHA-256 are never touched.

**This is the sixth story of Epic 3 — it turns the worker's one-shot "fresh acquire ⇒ parse" pipeline into a re-runnable derivation.** Today (`RunCLI`) an already-ingested demo **short-circuits and skips the parse** ([worker/ingest/cli.go:63-67](../../worker/ingest/cli.go#L63-L67)) — "deliberate re-parse is Story 3.6", it says in so many words — and `RecordParse` **upserts but never deletes** SteamIDs that a re-parse no longer produces ([worker/db/db.go:159-162](../../worker/db/db.go#L159-L162), [worker/db/db.go:178-184](../../worker/db/db.go#L178-L184)) — "that delete-missing is Story 3.6". 3.6 delivers exactly those two missing halves plus the `parse_generation` bump: a **deliberate re-parse entrypoint** that reads the **retained object back from the store** (never re-acquires, re-hashes to storage, or re-stores — AD-1), and a **`RecordReparse` transaction** that upserts the fresh rows **and** deletes the now-absent ones **and** bumps `demo.parse_generation`, all atomically.

The scope mirror-images Story 3.5: 3.5 was a **DB-only** slice (one migration + pgTAP, zero worker code); **3.6 is a worker-only slice** — Go code + Go tests, **no migration and no app/TS change**. The schema shells are already in place: `demo.parse_generation int not null default 1` ("bumps on re-parse (Story 3.6)" — [0005_demo.sql:37](../../supabase/migrations/0005_demo.sql#L37)) and the `service_role` **DELETE** grant on `stat_row` ("Story 3.6's re-parse deletes SteamIDs absent from a fresh parse, so the DELETE grant lands now (3.6 needs no grant migration)" — [0007_stat_row.sql:71-77](../../supabase/migrations/0007_stat_row.sql#L71-L77)). So `git diff supabase/ app/ lib/` must be **empty** — the exact inverse of 3.5's `git diff worker/ lib/ app/` empty.

It stops before the whole **republish/publish surface** that lives in Epic 4: the `Aprobar` action that creates the `Approved` state (Story 4.6), advancing the bracket, posting the feed, recomputing leaderboards, the "guard against already-consumed downstream bracket edges", the **admin-initiated rollback** without a re-parse (Story 4.7), the **server-gated audited re-parse command route** with its `audit_log action='reparse'` row (Epic 4 / Story 4.9), and the **async job + retry + MatchZy-HTTP trigger** (Story 3.8). 3.6 is the *worker mechanism* those later stories drive.

## Acceptance Criteria

> Restated from `epics.md#Story 3.6` (lines 561–582), elaborated with the design decisions resolved during story creation (see **Dev Notes → Key design decisions**). Traces: **FR-14 (re-parse) · AD-1, AD-3**.

**AC1 — A deliberate re-parse of a RETAINED demo re-derives its rows from the immutable raw `.dem`, reading the object back from the store (FR-14, AD-1, AD-3).**
The worker gains a deliberate re-parse entrypoint (recommended: `worker reparse --match <id>` — see Resolved Decision 1) that, given an already-ingested match, looks up its retained `demo` row, **reads the stored object back from the `DemoStore`** (`store.Get` — the read-back path `RunCLI` already flags "exactly the path Story 3.6 re-parse reuses", [cli.go:69-71](../../worker/ingest/cli.go#L69-L71)), parses it with the pinned `demoinfocs-golang v5.2.0`, re-validates (Story-3.4 gates), and republishes the rows. It **never re-acquires**: no `store.Put`, no new `demo` row, no new `storage_key` — the source of truth is the retained object, not a fresh upload. This is a **distinct** action from `RunCLI`'s fresh-acquire path (which still skips the parse on `AlreadyIngested` — that behavior is unchanged).

**AC2 — revert → reparse → republish is ONE transaction: upsert the fresh rows AND delete the now-absent SteamIDs, atomically, so there is no observable Pending window (FR-14, AD-3).**
A new `RecordReparse` writes in a **single** transaction: (a) upsert every freshly-parsed row `ON CONFLICT (match_id, steamid64) DO UPDATE` (replace, never duplicate — the AD-3 `stat_row UNIQUE(match_id, steamid64)` key), (b) **delete every `stat_row` for this `match_id` whose `steamid64` is absent from the new parse** (the "delete-missing" revert half — AD-3's "plus a delete of SteamIDs absent from the new parse"), and (c) bump `demo.parse_generation = parse_generation + 1` and re-stamp `parser_version`/`validation_state`/`anomaly_reasons`/`validated_at` on the same `demo` row. All-or-nothing: any error rolls the whole thing back (fail-closed), so published truth jumps old → corrected with **no intermediate state visible to any reader**.

**AC3 — `status` is preserved on re-upsert: an approved match's rows stay `approved` (no flicker to Pending); a genuinely-new SteamID lands `pending` (FR-14, AD-7).**
The upsert `DO UPDATE` set-list **does not touch `status`** (as `RecordParse` already omits it — [db.go:225-229](../../worker/db/db.go#L225-L229)), so a row that was `status='approved'` **stays `approved`** through the re-parse — this is the "no flicker back to Pending" guarantee on the **publish axis** (the axis viewers read, Story 3.5). A steamid the re-parse produces for the **first time** is INSERTed and takes the `'pending'` column default (correct — a newly-surfaced player is unpublished until an admin approves). Re-stamping `demo.validation_state='pending'` is on the **orthogonal anomaly axis** (Story 3.4) and does **not** make `stat_row`s invisible to viewers — do not conflate the two axes (see Dev Notes).

**AC4 — Re-parse touches ONLY derived rows; the raw demo and its stored SHA-256 are never altered (AD-1).**
The re-parse issues **no** `store.Put`/`store.Delete` on the retained object and **no** write to `demo.demo_sha256`/`storage_key`/`storage_backend`/`size_bytes` — only the derived `stat_row`s and the parse-metadata columns (`parser_version`, `parse_generation`, `validation_state`, `anomaly_reasons`, `validated_at`) change. As the AD-1 "re-hashable byte-for-byte" check, the re-parse **re-hashes the retained bytes as it reads them** (tee `store.Get` through SHA-256 while parsing) and **asserts the hash equals the stored `demo_sha256`**; on mismatch it **fails closed** (a corrupted/altered object must never silently re-derive) — the raw demo is proven immutable, not just left alone.

**AC5 — No migration, no app/TS change; the Approved-state publish, rollback, the audited route, and the async job are explicitly out of scope.**
`git diff --stat -- supabase/ app/ lib/` is **empty** (`parse_generation` + the `stat_row` DELETE grant already exist — 0005/0007; no schema change). `vitest run` and `next build` are unchanged. The whole deliverable is `worker/` Go code + Go tests. Explicitly **not** built here: the `Aprobar` publish that *creates* the `Approved` state (**Story 4.6**) — 3.6 only *preserves* an existing approved status through a re-parse, it never approves; the **republish side-effects** (advance bracket / post feed / recompute leaderboards / guard already-consumed downstream edges — AD-6/AD-8) — **Epic 4** (no `match`/bracket table exists); **admin-initiated rollback** without re-parse — **Story 4.7**; the **server-gated audited re-parse command route** (`is_admin()` re-check + `audit_log action='reparse'`) — **Epic 4 / Story 4.9**; the **async ingest job + retry + MatchZy-HTTP re-parse trigger** — **Story 3.8**.

## Dev Notes

### Key design decisions (resolved during story creation, 2026-07-12 — Cuatro to confirm at review; build for these)

1. **⭐ Story 3.6 is a WORKER-ONLY slice — Go code + Go tests, NO migration and NO app/TS change** (the mirror image of 3.5's DB-only slice). The re-parse entrypoint is a **new `worker reparse --match <id>` CLI subcommand** that reads the RETAINED object back from the store (never re-acquires). *(Chosen over: (a) adding a migration — unnecessary, `parse_generation` + the `stat_row` DELETE grant were pre-provisioned in 0005/0007 exactly so 3.6 needs none; (b) overloading `worker ingest` with a `--reparse <path>` flag that re-uploads a local file — that re-`Put`s bytes only to dedup-and-delete them, and reads a *local* file rather than the retained object, which is less faithful to "re-parse a **retained** demo"; (c) wiring re-parse into `server.go`/an async queue — that is Story 3.8 / Epic 4.)*
   *Why:* the AC says "re-parse a **retained** demo" — the R2 object is the source of truth (AD-1), so the truest entrypoint reads it back via `DemoStore.Get` (the path `RunCLI` already annotates as "exactly the path Story 3.6 re-parse reuses", [cli.go:69-71](../../worker/ingest/cli.go#L69-L71)). Everything the mechanical re-parse needs already exists in the schema; the two genuinely-missing behaviors are **delete-missing** (`RecordParse` explicitly defers it to 3.6) and the **`parse_generation` bump** (the column's own comment defers it to 3.6). A CLI subcommand keeps re-parse a deliberate operator action (not an accidental consequence of a re-ingest) and matches the "local-verify tool" character of `worker ingest`, with the server-route/queue drivers correctly deferred to Epic 4 / 3.8.

2. **⭐ "Re-parse an *Approved* match with no observable Pending window" is realized on the INGEST side as *status preservation*, not as an approval.** There is no `Approved` state reachable in Epic 3 (nothing flips `status→'approved'` until Story 4.6's `Aprobar`), and no `match`/bracket table (Epic 4). So 3.6 cannot *create* an approved match — it makes the re-parse **preserve** whatever `status` a row already has (upsert `DO UPDATE` omits `status`), which is exactly the "no flicker back to Pending" guarantee, and proves it by **seeding an approved row** at live-QA (the same technique 3.5 used to demonstrate the viewer/admin split before `Aprobar` existed). *(Chosen over inventing an approval path or a `match.state` here to make "Approved" real — that is Epic 4, and duplicating it would be guaranteed rework.)*
   *Why:* this is the direct analogue of 3.5's Resolved Decision 2 (the "match enters Pending" clause had no schema home in Epic 3; it was the derived aggregate of `stat_row.status`). Here, "re-parse an Approved match ⇒ jumps straight to corrected published truth" decomposes cleanly: the **publish axis** (`stat_row.status`, viewer-read per 3.5) is *preserved* by the upsert (3.6's job); the **atomic republish that advances the bracket / posts the feed / recomputes leaderboards** and *creates* the approved state is **Story 4.6/Epic 4's** job. 3.6 owns precisely the `stat_row`+`demo` transaction; SOLUTION-DESIGN §6 (L342-343) states the full "revert→reparse→republish in one transaction — no observable Pending window", and the bracket/feed/leaderboard limbs of that are unbuildable until Epic 4.

3. **⭐ Re-parse re-stamps `demo.validation_state='pending'` (the anomaly axis) — this does NOT contradict "no Pending window" on the publish axis.** A re-parse re-runs Story-3.4 validation and re-stamps `demo.validation_state` (`'pending'` = validated-clean, or `'anomalous'` = a gate failed). That is the **orthogonal anomaly-hold axis** (admin-only, [0008_demo_validation.sql:31-39](../../supabase/migrations/0008_demo_validation.sql#L31-L39)), **not** the `stat_row.status` publish axis viewers read (3.5). An approved `stat_row` stays `approved` regardless of `demo.validation_state`. Do not "fix" this by skipping re-validation or by touching `status`. *(Chosen to pre-empt the likely dev confusion that re-stamping `validation_state='pending'` looks like a Pending flicker — it is a different axis and invisible to viewers.)*

**⚠️ Headline risk — the delete-missing scope + the empty-set case.** The single biggest way this story goes wrong is the delete predicate. It **must** be `where match_id=$1 and steamid64 <> all($newset)` — scoped to the match, keyed on the *new parse's* SteamID64 set, **inside the same transaction** as the upsert. Get the empty-set case right: an empty `$newset` (a re-parse that now yields zero players) makes `steamid64 <> all(ARRAY[]::text[])` TRUE for every row, so **all** of the match's rows are deleted — which is correct (then `empty_stats` flags it anomalous). Passing `matchID` explicitly (not deriving it from `rows[0]`) is what makes the zero-player case even *possible* to express. A delete outside the tx, or scoped by `demo_id` instead of `match_id`, or forgetting the empty case, are the failure modes.

### Architecture patterns & invariants (must follow)

### The `RecordReparse` transaction (implement in `worker/db/db.go`)

```go
// RecordReparse re-derives a match's stat rows from a RE-PARSE of the retained demo, in ONE transaction
// (AD-3 revert→reparse): it (a) re-stamps parser_version + the Story-3.4 validation outcome AND bumps
// demo.parse_generation, (b) upserts every freshly-parsed row ON CONFLICT (match_id, steamid64) DO UPDATE
// — PRESERVING status (the DO UPDATE set-list omits it, so an approved row stays approved: AD-7, no Pending
// flicker), and (c) DELETES every stat_row for match_id whose steamid64 is absent from the new parse (the
// AD-3 "delete of SteamIDs absent from the new parse"). matchID is passed explicitly (not derived from
// rows) so a zero-player re-parse deletes ALL of the match's rows. Touches only derived rows — the raw
// demo + its sha256 are never written (AD-1). All-or-nothing (fail-closed on any error).
func (r *PgxStatRecorder) RecordReparse(ctx context.Context, matchID, demoID int64, parserVersion string, rows []StatRow, val ValidationOutcome) error {
    // Begin / defer Rollback (as RecordParse) ...
    // (a) UPDATE demo SET parser_version=$1, validation_state=$2, anomaly_reasons=$3::jsonb,
    //        validated_at=now(), parse_generation = parse_generation + 1  WHERE id=$4
    // (b) batch: INSERT ... ON CONFLICT (match_id, steamid64) DO UPDATE SET kills=..., deaths=...,
    //        rounds_played=..., demo_id=...   -- NB: no `status` in the set-list (preserve it)
    // (c) newIDs := []string{ each row.SteamID64 }
    //     DELETE FROM stat_row WHERE match_id=$1 AND steamid64 <> ALL($2::text[])   -- empty $2 ⇒ delete all
    // Commit ...
}
```

### Regression / boundary notes

- **The delete-missing predicate is the #1 risk** — `where match_id=$1 and steamid64 <> all($newset)`, inside the tx, empty-set ⇒ deletes all (see the headline-risk note). Do NOT scope it by `demo_id`, and do NOT run it outside the transaction.
- **Do NOT touch `status`/`approved_at`/`approved_by` on the upsert** — preserving `status` is the whole "no Pending flicker" guarantee (AC3). Adding `status` to the `DO UPDATE` set-list would re-pending an approved row.

- **Do NOT overload `worker ingest`** — re-parse is the separate deliberate `worker reparse` command; `ingest`'s `AlreadyIngested` short-circuit stays as-is.
- **Do NOT build** the `Aprobar`/approval write, the bracket-advance/feed/leaderboard republish, the rollback-without-re-parse (4.7), the audited command route + `audit_log` write (4.9), or the async queue/HTTP trigger (3.8).
